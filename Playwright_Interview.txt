Explain in detail lexical binding of this in playwright typescript cucumber


Why this guardrail is critical

In cucumber-js E2E setups, arrow functions break the lexical binding of this. Cucumber relies on regular functions to bind this to the custom "World" instance (which shares your Playwright page, browser, or context details across steps). Using an arrow function makes this evaluate to undefined or the outer scope, breaking your step definitions.

Option 1: The Native ESLint Guardrail (No Plugin Required)

If you are using modern ESLint (eslint.config.js / Flat Config), you can enforce this globally using the native no-restricted-syntax rule. It evaluates the abstract syntax tree (AST) to flag when an arrow function expression is passed directly into Cucumber functions (Given, When, Then, Before, After).
Add this object inside your eslint.config.js array:
javascript
import { defineConfig } from "eslint/config"; // If using modern Flat Config

export default [
  {
    files: ["**/*.steps.ts", "**/*.hooks.ts"], // Scope to your step definition and hook files
    rules: {
      "no-restricted-syntax": [
        "error",
        {
          selector: "CallExpression[callee.name=/^(Given|When|Then|Before|After|BeforeAll|AfterAll)$/] > ArrowFunctionExpression",
          message: "Do not use arrow functions in Cucumber step definitions or hooks. Use regular 'async function()' blocks to correctly preserve 'this' binding to the World context."
        }
      ]
    }
  }
];
Use code with caution.

Option 2: The Dedicated Plugin Guardrail

If you prefer a pre-built package, you can leverage the eslint-plugin-cucumber package. It features a built-in rule called no-arrow-functions specifically tailored for this issue.

1. Install the plugin:

bash

2. Configure it in your environment:

  }

The Correct Way to Write Step Definitions

Once the guardrail is in place, the linter will block arrow functions and mandate the standard function declaration syntax:
❌ Incorrect (Fails Linter):
typescript

  await this.page.goto('/dashboard'); // 'this' is undefined!

# Playwright Cucumber 
In Cucumber with Playwright and TypeScript, the Custom World class acts as an isolated, per-scenario state container. It allows you to share Playwright browser instances, page objects, and scenario-specific data across your step definitions smoothly without relying on global variables.

1. The Core Trap: Why this Fails for Newcomers

When using a Custom World, your page and context are attached to Cucumber's this context. You must use standard functions (async function()) instead of arrow functions (async () =>) in your step definitions. Arrow functions lexically bind this, which prevents Cucumber from injecting the scenario's World context.

2. Implementation Guide


Step 1: Create the Custom World (world.ts)

Define your custom world interface and class, then register it using setWorldConstructor.

// features/support/world.ts
import { setWorldConstructor, IWorldOptions, World } from "@cucumber/cucumber";
import { Browser, BrowserContext, Page } from "@playwright/test";

// 1. Define the type interface for safety
export interface ICustomWorld extends World {
  browser?: Browser;
  context?: BrowserContext;
  page?: Page;
  testData: Record<string, any>;
}

// 2. Implement the Custom World Class
export class CustomWorld extends World implements ICustomWorld {
  browser?: Browser;
  context?: BrowserContext;
  page?: Page;
  testData: Record<string, any> = {};

  constructor(options: IWorldOptions) {
    super(options);
  }
}

// 3. Register your world with Cucumber
setWorldConstructor(CustomWorld);
Use code with caution.

Step 2: Initialize Playwright via Hooks (hooks.ts)

Use Cucumber hooks (BeforeAll, Before, After) to manage the lifecycle of the browser and assign the current page to your CustomWorld instance.
typescript
// features/support/hooks.ts
import { BeforeAll, AfterAll, Before, After } from "@cucumber/cucumber";
import { chromium, Browser } from "@playwright/test";
import { CustomWorld } from "./world";

let globalBrowser: Browser;

BeforeAll(async function () {
  // Launch the browser once for the entire test suite
  globalBrowser = await chromium.launch({ headless: true });
});

Before(async function (this: CustomWorld) {
  // Create an isolated context and page for EVERY scenario
  this.browser = globalBrowser;
  this.context = await this.browser.newContext();
  this.page = await this.context.newPage();
});

After(async function (this: CustomWorld) {
  // Clean up and close tabs/contexts after each scenario finishes
  if (this.page) await this.page.close();
  if (this.context) await this.context.close();
});

AfterAll(async function () {
  // Shut down browser completely
  if (globalBrowser) await globalBrowser.close();
});

Step 3: Consume World in Step Definitions (steps.ts)

Explicitly type this as CustomWorld as the first argument of your step functions.
typescript
// features/step_definitions/login.steps.ts
import { Given, When, Then } from "@cucumber/cucumber";
import { expect } from "@playwright/test";
import { CustomWorld } from "../support/world";

Given("I am on the login page", async function (this: CustomWorld) {
  // Use 'this.page' populated by your Before hook
  await this.page!.goto("https://example.com");
});

When("I log in with valid credentials", async function (this: CustomWorld) {
  await this.page!.getByLabel("Username").fill("testuser");
  await this.page!.getByLabel("Password").fill("password123");
  await this.page!.getByRole("button", { name: "Login" }).click();
  
  // Storing state to share with subsequent steps if needed
  this.testData.username = "testuser"; 
});

Then("I should see the dashboard", async function (this: CustomWorld) {
  await expect(this.page!).toHaveURL(/.*dashboard/);
});
Use code with caution.

// features/steps/fixtures.ts
import { test as base } from 'playwright-bdd';
import { LoginPage } from '../../pages/LoginPage'; // Example POM

type MyBddFixtures = {
  loginPage: LoginPage;
  scenarioData: { userId?: string };

export const test = base.extend<MyBddFixtures>({

    await use(new LoginPage(page));

  scenarioData: async ({}, use) => {
    // This creates an isolated state object for every individual scenario
    await use({});
  },
});

// Export BDD step bindings tied to these specific fixtures
export const { Given, When, Then } = createBdd(test);

# Q : DOM Hierarchy 
===>  The Document Object Model (DOM) hierarchy in JavaScript is a tree-like structure that represents the architecture of an HTML document. When a browser loads a webpage, it parses the HTML and constructs this object-oriented representation in memory, allowing JavaScript to dynamically read, traverse, and modify the page content.

1. The Logical DOM Hierarchy

At the runtime level, the hierarchy begins even before the document itself, starting from the global browser context.
text
[window]                 <-- The global browser environment (BOM)
   │
   └── [document]        <-- The root entry point of the web page (DOM)
          │
          └── <html>     <-- The root element of the HTML document
               ├── <head>
               │     ├── <title>
               │     └── <link>
               └── <body>
                     ├── <h1>
                     ├── <p>
                     └── <div>
Use code with caution.
• window (BOM): The global object representing the browser window. It serves as the container for the entire execution environment.
• document: A property of the window object (window.document). It is the absolute entry point to the actual webpage content.
• Root Element (<html>): The primary node that encapsulates all other structural elements on the page.

2. The Node Inheritance Hierarchy (Prototype Chain)

Behind the scenes, every piece of the DOM tree is a JavaScript object. These objects inherit properties and methods from a strict class/interface hierarchy.

Interface / Class	Description	Key Properties & Methods
EventTarget	The root interface that allows objects to receive events.	addEventListener(), removeEventListener(), dispatchEvent()
Node	The base class for everything inside the document.	parentNode, childNodes, appendChild(), removeChild()
Document	Represents the entire webpage.	getElementById(), createElement(), body
Element	Represents an actual HTML or XML tag element.	querySelector(), innerHTML, classList, getAttribute()
HTMLElement	The base class for all standard HTML tags.	style, innerText, dataset, click()
Specific Elements	Specialized blueprints tailored to individual tags.	E.g., HTMLAnchorElement (href), HTMLImageElement (src)

Example: A <button> element inherits from: HTMLButtonElement → HTMLElement → Element → Node → EventTarget → Object.

3. Types of Nodes in the Tree

Not everything in the DOM tree is an HTML tag. The tree contains several specialized node types:
1. Element Nodes (Node.ELEMENT_NODE): The HTML tags themselves (e.g., <body>, <div>).
2. Text Nodes (Node.TEXT_NODE): The actual text inside tags, including whitespaces and line breaks.
3. Attribute Nodes (Node.ATTRIBUTE_NODE): The attributes applied to tags (e.g., class="container", href="...").
4. Comment Nodes (Node.COMMENT_NODE): HTML comments (<!-- comment -->) which remain accessible via script.

4. Navigating the Hierarchy

JavaScript provides two distinct pathways to traverse the DOM hierarchy: Node Traversal (which includes whitespaces/text nodes) and Element Traversal (which ignores text nodes and focuses strictly on HTML tags).
javascript
// Assume we start with an element: const base = document.querySelector('.item');

// ─── MOVE UPWARDS ───
let parent = base.parentElement;      // Gets the parent HTML element
let parentNode = base.parentNode;    // Gets the parent node (could be a document node)

// ─── MOVE DOWNWARDS ───
let HTMLchildren = base.children;     // Live HTMLCollection of element children only
let allNodes = base.childNodes;      // NodeList of all child nodes (includes text/spaces)
let firstTag = base.firstElementChild;// First child that is a tag

// ─── MOVE SIDEWAYS (SIBLINGS) ───
let nextTag = base.nextElementSibling;// Next sibling element on the same level

# Q : Explain your Playwright framework architecture. Why did you choose it?
===> In my current project, I have designed and worked with a modular Playwright automation framework using TypeScript, the Page Object Model (POM), and Playwright Test Runner. The main objective was to make the framework scalable, maintainable, reusable, and easy to integrate with CI/CD pipelines.

1. Framework Architecture
My framework follows a layered architecture, where each component has a specific responsibility.
Test Layer
Test Specs · Test Scenarios · Assertions

Page Object Layer
Locators · Page Actions · Reusable Methods

Core / Utility Layer
Fixtures · API Helpers · Test Data · Custom Utilities

Playwright Engine
Browser · Context · Page · Network Interception

Execution & Reporting
CI/CD · Parallel Execution · HTML Reports · Traces

3. Responsibilities of Each Layer
- Test layer: Contains test scenarios, test steps, and assertions. I keep business validation in the test cases rather than putting it inside page classes.
- Page Object Model: Each page has a separate class containing locators and reusable actions, such as login, search, or checkout.
- Fixtures: I use custom fixtures to initialize page objects, share common setup, and manage test-specific dependencies.
- Utilities: Contains reusable functions for API calls, test data generation, date handling, and common operations.
- API layer: I use Playwright's APIRequestContext for API validation, test-data setup, and cleanup.
- Configuration: playwright.config.ts manages browsers, base URL, timeouts, retries, parallel execution, screenshots, traces, and reporting.
- Reporting and CI/CD: I generate HTML reports, capture traces and screenshots for failures, and execute tests through Jenkins or another CI/CD pipeline.

4. Why Did I Choose This Architecture?
I chose this architecture for the following reasons:
  1. Maintainability: If a locator changes, I generally update it in one page object instead of multiple test cases.
  2. Reusability: Common actions, fixtures, API helpers, and utilities can be reused across tests.
  3. Parallel execution: Playwright supports parallel testing with isolated browser contexts, helping reduce execution time.
  4. TypeScript support: Static typing, interfaces, and IDE autocomplete help catch mistakes early and improve code readability.
  5. Reliable execution: Auto-waiting, web-first assertions, and locator strategies help reduce flaky tests.
  6. API and UI integration: I can create test data through APIs and validate the same data through the UI without performing every setup step manually.
  7. Debugging: Playwright traces, screenshots, videos when configured, and HTML reports make failures easier to investigate.
  8. CI/CD integration: The framework can run automatically on every build or deployment and provide feedback to the development team.

Q. Would you like to explore how to apply this exact data management architecture inside your Before/After hooks to securely attach authentication browser cookies straight onto your scenarios
===> Would you like to explore how to apply this exact data management architecture inside your Before/After hooks to securely attach authentication browser cookies straight onto your scenarios?

Applying this exact data management architecture inside your Before/After hooks allows you to handle global authentication injection safely without repeating the login UI steps for every single scenario.

By injecting authorization state (like cookies or localStorage tokens) straight onto your dynamic this context during the Before hook, you can bypass the login page completely for subsequent tests.

Step 1: Update the Shared Hook Types in world.ts
First, add an optional property to hold an authentication cookie or token payload within your CustomWorld interface.

// support/world.ts
import { World, IWorldOptions, setWorldConstructor } from '@cucumber/cucumber';
import { BrowserContext, Page } from '@playwright/test';

export interface CustomWorld extends World {
  context?: BrowserContext;
  page: Page;
  authToken?: string; // 👈 Holds the session token injected via the Before hook
}

export class PlaywrightWorld extends World implements CustomWorld {
  context?: BrowserContext;
  page!: Page;
  authToken?: string;

  constructor(options: IWorldOptions) {
    super(options);
  }
}

setWorldConstructor(PlaywrightWorld);

Step 2: Implement the Token Injection in the Before Hook

Instead of running a slow UI login flow for every single test scenario, you can fetch an auth token via a fast API call or read a pre-cached JSON state, then attach it to the this context before the test steps even start.

Remember, because the hook is part of Cucumber's lifecycle execution, you must use a regular function (async function) here as well so this resolves correctly.

// support/hooks.ts
import { Before, After } from '@cucumber/cucumber';
import { chromium, ChromiumBrowser } from '@playwright/test';
import { CustomWorld } from './world';

let globalBrowser: ChromiumBrowser;

Before(async function (this: CustomWorld) {
  // 1. Initialize a clean, isolated browser context per scenario
  if (!globalBrowser) {
    globalBrowser = await chromium.launch({ headless: true });
  }
  
  this.context = await globalBrowser.newContext();
  this.page = await this.context.newPage();

  // 2. Perform a fast API login bypass (simulate auth token retrieval)
  // In a real framework, replace this with a native fetch/axios request to your /login endpoint
  const simulatedToken = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.dummyToken12345";
  
  // 3. Save the token onto the dynamic 'this' context
  this.authToken = simulatedToken;

  // 4. Inject the cookie directly into Playwright's browser context before navigating
  await this.context.addCookies([
    {
      name: 'auth_session_token',
      value: this.authToken,
      domain: 'example.com',
      path: '/',
      httpOnly: true,
      secure: true,
      sameSite: 'Strict'
    }
  ]);
  
  console.log("🔒 Secure authentication state injected via Before hook.");
});

After(async function (this: CustomWorld) {
  // Gracefully tear down the browser resources to clean up memory leaks
  await this.page?.close();
  await this.context?.close();
});

Step 3: Seamless Navigation in the Step Definition File

Because the Before hook executes prior to any step definition, your browser context is already fully authenticated. You can jump directly to a protected page (like a user dashboard) without hitting a login redirect loop.

// steps/dashboard.steps.ts
import { Given } from '@cucumber/cucumber';
import { expect } from '@playwright/test';
import { CustomWorld } from '../support/world';

Given('I visit my private account dashboard', async function (this: CustomWorld) {
  // 1. Verify that the hook successfully provisioned the security state
  if (!this.authToken) {
    throw new Error("Security Failure: Authentication state was not populated by the Before hook.");
  }

  // 2. Navigate straight to a secure URL. Playwright will automatically pass the injected cookie along.
  await this.page.goto('https://example.com');

  // 3. Confirm that we are bypassed directly to the dashboard, skipping the login prompt
  const secureHeader = this.page.locator('h1.dashboard-title');
  await expect(secureHeader).toHaveText('Welcome to Your Account');
});

Use code with caution.

export class ApiClient {

	constructor(request: APIRequestContext) {
		this.request = request;
	}
	// Seeding method to instantly inject test entities into the backend
	async createTestUser(username: string, role: string) {
		const response = await this.request.post('https://api.example.com/v1/users', {
			data: { username, role }
		});
		if (!response.ok()) {

Part 2: Final Summary Blueprint: The Lexical Binding Guardrail
To close out our deep-dive architecture journey, let's look at the foundational ground rules for using this inside your Playwright TypeScript Cucumber framework:
The Guardrail Rule: If your project uses the Classic Approach (cucumber-js), arrow functions (() => {}) are strictly forbidden inside your step definition files (.steps.ts) and system hook hooks files (.hooks.ts).
The Root Cause: Arrow functions enforce lexical binding, locking this permanently to the module's top-level outer scope (undefined). This blocks Cucumber from executing .apply(), which means your Playwright instances (this.page) fail to inject and crash at execution time.
The Fixed Standard: You must enforce the use of standard function blocks (async function(this: CustomWorld) {}) inside your configuration rules. This enables dynamic runtime binding, meaning Cucumber can safely attach isolated test data, API clients, cookie caches, and page controls onto the execution instance per scenario.

Frame in Playwright : 
In Playwright, a Frame (Frame class) represents an XML/HTML document loaded inside a page, including the main page itself and any embedded <iframe> or <frame> elements. [1, 2]

Key Concepts & Structure
Main Frame: Every Page has a main frame accessible via page.mainFrame(). All standard page-level interactions (like page.click()) happen in the main frame by default. [1, 2]
Child Frames: Frames can contain nested sub-frames (<iframe crossorigin>, etc.). You can inspect the hierarchy using frame.childFrames() or list all frames on a page with page.frames(). [1, 2]
Lifecycle Events: The Page dispatches three primary events to track frame state:
page.on('frameattached'): Fired when a frame is attached to the page (only happens once per frame).
page.on('framenavigated'): Fired when a frame commits a navigation to a new URL.
page.on('framedetached'): Fired when a frame is detached/removed from the page (only happens once per frame). 
How to Access and Interact with Frames
Playwright provides two primary ways to work with frames:
1. Using page.frameLocator() (Recommended)
frameLocator returns a locator object that scopes all subsequent actions and assertions to the target iframe. It auto-waits for the iframe and the target element to be ready:
typescript
const username = page.frameLocator('.frame-class').getByLabel('User Name');
await username.fill('John');

Use code with caution.
Nested Iframes: You can chain .frameLocator() calls to drill down into multi-level nested frames: [1]
typescript
const innerElement = page.frameLocator('#outer-frame').frameLocator('#inner-frame').getByRole('button');
Use code with caution.
2. Using page.frame() (Direct Frame Object)
You can grab a specific Frame instance using its name attribute, URL, or a regex pattern matching its URL: [1, 2]
typescript
// By name attribute
const frameByName = page.frame('frame-login');

// By URL or regex
const frameByUrl = page.frame({ url: /.*domain.*/ });

if (frameByUrl) {
  await frameByUrl.fill('#username-input', 'John');
}

Use code with caution.
3. Properties and Methods on the Frame Object
Once you have a Frame object, you can query or interact with it directly:
frame.url(): Returns the current URL of the frame. [1]
frame.name(): Returns the name attribute of the frame. [1]
frame.parentFrame(): Returns the parent frame (or null if it's the main frame).
frame.childFrames(): Returns an array of child Frame objects. [1]
frame.locator(selector): Creates a locator scoped inside this specific frame. [1]
frame.contentFrame(): (From a locator) retrieves the frame corresponding to an iframe element.

Why Playwright's Approach is Different from Selenium
Unlike Selenium, where you must explicitly switch driver focus into a frame (switchTo().frame()) and switch back out, Playwright does not require context switching. You simply scope your locators using frameLocator or target elements directly while Playwright handles the underlying frame boundaries automatically. [1, 2, 3]

# Q : Tests pass locally but fail intermittently in CI/CD. How would you debug?
===> In my experience, if tests pass locally but fail intermittently in CI/CD, I treat it as a potential flaky test issue. I don't immediately increase retries or add hard waits. First, I investigate the failure using logs, screenshots, traces, and the CI environment details to identify the root cause.
I follow a systematic approach.

1. Analyze the CI/CD failure
First, I check the CI/CD execution logs and identify:
- Which test cases are failing?
- Is the failure consistent or intermittent?
- Is it a timeout, locator issue, assertion failure, API error, or environment issue?
- Does it happen only in headless mode or during parallel execution?
- Did the failure start after a recent code or application change?
For example, if a login test fails because the dashboard does not load within the expected time, I investigate whether the application is slow, the login API failed, or the test navigated incorrectly.

2. Use Playwright debugging artifacts
I configure screenshots, traces, and HTML reports to investigate failures in CI.
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  timeout: 30_000,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,

  use: {
    headless: true,
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },

  reporter: [
    ['list'],
    ['html', { open: 'never' }],
  ],
});


How I use these artifacts:
- Trace: Inspect the sequence of actions, locator resolution, network requests, and timing.
- Screenshot: Check the actual UI state at failure time.
- Video: Observe the sequence of interactions leading to the failure.
- HTML report: Identify failed tests, errors, and retry results.
I download the CI artifacts and open the trace using:
npx playwright show-trace trace.zip

This helps me determine whether the failure comes from the test script, application behavior, or execution environment.

3. Check synchronization and auto-waiting
A common cause is that the test interacts with an element before the application is ready.
Unreliable approach:
await page.waitForTimeout(5000);
await page.locator('#submit').click();

This adds a fixed delay and may still fail when the application takes longer than five seconds.
Better approach:
const submitButton = page.getByRole('button', {
  name: 'Submit',
});

await expect(submitButton).toBeVisible();
await expect(submitButton).toBeEnabled();
await submitButton.click();

await expect(
  page.getByText('Order submitted successfully')
).toBeVisible();

Playwright automatically waits for actionability conditions when performing actions such as click(). Web-first assertions also retry until their conditions are satisfied or time out.
I use explicit waits for meaningful application states rather than arbitrary sleep statements.

4. Investigate parallel execution and test data
Tests may pass individually but fail when executed together because of shared state or test data.
For example:
- Two tests update the same user account.
- Multiple workers create records with the same email address.
- One test deletes data required by another.
- Tests depend on execution order or share mutable global variables.

My approach:
1. Run the failing test individually.
2. Run it repeatedly to check whether it is intermittent.
3. Run the suite with one worker.
4. Check for shared test data and dependencies.
5. Use unique test data and isolated browser contexts.
# Run the specific test
npx playwright test tests/checkout.spec.ts

# Repeat the test to reproduce intermittent failures
npx playwright test tests/checkout.spec.ts --repeat-each=10

# Check whether parallel execution causes the issue
npx playwright test --workers=1
If the test passes with one worker but fails with multiple workers, I investigate race conditions, shared resources, and test isolation.

5. Compare local and CI environments
I compare the following settings between local and CI environments:
Area	:		What I investigate
1. Browser :		Browser version and headless behavior
2. Environment :	Base URL, credentials, environment variables
3. Performance : 	CPU, memory, network latency, and timeouts
4. Dependencies	: 	Node.js version, lockfile, installed packages
5. Test data :		Availability, permissions, and shared state
6. Infrastructure :	Service health, API responses, and network restrictions
I also try to reproduce the CI conditions locally by running tests in headless mode and, when applicable, inside the same Docker image used by the pipeline.

6. Investigate API and network failures
If the UI depends on backend services, I inspect failed API requests, response status codes, and request timing.
For example:
const responsePromise = page.waitForResponse(response =>
  response.url().includes('/api/orders') &&
  response.request().method() === 'POST'
);

await page.getByRole('button', {
  name: 'Place order',
}).click();

const response = await responsePromise;

expect(response.status()).toBe(201);
This helps distinguish a backend failure from a UI synchronization issue. I also verify that the application has completed the relevant operation before asserting the final UI state.

7. Use retries carefully
I may enable a limited number of retries in CI to collect additional diagnostic information. However, a retry is not the permanent fix.
For example, Playwright can classify tests as passed, flaky, or failed based on the initial result and retry outcomes. I monitor flaky results and investigate recurring failures rather than treating retry success as proof that the test is reliable.

My debugging workflow
Step 1: Identify the failure
CI logs, error message, failed assertion

Step 2: Inspect artifacts
Trace, screenshot, video, network activity

Step 3: Reproduce the failure
Run individually, repeat, compare workers

Step 4: Fix the root cause
Synchronization, isolation, data, environment, or application bug

Step 5: Validate the fix
Repeat the test and run the full regression suite in CI


Real-world example you can explain in an interview
“Suppose my checkout test passes locally but intermittently fails in Jenkins. I first inspect the HTML report and trace. I find that the checkout button is clicked, but the confirmation message is not displayed. I check the network requests and discover that the order API sometimes takes longer to respond in CI. I replace any fixed sleep with an appropriate response or UI-state wait, verify the API result, and ensure the test data is isolated for parallel execution. Then I rerun the test repeatedly and execute the regression suite in CI to confirm the fix. If the API itself returns an error, I report it as a possible application or environment defect instead of hiding it with retries.”
Only use this example as your own project experience if it reflects a scenario you have actually encountered.
Strong closing statement
“My approach is to identify the root cause rather than simply make the test pass. In Playwright, I rely on traces, screenshots, HTML reports, web-first assertions, proper test isolation, and environment comparison. I use retries for diagnosis, but I fix the underlying issue to make the automation suite stable and reliable in CI/CD.”

# Q : A button becomes enabled after multiple API calls. How would you handle it without `waitForTimeout()`?
==> If a button becomes enabled only after multiple API calls are completed, I would avoid waitForTimeout() because the response time can vary between local and CI/CD environments.
Instead, I would use Playwright's web-first assertions to wait for the button to become enabled, or wait for specific API responses if I need to verify that the required API calls have completed.

Approach 1: Wait until the button is enabled (my preferred approach)
import { test, expect } from '@playwright/test';

test('Button should become enabled after loading', async ({ page }) => {
  
  await page.goto('/checkout');

  const submitButton = page.getByRole('button', { name: 'Submit Order',  });

  // Automatically retries until the button is enabled or times out
  await expect(submitButton).toBeEnabled();

  await submitButton.click();
});

Why do I use this approach?
- toBeEnabled() automatically retries until the button becomes enabled or the assertion times out.
- It does not depend on a hardcoded delay.
- It is simple and reliable when I only care about the final UI state.

Approach 2: Wait for multiple API responses
If the requirement specifically says that three API calls must complete before the button is enabled, I can wait for those responses explicitly.
import { test, expect } from '@playwright/test';

test('Enable button after required API calls', async ({ page }) => {
  const requiredApis = [
    '/api/user',
    '/api/products',
    '/api/permissions',
  ];

  const responsePromises = requiredApis.map((endpoint) =>
    page.waitForResponse((response) =>
      response.url().includes(endpoint) &&
      response.ok()
    )
  );

  await page.goto('/checkout');

  // Wait for all three successful API responses
  await Promise.all(responsePromises);

  const submitButton = page.getByRole('button', { name: 'Submit Order', });

  await expect(submitButton).toBeEnabled();
  await submitButton.click();
});
Important: I register the response listeners before navigation so I don't miss requests triggered during page loading. This example assumes all three endpoints are requested during navigation and each returns a successful response. If they are triggered by a user action, I register the listeners before that action instead.

Approach 3: Wait for a specific API response and then verify the UI
When a particular API determines whether the button can be enabled, I wait for that response and assert the UI state.

const permissionsResponse = page.waitForResponse(response =>
  response.url().includes('/api/permissions') &&
  response.request().method() === 'GET'
);

await page.getByRole('button', { name: 'Load Data' }).click();

const response = await permissionsResponse;
expect(response.ok()).toBeTruthy();

const submitButton = page.getByRole('button', {
  name: 'Submit Order',
});

await expect(submitButton).toBeEnabled();


This approach is useful when a user action triggers the API call.
Which approach would I choose?
Scenario : 					Approach
1. Only the final button state matters : 	await expect(button).toBeEnabled()
2. All required API calls must complete : 	Promise.all() with waitForResponse()
3. A user action triggers an API call :		Register waitForResponse() before the action
4. API calls are dynamic or repeated : 		Track the relevant requests or wait for a meaningful application state

My interview conclusion:
“I prefer waiting for the expected UI state using Playwright's web-first assertions. If the requirement depends on multiple backend calls, I explicitly wait for the relevant responses using Promise.all() and then verify that the button is enabled. This avoids hard waits and makes the test more reliable in CI/CD.”

# Q : How do you handle multiple browser tabs and validate data between them?
==>  In Playwright, I handle multiple browser tabs using context.waitForEvent('page') or page.waitForEvent('popup'), depending on how the new tab is opened.
I register the event listener before clicking the link or button to avoid missing the new tab event. Once the new tab opens, I can interact with both pages and validate that the data is consistent between them.
1. Scenario: Open a new tab and validate data between tabs
For example, suppose I have an application where clicking View Order Details opens a new tab. I need to validate that the order ID displayed in the first tab matches the order ID in the second tab.
import { test, expect, Page } from '@playwright/test';

test('Validate order data between multiple tabs', async ({ page }) => {
  await page.goto('https://example.com/orders');

  // Get the order ID from the first tab
  const orderId = await page.locator('#orderId').innerText();

  // Register the listener before clicking
  const newTabPromise = page.waitForEvent('popup');

  await page.getByRole('link', { name: 'View Order Details', }).click();

  // Capture the newly opened tab
  const newTab = await newTabPromise;

  await newTab.waitForLoadState();

  // Validate the order ID in the second tab
  await expect(newTab.locator('#orderDetailsId')).toHaveText(orderId);

  // Validate the second tab's page
  await expect(newTab).toHaveURL(/order-details/);
});

Why use page.waitForEvent('popup')?
- It captures a new tab opened by the current page.
- Registering the listener before the click prevents race conditions.
- It gives me a separate Page object to interact with the new tab.
The selectors and URL in this example are placeholders; I would replace them with the application's actual locators.

2. Scenario: Handle multiple tabs opened from the browser context
If the application opens a new tab through a mechanism where I want to listen at the browser-context level, I use context.waitForEvent('page').
import { test, expect } from '@playwright/test';

test('Handle multiple pages', async ({ context, page }) => {
  await page.goto('https://example.com');

  const newPagePromise = context.waitForEvent('page');

  await page.getByRole('link', { name: 'Open Report', }).click();

  const reportPage = await newPagePromise;

  await reportPage.waitForLoadState();

  await expect(reportPage).toHaveTitle(/Report/);

  // Both pages can be used independently
  await expect(page).toHaveURL(/example\.com/);
  await expect(reportPage).toHaveURL(/report/);
});


The difference is:
- page.waitForEvent('popup') is appropriate when the new tab is opened by a specific page.
- context.waitForEvent('page') listens for a new page created anywhere within that browser context.

3. How do I validate data between tabs?
Suppose a user selects a product in the first tab and opens its details in the second tab. I compare the values from both pages.
const productName = await page.locator('[data-testid="product-name"]').innerText();
const productPrice = await page.locator('[data-testid="product-price"]').innerText();
await expect(newTab.locator('[data-testid="detail-name"]')).toHaveText(productName);
await expect(newTab.locator('[data-testid="detail-price"]')).toHaveText(productPrice);

This approach is useful for validating:
- Order IDs between order and invoice tabs.
- Product names and prices between listing and detail tabs.
- User information between profile and account tabs.
- Transaction details between payment and confirmation tabs.
For values that load asynchronously, I prefer Playwright's retrying assertions rather than extracting text too early and comparing immediately.

# Q : How do you handle shadow DOM inputs in Playwright vs Selenium?
==> In my automation projects, I handle Shadow DOM elements differently in Playwright and Selenium.
A Shadow DOM is used in web components to encapsulate HTML, CSS, and JavaScript. Sometimes, normal DOM inspection or traditional locators cannot directly access elements inside a shadow root.
The main difference is that Playwright supports locating elements inside open Shadow DOMs by default, whereas Selenium generally requires locating the shadow root first and then finding the elements inside it.
1. Playwright with TypeScript
Suppose the application contains this structure:
<login-component>
  #shadow-root (open)
    <input id="username">
    <input id="password">
    <button id="login">Login</button>
</login-component>


In Playwright, I can directly locate the input fields using CSS selectors or other supported locators without explicitly accessing the shadow root.
import { test, expect } from '@playwright/test';

test('Handle Shadow DOM inputs', async ({ page }) => {
  await page.goto('https://example.com');

  const username = page.locator(
    'login-component #username'
  );

  const password = page.locator(
    'login-component #password'
  );

  await username.fill('testuser');
  await password.fill('password123');

  await page.locator(
    'login-component #login'
  ).click();

  await expect(page).toHaveURL(/dashboard/);
});


Why does this work?
	Playwright's CSS locators and most other locators, such as role and label locators, pierce open Shadow DOM boundaries automatically.

There are exceptions: XPath does not pierce Shadow DOM boundaries, and closed Shadow DOM roots are not accessible through Playwright's normal locators.

2. Selenium with Java
In Selenium, I explicitly retrieve the shadow root using getShadowRoot() and then locate the input fields inside it.
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.SearchContext;

public class ShadowDOMExample {
    public static void main(String[] args) {
        WebDriver driver = new ChromeDriver();

        try {
            driver.get("https://example.com");

            // Locate the web component host
            WebElement host = driver.findElement(By.cssSelector("login-component") );

            // Access its open shadow root
            SearchContext shadowRoot = host.getShadowRoot();

            // Locate elements inside the shadow root
            WebElement username = shadowRoot.findElement(By.cssSelector("#username"));

            WebElement password = shadowRoot.findElement(By.cssSelector("#password") );

            WebElement loginButton = shadowRoot.findElement(By.cssSelector("#login"));

            username.sendKeys("testuser");
            password.sendKeys("password123");
            loginButton.click();

        } finally {
            driver.quit();
        }
    }
}


Here, SearchContext represents the shadow root context in which Selenium searches for elements.
This approach requires a Selenium version that supports getShadowRoot().

3. Key differences: Playwright vs Selenium
Feature			|	Playwright	|	Selenium
1. Open Shadow DOM	| Supported by default	| Explicitly access shadow root
2. Access shadow root	| Usually not required	| getShadowRoot()
3. Locate nested shadow elements |	Direct locators can pierce open roots |	Access each nested root step by step
4. XPath across shadow boundary	| Does not pierce the boundary	| Cannot cross it directly either
5. Closed Shadow DOM	| Not accessible through normal locators  |	Not directly accessible through standard shadow-root APIs
6. Waiting for elements	| Auto-waiting and retrying assertions |	Usually explicit or implicit waits as needed

4. What if Shadow DOM is nested?
For example:
<outer-component>
  #shadow-root (open)
    <inner-component>
      #shadow-root (open)
        <input id="email">


In Playwright:
const email = page.locator('outer-component inner-component #email');
await email.fill('user@example.com');

In Selenium Java:
WebElement outerHost = driver.findElement( By.cssSelector("outer-component"));

SearchContext outerRoot = outerHost.getShadowRoot();

WebElement innerHost = outerRoot.findElement(By.cssSelector("inner-component"));

SearchContext innerRoot = innerHost.getShadowRoot();

WebElement email = innerRoot.findElement(By.cssSelector("#email"));

email.sendKeys("user@example.com");


In Selenium, I access each shadow root individually because each shadow root creates a separate search context.
5. What if the Shadow DOM input is dynamic?
In Playwright, I use a locator and a web-first assertion rather than a fixed wait:
const email = page.locator('login-component #username');

await expect(email).toBeVisible();
await expect(email).toBeEnabled();
await email.fill('testuser');


In Selenium, I use WebDriverWait to wait for the element to become available or clickable. For dynamic shadow components, I may need to reacquire the host and shadow root if the component is re-rendered.
Final interview answer
“In Playwright, I can interact with inputs inside open Shadow DOMs directly using normal supported locators, without manually retrieving the shadow root. In Selenium Java, I first locate the shadow host, call getShadowRoot(), and then locate the input within that shadow root. For nested Shadow DOMs, I repeat this process for each level in Selenium. I also account for dynamic components using Playwright's auto-waiting or Selenium's explicit waits. This is one reason I find Playwright simpler for modern web applications that use web components.”

# Q : Fix dynamic element wait issue on fast-loading React forms
==> In React applications, elements may render dynamically, re-render after state updates, or become enabled only after API calls finish. Sometimes, an element appears briefly and gets replaced during a React re-render.
In these situations, I avoid waitForTimeout() and use Playwright locators, web-first assertions, and waits for meaningful application states.
1. Problem: Element gets detached during React re-render
A common mistake is storing an ElementHandle and reusing it after the DOM changes.
Unreliable approach:
const submitButton = await page.locator('#submit').elementHandle();

await page.locator('#name').fill('John');

await submitButton?.click();
React might replace the button after the input changes, leaving the stored handle detached from the DOM.

Better approach:
import { test, expect } from '@playwright/test';

test('Submit dynamic React form', async ({ page }) => {
  await page.goto('/register');

  await page.getByLabel('Name').fill('John');
  await page.getByLabel('Email').fill('john@example.com');

  const submitButton = page.getByRole('button', {name: 'Submit',});

  await expect(submitButton).toBeEnabled();
  await submitButton.click();

  await expect(page.getByText('Registration successful')).toBeVisible();
});


Why? A Playwright Locator resolves the element when it is used, so it can handle DOM replacement better than a previously captured ElementHandle.

2. Problem: Button becomes enabled after API validation
Suppose a React form validates an email address through an API before enabling the Submit button.
const emailInput = page.getByLabel('Email');

await emailInput.fill('john@example.com');

const submitButton = page.getByRole('button', {name: 'Submit',});

// Wait until React enables the button
await expect(submitButton).toBeEnabled();

await submitButton.click();


Here, toBeEnabled() retries until the button becomes enabled or the assertion times out.
If I also need to verify the backend validation request, I wait for its response explicitly:
const validationResponse = page.waitForResponse(response =>
  response.url().includes('/api/validate-email') &&
  response.request().method() === 'POST'
);

await page.getByLabel('Email').fill('john@example.com');

const response = await validationResponse;
expect(response.ok()).toBeTruthy();

await expect(page.getByRole('button', { name: 'Submit' })).toBeEnabled();

This assumes the email input triggers that request. I register the response listener before filling the field so the request is not missed.

3. Problem: Form appears before React finishes rendering
Sometimes, the page loads but the form is still being initialized.
Instead of waiting an arbitrary number of seconds, I wait for a meaningful UI condition.
await page.goto('/register');

const form = page.getByTestId('registration-form');

await expect(form).toBeVisible();
await expect(page.getByLabel('Name')).toBeEditable();

await page.getByLabel('Name').fill('John');


If the application displays a loading indicator, I can also wait for it to disappear:
await expect( page.getByTestId('loading-spinner')).toBeHidden();
await expect(page.getByLabel('Name')).toBeEditable();
This assumes the spinner is present or the application has a reliable loading-state indicator. If it is never rendered, toBeHidden() can pass immediately, so I also verify the actual form state.

4. Problem: Locator matches multiple dynamic elements
React forms may render duplicate controls during transitions or contain hidden template elements.
Instead of blindly using .first(), I identify the correct element using a stable locator.
const submitButton = page.getByTestId('registration-submit');

await expect(submitButton).toHaveCount(1);
await expect(submitButton).toBeVisible();
await expect(submitButton).toBeEnabled();
await submitButton.click();

I prefer accessible roles and labels when they uniquely identify the element; otherwise, I use stable test IDs.
5. My debugging checklist
Issue	:	How I handle it
1. Element detached from DOM	: Use a Locator instead of a stored ElementHandle
2. Button enabled asynchronously :	await expect(button).toBeEnabled()
3. API validation is pending :	Register waitForResponse() before the triggering action
4. React form is still rendering :	Wait for visible, editable, or ready UI state
5. Duplicate elements :	Use specific locators and verify uniqueness
6. CI-only failures :	Inspect traces, screenshots, and network activity

Final interview answer
“When handling fast-loading React forms, I use Playwright's locator-based approach instead of storing element handles or adding fixed waits. Locators resolve elements when actions are performed, and web-first assertions automatically retry until the expected condition is met. For API-driven validations, I wait for the relevant response and then verify the UI state. I also use stable test IDs, accessible locators, and traces to investigate intermittent failures. This makes my automation more reliable across local and CI/CD environments.”
Key point: Playwright's auto-waiting does not guarantee that every asynchronous React operation has finished. I wait for the specific business condition I need, such as a button becoming enabled, validation feedback appearing, or a successful submission message being displayed.

# Q : How would you retry a flaky action only for a specific exception?
===> In Playwright, I would implement a custom retry mechanism using try...catch when I want to retry an action only for a specific, known transient exception. I would not retry every failure because errors such as an assertion failure or invalid locator may indicate a genuine defect.
For normal UI interactions, I first rely on Playwright's built-in auto-waiting. I implement custom retries only when there is a clear reason to retry a particular transient failure.
1. Example: Retry only for a specific exception
Suppose clicking a button intermittently fails because the element becomes detached during a React re-render.
import { test, expect, Page } from '@playwright/test';

async function clickWithRetry( page: Page, selector: string, maxRetries = 3): Promise<void> {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      await page.locator(selector).click();
      return; // Success: stop retrying
    } catch (error) {
      const message = error instanceof Error ? error.message : String(error);

      const isDetachedError =  /element was detached from the DOM/i.test(message);

      // Do not retry unrelated failures
      if (!isDetachedError || attempt === maxRetries) {
        throw error;
      }

      console.log(`Detached element. Retry ${attempt + 1}/${maxRetries}`);
    }
  }
}

test('Retry click for detached element', async ({ page }) => {
  await page.goto('/checkout');

  await clickWithRetry(page, '[data-testid="submit-order"]');

  await expect(page.getByText('Order submitted successfully')).toBeVisible();
});
How it works:
- It attempts the click up to three times.
- It retries only when the error message matches the known detached-element condition.
- It immediately throws unrelated errors.
- It throws the final error when all attempts fail.
This is an illustrative pattern. Playwright's error messages can vary by version and failure type, so I would verify the actual error produced in my environment before relying on message matching.

2. Better approach for most React applications
Instead of retrying a detached-element error manually, I usually use a fresh locator for each attempt and let Playwright handle normal waiting.
const submitButton = page.getByTestId('submit-order');

await expect(submitButton).toBeVisible();
await expect(submitButton).toBeEnabled();

await submitButton.click();

await expect(page.getByText('Order submitted successfully')).toBeVisible();

A locator can resolve the current DOM element when used, and click() already waits for actionability conditions. Therefore, a custom retry loop is not normally needed for standard DOM updates.

3. Important consideration: Avoid duplicate actions
I would be especially careful when retrying operations such as:
- Submitting a payment
- Creating an order
- Deleting a record
- Sending a form that triggers a backend transaction
If the action succeeds on the server but the browser reports an error afterward, retrying may execute the operation twice. I would verify the resulting application state before attempting the action again.

4. What if I want to retry only a timeout?
I can classify the error and rethrow anything that is not the expected transient timeout. However, I would distinguish a timeout while waiting for an element from a timeout after a potentially successful business operation.
The exception classification should be based on the actual failure condition, not merely the fact that an error occurred.

Final interview answer
“In my Playwright framework, I use a custom try...catch retry wrapper when a particular action fails due to a known transient exception. I check the exception, retry only the expected failure, and immediately rethrow unrelated errors. I also limit the number of attempts and avoid blindly retrying non-idempotent operations such as payments or order creation. For normal locator and synchronization issues, I prefer Playwright's built-in auto-waiting and web-first assertions because they are simpler and more reliable.”

# Q : Explain Browser, BrowserContext and Page with a real project example.

1. Understanding the architecture
Browser
Chromium, Firefox, or WebKit instance

BrowserContext
An isolated browser session: cookies, storage, permissions

Page
A tab or popup where we interact with the application


Think of it like this:
- Browser: The browser application running the tests.
- BrowserContext: A separate user session inside that browser.
- Page: A tab within that user session.
2. Real project example: E-commerce application
Suppose I am automating an e-commerce application with two scenarios:
1. A customer logs in and places an order.
2. An administrator logs in and verifies the order.
I can create separate browser contexts for the customer and administrator, so their cookies and session storage do not mix.

softwareadvice.ie


3. Playwright TypeScript code
import { test, expect, chromium } from '@playwright/test';

test('Customer and admin have isolated sessions', async () => {
  // 1. Launch the browser
  const browser = await chromium.launch({
    headless: true
  });

  // 2. Create a context for the customer
  const customerContext = await browser.newContext();
  const customerPage = await customerContext.newPage();

  await customerPage.goto('https://example.com/login');
  await customerPage.getByLabel('Email').fill('customer@example.com');
  await customerPage.getByLabel('Password').fill('customerPass');
  await customerPage.getByRole('button', { name: 'Login' }).click();

  // 3. Create a separate context for the admin
  const adminContext = await browser.newContext();
  const adminPage = await adminContext.newPage();

  await adminPage.goto('https://example.com/admin/login');
  await adminPage.getByLabel('Email').fill('admin@example.com');
  await adminPage.getByLabel('Password').fill('adminPass');
  await adminPage.getByRole('button', { name: 'Login' }).click();

  // Validate each session independently
  await expect(customerPage.getByText('My Orders')).toBeVisible();

  await expect(adminPage.getByText('Order Management')).toBeVisible();

  // 4. Clean up resources
  await browser.close();
});


Note: This is illustrative code; the URLs, credentials, labels, and assertions must match the actual application. In a real project, I would store credentials securely and use fixtures for resource management.
4. Browser vs BrowserContext vs Page
Feature	      |	Browser	                      |	BrowserContext	      |	Page
1. Purpose    |	Launch and manage browser     |	Isolate a session     |	Interact with a tab
2. Example    |	Chromium		      |	Customer session      |	Customer dashboard tab
3. Cookies    | Shared through its contexts,  |	Separate from other   |	Uses its context's storage
/storage      | not directly a single session |    contexts           |

4. Can create |	Contexts		      |	    Pages	      |	Popups or additional tabs via browser events
5. Typical use|	Test execution setup	      | User/session isolation|	Locators, clicks, assertions

Important interview points
- One Browser can have multiple BrowserContexts.
- One BrowserContext can have multiple Pages, such as tabs and popups.
- Pages in the same context share that context's session state, while separate contexts provide isolation.
- A new context is lightweight compared with launching a separate browser process.
- Playwright Test normally manages the browser and creates an isolated context and page for each test, so you often use the built-in page fixture rather than manually launching a browser.
5. Example from a framework
In a real Playwright framework, I typically use the built-in fixtures:
import { test, expect } from '@playwright/test';

test('Verify product page', async ({ page }) => {
  await page.goto('https://example.com/products');

  await expect(page.getByRole('heading', { name: 'Products' })).toBeVisible();
});

Playwright Test provides the page fixture, backed by a browser context and browser managed by the test runner. This keeps the test concise and helps with isolation and cleanup.
Interview summary: “Browser represents the browser instance, BrowserContext represents an isolated user session, and Page represents an individual tab. In my e-commerce automation project, I can use separate contexts for customer and admin sessions and separate pages for tabs or popups. This helps me manage sessions independently, prevent cookie conflicts, and build reliable parallel tests.”

# Q : How do you validate an API response and use its data in UI automation?
==> In Playwright with TypeScript, I validate an API response using status codes, response headers, response body, and business rules. Then I reuse the API response data in UI automation to verify that the frontend displays the correct information.
In a real project, I prefer this approach because it reduces hardcoded test data and helps validate both backend and frontend behavior in one scenario.
1. Real project example: E-commerce application
Suppose an API returns product details, and I need to verify that the same product name, price, and ID appear on the UI.

Step 1: API request
GET /api/products/101

Step 2: Validate response
Status 200, content type, product ID, name, and price

Step 3: Validate UI
Compare product details displayed on the page with the API data

2. Complete Playwright TypeScript example
import { test, expect } from '@playwright/test';

test('Validate product API data against UI', async ({request, page }) => {
  // 1. Call the API
  const response = await request.get('https://example.com/api/products/101' );

  // 2. Validate the response status and headers
  expect(response.status()).toBe(200);
  expect(response.headers()['content-type']).toContain('application/json');

  // 3. Extract response data
  const product = await response.json();

  // 4. Validate API business data
  expect(product.id).toBe(101);
  expect(product.name).toBeTruthy();
  expect(product.price).toBeGreaterThan(0);

  // 5. Open the corresponding UI page
  await page.goto('https://example.com/products/101');

  // 6. Compare UI data with API response
  await expect(page.getByTestId('product-name')).toHaveText(product.name);

  await expect( page.getByTestId('product-price')).toHaveText(`$${product.price.toFixed(2)}`);
});

Note: The endpoint, response fields, test IDs, currency format, and UI structure are illustrative. Adapt them to the actual application. The example assumes price is a number and the UI displays two decimal places.
3. How I validate the API response
Validation          :	Example
1. HTTP status	    :	expect(response.status()).toBe(200)
2. Response headers :	Verify JSON content type
3. Response schema  :	Check required fields and their data types
4. Business rules   :	Price must be greater than zero
5. Data consistency :	Product ID in the response matches the requested ID
6. UI consistency   :	Product name and price match the API response

For larger projects, I use reusable API clients, TypeScript interfaces, and schema validation where appropriate. I also validate negative scenarios, such as 401 Unauthorized, 404 Not Found, and invalid request payloads.
4. What if the UI itself triggers the API?
Sometimes, instead of making a separate API request, I need to validate the API response generated by a UI action. I listen for the response before clicking the button.
const responsePromise = page.waitForResponse(response =>
  response.url().includes('/api/products') &&
  response.request().method() === 'GET' &&
  response.status() === 200
);

await page.getByRole('button', { name: 'Load Products'}).click();

const response = await responsePromise;
const products = await response.json();

expect(products.length).toBeGreaterThan(0);
Registering waitForResponse() before the click prevents missing a fast response. In production tests, I would also match the expected URL more precisely and validate the response body.

5. Why use API data in UI automation?
- Less hardcoding: Expected values come from the API response.
- Better coverage: Backend data and frontend rendering are checked together.
- Faster setup: API calls can create or retrieve test data without navigating through every setup screen.
- Easier debugging: If the API is correct but the UI is wrong, the issue is easier to isolate.

One important distinction: when I compare the UI against the same API response, I verify that the frontend renders backend data correctly. For stronger end-to-end validation, I also compare against an independent expected value or a known test-data fixture, because the API and UI could otherwise share the same incorrect data.

Interview-ready answer
“With my Playwright and TypeScript framework, I use the API request fixture or page.waitForResponse() to capture API responses. I validate the status code, headers, response body, data types, and business rules. Then I extract the response data and compare it with the values displayed in the UI using Playwright assertions. I also use API calls for test-data setup to reduce execution time and avoid unnecessary UI navigation. This approach gives me better backend and frontend coverage and makes failures easier to debug.”

# Q : How do you intercept an API response and mock the data?
==> In Playwright with TypeScript, I use page.route() to intercept API requests and mock responses. This allows me to test different backend scenarios without depending on the actual backend service.
For example, in an e-commerce project, I can mock product details, empty product lists, server errors, or unavailable services to verify how the UI behaves.
1. How API interception works
1. UI sends an API request
GET /api/products

2. Playwright intercepts the request
page.route()

Mock response
Return controlled JSON

Real backend
Use route.continue()

3. Validate the UI
Verify the expected product data or error message

2. Example 1: Intercept API and mock product data
Suppose the real API returns product data, but I want to test the UI with controlled mock data.
import { test, expect } from '@playwright/test';

test('Mock product API response', async ({ page }) => {
  // Intercept the API request
  await page.route('**/api/products', async route => {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([
        {
          id: 101,
          name: 'Laptop',
          price: 50000
        },
        {
          id: 102,
          name: 'Mobile',
          price: 20000
        }
      ])
    });
  });

  // Open the application after registering the mock
  await page.goto('https://example.com/products');

  // Validate mocked data on the UI
  await expect(page.getByText('Laptop')).toBeVisible();
  await expect(page.getByText('Mobile')).toBeVisible();
  await expect(page.getByText('50000')).toBeVisible();
});
How it works:
- page.route() registers a handler for matching requests.
- route.fulfill() returns the mocked response instead of sending the request to the backend.
- The frontend processes the mock as an API response.
- Playwright assertions verify the rendered UI.
The URL and response structure must match the actual application's API contract for this example to work.

3. Example 2: Mock a 500 Internal Server Error
In real projects, I also test how the application behaves when the backend fails.

test('Display error when product API fails', async ({ page }) => {
  await page.route('**/api/products', async route => {
    await route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({
        message: 'Internal Server Error'
      })
    });
  });

  await page.goto('https://example.com/products');

  await expect(page.getByText('Unable to load products')).toBeVisible();
});

This verifies the frontend's error handling without requiring the actual server to fail.
Other useful mock scenarios include:
- 200 — successful response.
- 401 — unauthorized request.
- 403 — forbidden request.
- 404 — resource not found.
- 500 — internal server error.
- Empty arrays — no products available.
- Delayed responses — loading indicators and timeout behavior.
The error message in the assertion must match what the application actually displays.

4. Example 3: Intercept a request but modify the real response
Sometimes I want to call the actual backend and change only part of its response. For this, I use route.fetch() followed by route.fulfill().
test('Modify real API response', async ({ page }) => {
  await page.route('**/api/products', async route => {
    // Fetch the real API response
    const response = await route.fetch();

    // Read the actual response body
    const products = await response.json();

    // Modify a field for testing
    if (products.length > 0) {
      products[0].name = 'Mocked Laptop';
    }

    // Return the modified response to the UI
    await route.fulfill({
      response,
      json: products
    });
  });

  await page.goto('https://example.com/products');

  await expect(page.getByText('Mocked Laptop')).toBeVisible();
});


This technique is useful when I want to preserve most real backend data but override a specific field. The real API must be reachable, and its response must have the expected structure.

5. Difference between fulfill(), continue(), and fetch()
Method	Purpose
route.fulfill()	 :      Return a mocked response directly
route.continue() :	Send the request to the actual server without further route handling
route.fetch()	 :	Send the request to the actual server and retrieve the response so it can be inspected or modified
Interview tip	 : 	Register the route before navigating to the page or triggering the action. Otherwise, a fast API request may already have completed before interception is configured.
Interview-ready answer
“With my Playwright and TypeScript framework, I use page.route() to intercept API requests and route.fulfill() to return mocked responses. This helps me test positive and negative scenarios independently of backend availability. For example, I can mock product data, return a 500 error, or simulate an empty response and validate the corresponding UI behavior. If I need to modify a real backend response, I use route.fetch() and then route.fulfill(). This improves test reliability and gives me control over scenarios that are difficult to reproduce with a real backend.”

# Q : Tell us about a flaky test you fixed. What was the real cause, and how did you find it?
===> For a 3.6-year Automation Engineer interview, I would answer this using a real-world scenario, explaining the symptom, root cause, investigation, fix, and result. A strong example is a flaky Playwright test caused by a React page updating asynchronously after an API response.

Interview-ready answer (STAR method)

Situation:
“In one of my automation projects, I had a Playwright test written in TypeScript that validated the product list on an e-commerce application. The test passed locally but failed intermittently in Jenkins. Sometimes the product list was displayed correctly, and sometimes the test failed because the expected product was not found.”

Task:
“My responsibility was to identify the actual root cause and make the test stable without simply increasing timeouts or adding retries.”
Action — How I investigated and fixed it:
“First, I checked the Jenkins execution logs, screenshots, and Playwright traces. I noticed that the test was trying to locate the product immediately after navigating to the page, while the frontend was still waiting for the product API response and rendering the list.
The real cause was a race condition between the asynchronous API response, React component rendering, and the test assertion. It was not a locator issue or a backend defect.”

Initially, the test looked something like this:
await page.goto('/products');

const product = page.getByText('Laptop');
await product.click();


The test assumed the product would be available immediately after navigation.
I fixed it by waiting for the expected UI state using Playwright's web-first assertions:
import { test, expect } from '@playwright/test';

test('Select a product', async ({ page }) => {
  await page.goto('/products');

  const product = page.getByText('Laptop', {exact: true  });

  // Wait until the product is actually rendered
  await expect(product).toBeVisible();

  await product.click();
});


If the API response itself was important to the scenario, I would register a response listener before navigating or triggering the action:
const responsePromise = page.waitForResponse(response =>
  response.url().includes('/api/products') &&
  response.request().method() === 'GET' &&
  response.status() === 200
);

await page.goto('/products');

await responsePromise;

await expect(page.getByText('Laptop', { exact: true })).toBeVisible();


I would use the response wait only when the test needs to verify that specific API call. The UI assertion remains important because an API response alone does not guarantee that the frontend rendered the expected data.

Result:
“After removing the timing assumption and synchronizing the test with the actual application state, the test became more reliable in CI. I also reviewed similar tests for hardcoded sleeps, unstable selectors, and shared test data to prevent the same issue elsewhere. I used retries only to help diagnose intermittent failures, not as the permanent fix.”

Follow-up questions an interviewer may ask

1. Why didn't you use waitForTimeout(5000)?
Because a fixed sleep waits for the same duration regardless of application state. It can slow down execution and still fail when the application takes longer. I prefer condition-based waits and web-first assertions.

2. How did you prove the root cause?
I correlated the failed assertion with the Playwright trace and API timing. The trace showed the test reaching the assertion before the product appeared in the DOM. After adding the appropriate synchronization, I reran the test repeatedly and in CI to verify stability.

3. What if the test still fails intermittently?
I would investigate other possible causes, such as shared test data, parallel execution conflicts, unstable selectors, network failures, or backend inconsistency. I would use traces, screenshots, logs, and response details to isolate the issue instead of automatically increasing retries.

Short answer for a live interview
	I fixed a flaky Playwright test that passed locally but failed intermittently in Jenkins. I investigated the execution logs and Playwright traces and found that the test was interacting with a product before the asynchronous API response had been rendered by React. I replaced the timing assumption with Playwright web-first assertions and added an API response wait where needed. I then reran the test locally and in CI to verify the fix. The key lesson was to identify and fix the actual race condition instead of hiding it with hardcoded sleeps or retries.”
Interview tip: Use this as a sample only if it matches your experience. Be ready to explain the actual trace, error message, and verification steps from a flaky test you personally investigated

# Q : How would you automate nested iframes?
==> In Playwright with TypeScript, I automate nested iframes using frameLocator(). It allows me to locate an element inside an iframe and then move into another iframe nested inside it, without manually switching browser context.
For example, in a payment application, the checkout page may contain a payment iframe, which contains another iframe for card details.
1. Nested iframe structure
Main page
checkout.example.com
Iframe 1 — Payment
payment-frame
Iframe 2 — Card details
card-frame
Card number input

2. Playwright TypeScript example
Suppose the card number input is inside a nested iframe.
import { test, expect } from '@playwright/test';

test('Handle nested payment iframes', async ({ page }) => {
  await page.goto('https://example.com/checkout');

  // Locate the outer iframe
  const paymentFrame = page.frameLocator('iframe[title="Payment frame"]');

  // Locate the nested iframe inside the outer iframe
  const cardFrame = paymentFrame.frameLocator('iframe[title="Card details"]');

  // Interact with elements inside the nested iframe
  await cardFrame.getByLabel('Card number').fill('4111111111111111');

  await cardFrame.getByLabel('Expiry date').fill('12/30');

  await cardFrame.getByLabel('CVV').fill('123');

  // Validate the expected state
  await expect(cardFrame.getByLabel('Card number')).toHaveValue('4111111111111111');
});
The iframe selectors, labels, and payment data above are illustrative; they must match the actual page. Use only authorized test payment data in a sandbox environment.

3. What if the iframe has no title or stable ID?
I inspect the DOM and identify a reliable selector, such as a stable name, data-testid, or another unique attribute.
const outerFrame = page.frameLocator('iframe[name="payment-container"]');

const innerFrame = outerFrame.frameLocator('iframe[name="card-entry"]');

await innerFrame.locator('input[name="cardNumber"]').fill('4111111111111111');

If multiple iframes match the selector, I narrow the locator so it identifies the intended frame rather than relying on .first() or .nth() without a clear reason.

4. What if the iframe loads slowly?
I use Playwright's auto-waiting and web-first assertions rather than fixed sleeps.
const cardFrame = page
  .frameLocator('iframe[title="Payment frame"]')
  .frameLocator('iframe[title="Card details"]');

const cardNumber = cardFrame.getByLabel('Card number');

await expect(cardNumber).toBeVisible();
await cardNumber.fill('4111111111111111');


If the iframe depends on an asynchronous network request, I investigate the relevant response or application state as well.
5. Common interview follow-up questions

Q: Do you need to switch into each iframe manually?
	No. frameLocator() lets me chain through nested iframes directly.

Q: Can Playwright handle cross-origin iframes?
	Yes. Playwright can interact with elements inside cross-origin iframes when the frame is accessible to the browser automation session and the selectors are valid. Same-origin JavaScript restrictions do not prevent Playwright's normal frame-locator workflow.

Q: What if the iframe is dynamically attached or detached?
	I use frameLocator() and resilient locators, which resolve elements as needed. If the frame repeatedly detaches, I inspect the trace and application lifecycle to identify the cause instead of adding arbitrary delays.

Q: How does Selenium Java differ?
	Selenium typically requires explicit frame switching with driver.switchTo().frame(...), repeating the process for each nested frame, then returning with parentFrame() or defaultContent().

Interview-ready answer
“In Playwright, I handle nested iframes using chained frameLocator() calls. First, I locate the outer iframe, then locate the inner iframe within it, and finally interact with the required element using normal Playwright locators. I use stable iframe attributes, auto-waiting, and assertions to handle dynamic loading. Unlike Selenium, I don't need to manually switch into and out of each frame. This makes the automation code cleaner and easier to maintain.”

# Q : How do you handle file downloads and verify content?
==> In Playwright with TypeScript, I handle file downloads using page.waitForEvent('download'). I register the download listener before clicking the download button, save the file, and verify its existence, file name, and actual content.
In my automation framework, I commonly apply this to reports, invoices, CSV exports, and PDF documents.

1. Real project example: Download and verify an invoice
Suppose an e-commerce application allows a customer to download an order invoice as a PDF. I need to verify that the download succeeds and that the invoice contains the correct order details.

Step 1: Download the file
import { test, expect } from '@playwright/test';
import fs from 'node:fs/promises';
import path from 'node:path';

test('Download and verify invoice', async ({ page }) => {
  await page.goto('https://example.com/orders');

  // Register listener before clicking Download
  const downloadPromise = page.waitForEvent('download');

  await page.getByRole('button', {name: 'Download Invoice'}).click();

  const download = await downloadPromise;

  // Verify suggested file name
  expect(download.suggestedFilename()).toMatch(/invoice.*\.pdf$/i);

  // Save the downloaded file
  const filePath = path.join(test.info().outputDir, download.suggestedFilename());

  await download.saveAs(filePath);

  // Verify the file exists
  const fileStat = await fs.stat(filePath);
  expect(fileStat.size).toBeGreaterThan(0);

  // Verify the download completed without an error
  expect(await download.failure()).toBeNull();
});


This verifies that the file was downloaded and is non-empty. It does not yet prove that the PDF contains the correct invoice data.
2. How do you verify the actual file content?
The validation depends on the file format.

1. CSV / Excel
Parse rows and columns, then validate expected headers, order IDs, prices, and record counts.
2. PDF
Extract text using a PDF parsing library and assert the invoice number, customer name, and total amount.
3. JSON / TXT
Read the file and parse JSON or compare the expected text and values.

Example: Verify a downloaded CSV
import { test, expect } from '@playwright/test';
import fs from 'node:fs/promises';
import path from 'node:path';

test('Download and verify CSV export', async ({ page }) => {
  await page.goto('https://example.com/orders');

  const downloadPromise = page.waitForEvent('download');

  await page.getByRole('button', {name: 'Export CSV'}).click();

  const download = await downloadPromise;

  const filePath = path.join(test.info().outputDir, download.suggestedFilename());

  await download.saveAs(filePath);

  const csv = await fs.readFile(filePath, 'utf8');

  // Validate headers and business data
  expect(csv).toContain('Order ID');
  expect(csv).toContain('Customer');
  expect(csv).toContain('ORD-1001');
  expect(csv).toContain('Total');
});
For production tests, I would use a CSV parser rather than simple includes() checks when fields can contain commas, quotes, or line breaks. I would also assert the exact expected values rather than merely checking that a few strings exist.

3. Important points I mention in interviews
- Register waitForEvent('download') before clicking the download button to avoid missing the event.
- Use test.info().outputDir to keep downloaded files organized per test.
- Check download errors and ensure the file is non-empty.
- Verify the actual content, not only the filename.
- For PDFs, use a suitable PDF text-extraction library; for Excel, use a spreadsheet parser.
- Clean up temporary files when necessary.
- Playwright's acceptDownloads option is enabled by default in standard Playwright Test browser contexts, but check configuration if downloads are not being captured.

Interview-ready answer
“In my Playwright TypeScript framework, I handle downloads using page.waitForEvent('download'), registering the listener before clicking the download button. I save the file in the test output directory and validate the filename, download status, and file size. Then I verify the actual content according to the format—for example, parsing CSV records or extracting text from a PDF to check invoice numbers, order IDs, and totals. This ensures the download is not just successful but also contains the correct business data.

# Q : A test passes individually but fails in parallel. What could cause it?
==> In Playwright with TypeScript, if a test passes individually but fails when executed in parallel, I suspect a test isolation issue, shared test data, race condition, or resource contention.
In my automation framework, I investigate the root cause rather than disabling parallel execution or adding retries immediately.
1. Common causes and solutions
Possible cause			| 	Real-world example 					|		How I fix it
1. Shared test data		| Two tests update the same user account			|	Create unique test data for each test
2. Shared accounts		| Two tests change the same user's password or settings		|	Use separate test accounts or isolated data
3. Race conditions		| One test deletes a record while another verifies it		| 	Avoid dependencies and coordinate setup/cleanup
4. Shared files			| Multiple tests overwrite the same downloaded  		|	Use a unique file path per test
5.Global state			| Tests modify shared variables or singleton objects		|	Keep state test-scoped
6. Backend contention		| Too many parallel requests overload the server		| 	Tune worker count and investigate server capacity
7. Environment conflicts	| Tests share the same cart, database, or tenant		|	Isolate data and reset state reliably
8. Timing assumptions		| A test expects an element before an asynchronous update finishes|	Use Playwright auto-waiting and web-first assertions

2. Real project example: E-commerce application
Suppose two tests run in parallel:
- Test A adds a laptop to a shopping cart.
- Test B verifies that the cart is empty.

If both tests use the same account, Test A can modify the cart while Test B is checking it. Both tests may pass individually but fail when executed together.

Root cause: Shared mutable test data.
Fix: Give each test its own user or cart and create the required data independently.

import { test, expect } from '@playwright/test';

test('Customer A sees their own cart', async ({ page }) => {
  // Each test receives its own test data and session.
  const user = await createTestUser();

  await login(page, user);
  await page.goto('/cart');

  await expect( page.getByText('Your cart is empty')).toBeVisible();
});

test('Customer B can add a product', async ({ page }) => {
  const user = await createTestUser();

  await login(page, user);
  await page.goto('/products');

  await page.getByRole('button', {  name: 'Add to cart'  }).click();

  await expect( page.getByTestId('cart-count')).toHaveText('1');
});


Here, createTestUser() and login() represent project-specific helper functions. The important part is that each test receives independent user data, and the backend must enforce that isolation.
3. How I investigate the failure

Step 1: Reproduce
	Run the test individually, then with parallel workers. Compare the failure patterns.

Step 2: Inspect evidence
	Check Playwright traces, screenshots, logs, API responses, and backend records.

Step 3: Check isolation
	Look for shared accounts, duplicate records, static variables, shared files, and test dependencies.

Step 4: Verify the fix
	Run the affected tests repeatedly in parallel and confirm that the root cause is resolved.

4. How do you configure parallel execution?
Playwright Test supports worker configuration in playwright.config.ts:
import { defineConfig } from '@playwright/test';

export default defineConfig({
  fullyParallel: true,
  workers: process.env.CI ? 4 : undefined,

  use: {
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure'
  }
});

This is an example configuration, not a universal worker recommendation. I would tune the worker count according to CI machine resources, application capacity, and observed contention.
Also, Playwright Test normally gives each test an isolated browser context. That does not automatically isolate backend accounts, database records, external services, or files.

Interview-ready answer
“If a test passes individually but fails in parallel, I first suspect shared test data, race conditions, or resource contention. For example, two e-commerce tests might modify the same user's cart, causing inconsistent results. I investigate using Playwright traces, screenshots, logs, and API responses. Then I isolate test data, avoid dependencies between tests, ensure proper cleanup, and tune the worker count if the environment is overloaded. Finally, I rerun the tests repeatedly in parallel to confirm the fix. I don't treat retries or disabling parallel execution as the permanent solution unless there is a justified infrastructure limitation.”

# Q : How do you capture screenshots only when a test fails?
==> In Playwright with TypeScript, I configure screenshot: 'only-on-failure' in playwright.config.ts. This automatically captures a screenshot when a test fails, without requiring screenshot code in every test case.

1. Recommended approach: Playwright configuration
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    screenshot: 'only-on-failure',
    trace: 'retain-on-failure',
    video: 'retain-on-failure'
  },

  reporter: [
    ['html', { open: 'never' }]
  ]
});


How it works:
- screenshot: 'only-on-failure' — captures screenshots for failed tests.
- trace: 'retain-on-failure' — retains traces for debugging failed tests.
- video: 'retain-on-failure' — retains video recordings for failed tests.
- reporter — generates an HTML report containing test results and available attachments.
The HTML report can be opened after execution using:
npx playwright show-report

2. Alternative: Capture screenshots manually
If I need custom screenshot naming or want to control exactly what gets captured, I use a fixture or afterEach hook.
import { test, expect } from '@playwright/test';

test.afterEach(async ({ page }, testInfo) => {
  if (testInfo.status !== testInfo.expectedStatus) {
    await page.screenshot({
      path: testInfo.outputPath('failure.png'),
      fullPage: true
    });
  }
});

test('Verify login', async ({ page }) => {
  await page.goto('https://example.com/login');

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});
The hook captures a screenshot when the actual result differs from the expected result, including unexpected passes of tests marked as expected to fail. testInfo.outputPath() creates a test-specific output path, avoiding filename conflicts during parallel execution.
Important: For ordinary projects, I prefer the built-in configuration because it is simpler and automatically integrates with Playwright's test reporting.

Interview-ready answer
“In my Playwright framework, I configure screenshot: 'only-on-failure' in playwright.config.ts. This automatically captures screenshots for failed test cases. I also enable trace: 'retain-on-failure' to inspect actions, locators, and network activity. If I need custom screenshot naming or conditional capture logic, I use an afterEach hook and testInfo.outputPath() to save screenshots without conflicts during parallel execution.”

# Q : A locator works in Chrome but fails in Firefox. How would you debug it?
===> For an Automation Engineer with 3.6 years of experience, I would answer this using a systematic debugging approach in Playwright with TypeScript, rather than assuming the issue is a browser bug.

Interview-ready answer
“If a locator works in Chrome but fails in Firefox, I first determine whether the issue is caused by the locator, browser-specific rendering, timing, or an actual application compatibility problem.
I would follow these steps:
1. Reproduce the failure: Run the same test in both browsers and confirm that it consistently fails only in Firefox.
2. Check the error and trace: Review the Playwright error message, screenshot, trace viewer, DOM snapshot, and console logs to understand whether the element is missing, hidden, covered, or not actionable.
3. Validate the locator: Check whether the locator depends on a browser-specific CSS selector, unstable class, XPath, or exact text. Prefer stable attributes such as data-testid, accessible roles, and labels.
4. Check timing and rendering: Firefox may render the page or complete an animation differently. Use Playwright's auto-waiting and web-first assertions instead of fixed sleeps.
5. Check visibility and interaction: Verify that the element is visible, enabled, and not blocked by an overlay. Check whether the application behaves differently in Firefox.
6. Compare browser configurations: Check browser versions, viewport size, permissions, authentication state, and network/API failures.
7. Fix and verify: Make the locator or synchronization reliable, then rerun the test in Chromium, Firefox, and WebKit to ensure the fix is not browser-specific.”

Example: Debugging with Playwright TypeScript
Suppose a Login button works in Chrome but fails in Firefox.
Potentially fragile locator
// May depend on an unstable CSS class
const loginButton = page.locator(".btn-primary.login-v2");
await loginButton.click();


I would inspect the DOM and replace it with a stable, user-facing locator if possible.
Preferred approach
import { test, expect } from "@playwright/test";

test("login works across browsers", async ({ page }) => {
  await page.goto("https://example.com/login");

  const loginButton = page.getByRole("button", { name: "Login", exact: true });

  await expect(loginButton).toBeVisible();
  await expect(loginButton).toBeEnabled();

  await loginButton.click();

  await expect(page).toHaveURL(/dashboard/);
});

This helps eliminate brittle selectors and verifies the button's state before interaction. Playwright automatically waits for the click action's required actionability conditions.
Important: If this still fails in Firefox, I would not immediately add a timeout or force the click. I would inspect the trace and DOM to identify the actual cause.

How I would investigate the failure
Symptom						|	What I would check
1. Locator resolves to zero elements		|	DOM differences, selector validity, rendering, iframe or shadow DOM
2. Strict mode violation			|	Multiple matching elements; scope the locator to the correct container
3. Element is not visible			|	CSS differences, responsive layout, hidden elements
4. Click times out				|	Overlay, animation, disabled state, or element movement
5. Click succeeds but test fails		|	Application behavior, API responses, navigation timing
6. Test passes alone but fails in a suite	|	Shared data, test isolation, parallel execution, or state leakage

Run the test in Firefox with debugging enabled
npx playwright test tests/login.spec.ts --project=firefox --headed


To open the Playwright Inspector:
npx playwright test tests/login.spec.ts --project=firefox --debug


For trace collection, configure:
// playwright.config.ts
use: {
  trace: "retain-on-failure",
  screenshot: "only-on-failure"
}

Then inspect the trace to see the failed action, DOM snapshot, timing, and network activity.
Strong closing statement for the interview
“I would first isolate whether the failure is due to a brittle locator, timing, browser rendering, or an application defect. I would use Playwright traces and browser-specific debugging to find the root cause, fix the underlying issue, and rerun the test across all supported browsers. I would avoid waitForTimeout() and force: true unless there is a justified reason, because they can hide the real problem.”

# Q : Your suite takes 2 hours. How would you reduce it to 30 minutes?
==> For an Automation Engineer with 3.6 years of experience, I would approach this as a test execution optimization problem. My goal would be to reduce execution time from 2 hours to 30 minutes without compromising test coverage, reliability, or result accuracy.
1. Interview-ready answer
“If my automation suite takes 2 hours, I would first analyze where the time is being spent rather than immediately increasing parallel workers.
I would take the following steps:
1. Analyze execution time: Identify slow test cases, repeated setup, unnecessary waits, and environment bottlenecks using Playwright reports and traces.
2. Enable parallel execution: Split independent tests across multiple workers and CI agents, ensuring tests do not share mutable data or state.
3. Reduce unnecessary UI operations: Use API requests to create test data and establish preconditions instead of navigating through multiple UI screens.
4. Remove fixed waits: Replace waitForTimeout() with web-first assertions, appropriate locator waits, and waits for specific network responses where necessary.
5. Optimize test coverage: Run smoke tests on every pull request, execute the full regression suite on a schedule or before releases, and avoid duplicate scenarios without reducing required coverage.
6. Improve test isolation: Use independent test data and accounts so tests can safely run in parallel.
7. Optimize CI infrastructure: Check CPU, memory, browser startup overhead, and test environment response times. Add workers or distributed execution only when resources support them.
8. Measure the results: Compare execution time, failure rate, retries, and coverage after each optimization.
I would aim for 30 minutes through measured improvements, then validate that the faster suite remains stable across repeated CI runs.”
2. How I would implement it in Playwright + TypeScript
Step 1: Enable parallel execution
In playwright.config.ts:
import { defineConfig } from "@playwright/test";

export default defineConfig({
  fullyParallel: true,

  workers: process.env.CI ? 4 : undefined,

  retries: process.env.CI ? 1 : 0,

  reporter: [
    ["list"],
    ["html", { open: "never" }]
  ],

  use: {
    trace: "retain-on-failure",
    screenshot: "only-on-failure"
  }
});


Here, workers: 4 is an illustrative starting point, not a guaranteed optimal value. I would benchmark different worker counts against the available CI resources and application capacity.
Step 2: Replace fixed waits
Avoid this
await page.waitForTimeout(5000);
await expect(page.getByText("Order placed")).toBeVisible();


Prefer this
await expect(
  page.getByText("Order placed")
).toBeVisible({ timeout: 10000 });


The assertion waits for the expected state instead of always consuming five seconds. The timeout is a maximum, not a delay that always runs.
Step 3: Use API setup instead of repetitive UI setup
Suppose every checkout test creates a user and adds products through the UI. That setup could take several minutes across many tests.
Instead, create the user or seed the required data through an API, then use the UI only to test the checkout behavior itself.
import { test, expect } from "@playwright/test";

test("customer can view a seeded order", async ({
  page,
  request
}) => {
  const response = await request.post(
    "/api/test/orders",
    {
      data: {
        productId: "SKU-101",
        quantity: 1
      }
    }
  );

  expect(response.ok()).toBeTruthy();

  const order = await response.json();

  await page.goto(`/orders/${order.id}`);

  await expect(
    page.getByTestId("order-status")
  ).toHaveText("Confirmed");
});

This is illustrative: the test endpoint, authentication, and response structure must match the actual application. API-created data should not bypass the behavior the test is supposed to validate.
Step 4: Separate fast feedback from full regression
Test group		|	When to run		|	Purpose
1. Smoke tests		| Every pull request		|	Validate critical application flows
2.Focused regression	| After relevant changes	|	Test impacted features
3. Full regression	| Scheduled or before release	|	Broader coverage across features
4. Cross-browser suite	| CI or scheduled runs		|	Validate browser compatibility

This improves feedback time without treating skipped regression tests as completed tests.

4. How I would prioritize the work

1. First: Measure
	Find the slowest tests, expensive fixtures, repeated login/setup, and fixed waits.
2. Second: Parallelize safely
	Use independent data, isolate accounts, remove shared-file conflicts, and tune workers.
3. Third: Remove waste
	Use API-based setup, reusable authenticated state where appropriate, and event-based synchronization.
4. Finally: Validate quality
	Repeat runs and compare failures, flaky-test rates, coverage, and total execution time.

5. Follow-up question interviewers may ask

Q: What if you enable parallel execution but tests start failing?
“I would investigate shared test data, shared user accounts, race conditions, environment capacity, and order-dependent setup. I would make tests independent and control access to genuinely shared resources. I would not simply reduce workers or add retries to hide the failures.”
Strong closing line: “My strategy is to reduce wasted execution time, parallelize independent tests, optimize setup, and measure the results—while preserving coverage and reliability. I would target 30 minutes based on actual profiling rather than promise a fourfold speedup from parallelization alone.”

import { type Page, type Locator } from "@playwright/test";

export class LoginPage {
  private readonly username: Locator;
  private readonly password: Locator;
  private readonly loginButton: Locator;
  private readonly errorMessage: Locator;

  constructor(private readonly page: Page) {
    this.username = page.getByLabel("Username");
    this.password = page.getByLabel("Password");
    this.loginButton = page.getByRole("button", {
      name: "Login"
    });
    this.errorMessage = page.getByTestId("login-error");
  }

  async open(): Promise<void> {
    await this.page.goto("/login");
  }

  async login(username: string, password: string): Promise<void> {
    await this.username.fill(username);
    await this.password.fill(password);
    await this.loginButton.click();
  }

  async getErrorMessage(): Promise<string | null> {
    return this.errorMessage.textContent();
  }
}

Why? Locators and page actions stay in one place, making maintenance easier when the UI changes. I would keep business assertions primarily in test files rather than making page objects responsible for every test expectation.

# Q : Explanation: opening and capturing a new tab
typescript
const [newTab] = await Promise.all([
    context.waitForEvent('page'),
    sauceDemoLink.click({ modifiers: ['Control'] })
]);

This statement clicks a link so that it opens in a new tab, and gets a handle to that new tab so you can control it. The blank lines in your version are just formatting and change nothing.

The problem it solves

When you Ctrl+click a link, the browser opens a new tab. Playwright does not return that tab from click(). It only announces it as an event on the browser context. Your code has to be listening for that event before the click happens.

You can think of it as registering a listener before firing the action that triggers it.

Piece by piece
context.waitForEvent('page')
context is the browser session that holds all the tabs.
waitForEvent('page') means “notify me when a new page (tab) is created in this context”.
It returns a Promise that stays pending until a tab opens. It then resolves with the new tab’s Page object.
It starts listening immediately when the line runs. It does not block.
sauceDemoLink.click({ modifiers: ['Control'] })
Clicks the link while holding the Ctrl key, which makes the browser open it in a new tab.
modifiers accepts 'Control', 'Shift', 'Alt' and 'Meta'.
On macOS, Cmd+click opens a new tab, so you would use 'Meta' there.
It also returns a Promise. That Promise resolves with nothing (void) once the click has finished.
Promise.all([ ... ])
Takes an array of Promises and runs them concurrently.
Returns one Promise that resolves when all of them have resolved.
The result is an array of the results in the same order as the input: [ <result of waitForEvent>, <result of click> ], which here is [ Page, undefined ].
If any Promise rejects (for example, the click fails), Promise.all rejects immediately.
Java analogy: it is similar to CompletableFuture.allOf(...), except it also hands back all the values.
const [newTab] = ...
This is array destructuring. It takes the first element of the result array and names it newTab.
The first element is the Page from waitForEvent. The undefined from the click is ignored.
It is shorthand for const result = await Promise.all([...]); const newTab = result[0];.
await

Pauses the test until Promise.all resolves, meaning the tab exists and the click is done.

Order of execution
JavaScript evaluates the array items from top to bottom.
context.waitForEvent('page') runs first and the listener is now active.
click(...) runs second and the click happens.
The browser opens the new tab and the page event fires.
The waitForEvent Promise resolves with the new Page, the click Promise resolves, and Promise.all resolves.

Because the listener is registered before the click, the event cannot be missed.

Why not write it sequentially?

Wrong version 1: click first, then listen

typescript
await sauceDemoLink.click({ modifiers: ['Control'] });
const newTab = await context.waitForEvent('page');

This is a race condition. If the tab opens before waitForEvent starts listening, the event is already gone. The test then waits until it times out. It may pass on a fast machine and fail on a slow one, which is the worst kind of flaky test.

Wrong version 2: listen first with await, then click

typescript
const newTab = await context.waitForEvent('page'); // waits forever
await sauceDemoLink.click({ modifiers: ['Control'] }); // never reached

The await pauses the test until a tab opens. But the click that opens the tab is on the next line, so it never runs. The test times out.

Equivalent version without Promise.all
typescript
const newTabPromise = context.waitForEvent('page'); // no await: listener starts, Promise saved
await sauceDemoLink.click({ modifiers: ['Control'] });
const newTab = await newTabPromise;                 // now wait for the result

This does the same thing and is the pattern shown in Playwright’s docs. The key is that you do not await the listener before the click. Many people find it easier to read than Promise.all.

Why context and not page?
context.waitForEvent('page') catches any new tab opened anywhere in that context. This is the safest choice for a Ctrl+click.
page.waitForEvent('popup') only catches popups opened by that specific page, such as window.open or target="_blank" links.
Use context when you want any new tab, and popup when you want a tab opened by one particular page.
Likely interview questions

Q: Why is Promise.all used here?
To start listening for the new tab and click the link at the same time, so the new tab event is never missed.

Q: What does newTab hold?
A Page object for the new tab. All later actions on that tab must use newTab.locator(...), not page.locator(...).

Q: What if no tab opens?
waitForEvent times out and throws an error, so Promise.all rejects and the test fails. You can also pass { timeout: ... } as a second argument to control how long it waits.

Q: How is this different from Selenium?
In Selenium you click, then read driver.getWindowHandles() and call switchTo().window(handle). In Playwright you get a separate Page object for each tab, so there is no switching. You just use the newTab object.

Playwright has five modifier values:

Modifier            :	Key	Notes
1. 'Alt'	        :   Alt (Option on Mac)

Usage

// single modifier

// multiple modifiers at once (Ctrl + Shift + click)
await link.click({ modifiers: ['Control', 'Shift'] });

// cross-platform: Ctrl on Windows/Linux, Cmd on Mac
await link.click({ modifiers: ['ControlOrMeta'] });

modifiers is an array, so you can combine several. Playwright presses them down before the click and releases them afterward.

Where they work

The modifiers option is available on mouse actions such as click(), dblclick(), hover() and tap().

Common browser behaviors
Ctrl/Cmd + click opens a link in a new background tab (what your test uses).
Shift + click opens a link in a new window.
Alt + click downloads the link in Chrome.

These behaviors come from the browser, not from Playwright, and can vary by browser and OS.

Keyboard shortcuts are separate

For keyboard combinations, use press() instead, and join the keys with +:

typescript
await page.keyboard.press('Control+A');
await page.keyboard.press('Shift+Tab');
await page.keyboard.press('ControlOrMeta+C');
Interview tip

Using ControlOrMeta makes your test portable across Windows, Linux and Mac. If your Playwright version is older, you can use process.platform === 'darwin' ? 'Meta' : 'Control' instead.

# Q : What is world.ts explained

===>	1. What a “World” is

In Cucumber, a World is an object that holds the state of one scenario. Cucumber creates a fresh one at the start of every scenario and discards it when the scenario ends. Inside every step and hook, this refers to that World.

Cucumber has no built-in way to pass data between steps. Each step is just an isolated function:

gherkin
Given I am on the login page        # step 1
When I login as "standard_user"     # step 2
Then I should be on the inventory page   # step 3

These three steps live in different files, yet they all need the same browser page. The World is the shared object that makes this possible. Step 1 opens the page through this.pages.login, and step 3 asserts against the same page through this.pages.inventory.

2. Why not use global variables?

You could write let page: Page; at the top of a file, but that breaks in two ways:

Parallel runs: with PARALLEL=4, several scenarios run at the same time. A shared global would be overwritten by whichever scenario started last, so scenario A would click buttons in scenario B’s browser.
Leaking state: data from one scenario could silently affect the next, producing flaky tests that pass or fail depending on order.

Because each scenario gets its own World, none of that can happen. That is what the comment means by “full isolation”.

3. The code, line by line
typescript
import { IWorldOptions, World, setWorldConstructor } from '@cucumber/cucumber';
World is Cucumber’s base class. It provides useful built-ins such as this.attach() (add screenshots or text to the report), this.log() and this.parameters.
IWorldOptions is the TypeScript type for the options Cucumber passes into the constructor.
setWorldConstructor registers your class with Cucumber.
typescript
import { BrowserContext, Page } from '@playwright/test';
import { PageManager } from '../pages/PageManager';

These are only used as types for the fields below.

typescript
export class CustomWorld extends World {

Your World inherits everything from Cucumber’s World and adds the fields this framework needs. It is exported so that steps and hooks can import it as a type.

typescript
  context!: BrowserContext;
  page!: Page;
  pages!: PageManager;
context is the Playwright browser context, an isolated profile with its own cookies and storage. The After hook closes it, and tracing runs on it.
page is the browser tab the scenario controls.
pages is the PageManager, which hands out page objects such as this.pages.login and this.pages.cart.

The ! is TypeScript’s definite assignment assertion. These fields cannot be set in the constructor because creating a browser context is asynchronous, and constructors cannot await. They are filled in later by the Before hook:

typescript
Before(async function (this: CustomWorld) {
  this.context = await browser.newContext(...);
  this.page = await this.context.newPage();
  this.pages = new PageManager(this.page);
});

Without the !, TypeScript’s strict mode would report “property has no initializer”. The ! says: “I promise this will be assigned before it is used.”

typescript
  addedProducts: string[] = [];

This is shared scenario data, not browser infrastructure. When you add a product to the cart, the step records its name here. Later, the checkout step compares the number of prices on the overview page with this.addedProducts.length. Since the World is created per scenario, it starts as an empty array each time. For this field a ! isn’t needed, because it is initialized immediately.

typescript
  constructor(options: IWorldOptions) {
    super(options);
  }

Cucumber passes options (the attach and log functions and any world parameters) into the constructor. super(options) hands them to the base class, which is how this.attach(...) works later. This constructor is technically optional, because TypeScript would generate the same one automatically. It is written out here to make clear where the options come from, and it is the place to add setup logic if you ever need it.

typescript
setWorldConstructor(CustomWorld);

This is the line that makes everything work. Without it, Cucumber would use its default World, which has no page or pages. This call tells Cucumber to create a CustomWorld for each scenario. Because it runs at import time, the file must be loaded, which cucumber.js guarantees through require: ['src/support/**/*.ts', ...].

4. The this: CustomWorld annotation in steps

Cucumber steps must use function, not arrow functions. Cucumber binds this to the World when it calls the step, and arrow functions cannot receive a bound this. The this: CustomWorld parameter does nothing at runtime. It tells TypeScript what this is, so you get autocomplete and type checking:

typescript
When('I login as {string}', async function (this: CustomWorld, userKey: string) {
  await this.pages.login.login(...);   // fully typed
});
5. Lifecycle of one World
Scenario starts
   │
   ├─ Cucumber: new CustomWorld(options)       ← constructor runs, fields empty
   ├─ Before hook: fills context/page/pages
   ├─ Steps run: read and write this.*
   ├─ After hook: screenshot, trace, close context
   │
Scenario ends → World is garbage-collected
6. How you would extend it

Add any per-scenario state here, for example:

typescript
orderNumber?: string;                 // data captured in one step, checked in another
currentUser?: Credentials;            // who is logged in
apiResponse?: unknown;                // if you add API calls

Don’t put things here that are shared across scenarios, such as the browser or config. Those belong in hooks.ts (browser) or env.ts (config), because they live longer than one scenario.

Summary
Part				Purpose
1. extends World		Gets Cucumber’s built-ins (attach, log, parameters)
2. context, page, pages		Give every step access to the same browser session
3. ! on those fields		Promises TypeScript they are set later, in Before
4. addedProducts		Scenario-scoped data shared between steps
5. setWorldConstructor		Registers the class so Cucumber uses it
6. New instance per scenario	Prevents state leaking, which makes parallel runs safe

# Q :   const browser = await chromium.launch();
console.log(browser.contexts().length); // prints `0`

const context = await browser.newContext();
console.log(browser.contexts().length); // prints `1`
Explain in detail about difference in length why is it

===>  The difference in length occurs because chromium.launch() creates a fresh browser process with no active user profiles or memory sessions, while browser.newContext() instantiates a completely isolated, incognito-like environment within that process.
To understand why the count shifts from 0 to 1, we have to look closely at Playwright’s architecture and how it manages browser states under the hood.

Phase 1: chromium.launch() \(\rightarrow \) Length: 0

When you call await chromium.launch(), Playwright starts a native Chromium browser instance in the background.
• The Raw Engine: At this point, you have launched the physical browser application process (like opening chrome.exe), but it has been launched with zero user profiles, no history, and no memory allocations.
• No Default State: Unlike opening a retail browser on your desktop—which automatically loads your default profile, active extensions, and homepage—Playwright launches a "headless" or stripped-down process.
• The Array is Empty: Because there are no active environments or profiles currently managed by this browser instance, calling browser.contexts() returns an empty array ([]). Its length is logically 0.

Phase 2: browser.newContext() \(\rightarrow \) Length: 1

When you run await browser.newContext(), you are explicitly asking Playwright to provision an isolated sandbox inside the running Chromium process.
• What is a Context? A BrowserContext is a completely isolated session. It possesses its own separate cookies, local storage, session storage, browser cache, and permissions.
• Like an Incognito Window: You can think of a context as an entirely fresh Incognito or Private Browsing window. It does not share any state with any other contexts you might create later.
• The Array Populates: Now that the Chromium process is actively hosting and managing one of these distinct session sandboxes, browser.contexts() returns an array containing that specific context object ([BrowserContext]). The length of this array is now 1.

Visualising the Hierarchy

Playwright uses a strict three-tier hierarchy to handle automation. Understanding this explains why contexts and pages (tabs) are managed separately:
text
┌─────────────────────────────────────────────────────────┐
│ 				BROWSER (The overall operating system process)         		│
│ 				browser.contexts().length // 1                          	│
└────────────┬────────────────────────────────────────────┘
             			│
             			▼
┌─────────────────────────────────────────────────────────┐
│ 				BROWSER CONTEXT (An isolated Incognito profile)       		│
│ 				context.pages().length // 0                            		│
└────────────┬────────────────────────────────────────────┘
             			│
             			▼
┌─────────────────────────────────────────────────────────┐
│ 				PAGE (A single tab inside that Incognito profile)   	    │
└─────────────────────────────────────────────────────────┘

Use code with caution.
If you were to then run const page = await context.newPage();, your browser.contexts().length would still be 1, because you haven't created a new profile—you have just opened a tab inside the existing one.

Why does Playwright do this?

This design is built for efficiency and speed. Launching a browser process (chromium.launch()) is resource-heavy and takes time. Creating a context (browser.newContext()) takes milliseconds.
By separating the browser from the context, Playwright allows you to spin up dozens of completely isolated user sessions (e.g., testing a chat app with User A and User B concurrently) without needing to pay the time and CPU penalty of launching multiple separate browser processes.

# Q : What is addInitScript() ?

==> page.addInitScript() injects and runs a JavaScript snippet into every web page before any of the page's own scripts execute.
It ensures your custom code is active from the absolute beginning of the page lifecycle—even before the HTML begins parsing or the DOM loads.

Why to Use It (The Core Benefit)

If you evaluate standard script via page.evaluate() after a page loads, you are usually too late. By that time, the website’s own scripts have already run, API requests have fired, and features have initialized.
addInitScript() provides a "time-machine" effect, letting you modify the browser environment before the website knows what hit it.

When to Use It (Common Use Cases)

1. Mocking or Stubbing Browser APIs: Overriding built-in objects (like navigator.geolocation or Notification) to control their behavior during a test.
2. Bypassing Bot Detection: Adding fake plugins or overriding navigator.webdriver properties to prevent anti-bot services (like Cloudflare or Akamai) from flagging your script as an automated tool.
3. Preloading Global Configurations / Mocks: Attaching mock tokens, data layers (window.dataLayer), or testing flags to the window object before the application boots up.

How to Use It (Code Examples)

You can call addInitScript on either a context level (applies to all tabs/pages opened in that session) or a page level (applies only to that specific tab).

Example 1: Mocking Geolocation (Context Level)

This example intercepts the browser's geolocation API so that the website automatically believes the user is in Paris, France, without prompting for permissions.
javascript
import { chromium } from 'playwright';

const browser = await chromium.launch();
const context = await browser.newContext();

// Inject the script into the context before navigating
await context.addInitScript(() => {
  const mockCoords = { latitude: 48.8566, longitude: 2.3522 };
  
  // Override the native getCurrentPosition function
  navigator.geolocation.getCurrentPosition = (success) => {
    success({ coords: mockCoords, timestamp: Date.now() });
  };
});

const page = await context.newPage();
await page.goto('https://weather.com'); // The site will immediately read Paris coordinates
Use code with caution.

Example 2: Pre-populating a Global Object (Page Level)

This example injects a feature flag into the global window object before an Angular, React, or Vue application mounts.
javascript
import { chromium } from 'playwright';

const browser = await chromium.launch();
const page = await browser.newPage();

// Inject a mock token or feature flag
await page.addInitScript(() => {
  window.__MY_APP_FLAGS__ = {
    enableBetaFeatures: true,
    mockAuthToken: 'xyz123'
  };
});

await page.goto('https://my-single-page-app.com');
// The app reads window.__MY_APP_FLAGS__ during its initialisation boot phase
Use code with caution.

Example 3: Passing Arguments to the Script

If you need to pass dynamic data from your Node.js testing environment into the browser script, you can pass an argument object.

// Passing a dynamic user object into the init script
await page.addInitScript((user) => {
  window.currentUser = user;
}, { name: 'John Doe', role: 'admin' });

Use code with caution.

# Q : How do you mock 500 server error API responses in Playwright?
==> In my Playwright automation framework, I use page.route() and route.fulfill() to mock API responses with an HTTP 500 Internal Server Error. This allows me to validate how the application handles server failures without depending on the actual backend.

For example, if the product API returns a 500 error, I verify that the application displays an appropriate error message.
Code example — Playwright with TypeScript

import { test, expect } from '@playwright/test';

test('should handle API 500 server error', async ({ page }) => {

  // Intercept the products API
  await page.route('**/api/products', async route => {
    await route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({
        message: 'Internal Server Error'
      })
    });
  });

  // Navigate to the application
  await page.goto('https://example.com/products');

  // Verify the error message
  await expect(page.getByText('Something went wrong')).toBeVisible();
});

How it works
1. page.route() intercepts requests matching the products API URL.
2. route.fulfill() returns a mocked HTTP 500 response with a JSON error message.
3. The browser processes the response, and the application's error-handling logic runs.
4. I use Playwright assertions to verify that the expected error message is displayed.

How I use this in a Cucumber framework
I keep the API mocking logic in a reusable helper or step definition so that multiple scenarios can reuse it.
import { Given } from '@cucumber/cucumber';
import { expect } from '@playwright/test';

Given('the products API returns a 500 error', async function () {
  await this.page.route('**/api/products', async route => {
    await route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({
        message: 'Internal Server Error'
      })
    });
  });
});

Here, this.page assumes my Cucumber World exposes the Playwright Page instance.

Example Gherkin scenario:
Feature: Product API error handling

  Scenario: Display an error when the products API returns 500
    Given the products API returns a 500 error
    When I navigate to the products page
    Then I should see the server error message


Best practice: I register the route before navigating to the page, use specific URL patterns to avoid intercepting unrelated requests, and verify the user-facing error state. I also keep mocked API tests separate from integration tests that validate the real backend.

# Q : How do you debug scripts passing locally but failing in Jenkins?
==> In my experience, when Playwright tests pass locally but fail in Jenkins, I first investigate environmental differences, timing issues, browser configuration, and test execution differences. I follow a systematic debugging approach rather than immediately increasing timeouts or adding retries.
My debugging approach
1. Analyze Jenkins execution logs

I check the Jenkins console output to identify the exact failing test, error message, stack trace, and failure stage. I also review whether the failure occurs during browser launch, navigation, API calls, or assertions.

2. Compare local and Jenkins environments

I verify that both environments use compatible versions of Node.js, Playwright, browser binaries, and dependencies. In Jenkins, I run:
node --version
npm --version
npx playwright --version
npx playwright install --with-deps
npm ci


I also check environment variables, base URLs, credentials, file paths, and permissions.

3. Debug timing and synchronization issues

Sometimes a test passes locally because the machine is faster or the application responds differently. I use Playwright's auto-waiting and web-first assertions instead of fixed delays.
await page.getByRole('button', { name: 'Login' }).click();

await expect(
  page.getByText('Welcome')
).toBeVisible({ timeout: 10000 });


I avoid using waitForTimeout() as a permanent solution because it can make tests slower without fixing the underlying issue.

4. Capture screenshots, videos, and traces

I configure Playwright to retain debugging artifacts when a test fails.
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,

  use: {
    headless: true,
    screenshot: 'only-on-failure',
    trace: 'retain-on-failure',
    video: 'retain-on-failure'
  },

  reporter: [
    ['list'],
    ['html', { open: 'never' }]
  ]
});


In Jenkins, I publish the HTML report and archive the test-results directory so I can inspect screenshots, videos, and Playwright traces.

5. Investigate parallel execution and test data

If tests fail only in Jenkins, I check whether parallel execution causes shared-state issues, such as multiple tests updating the same user, database record, or file. I temporarily reduce the worker count to reproduce the issue and then isolate test data or use independent browser contexts.

6. Check network and infrastructure issues

I investigate API timeouts, unavailable test environments, authentication failures, proxy settings, and intermittent server errors. I also verify that Jenkins agents have sufficient memory and CPU resources.
Example from my automation framework
Suppose a login test passes locally but fails intermittently in Jenkins. I would inspect the trace to see whether the login API returned an error, the dashboard loaded slowly, or the locator matched an unexpected element. Based on the evidence, I would fix the underlying problem—for example, correct the environment configuration, wait for the actual dashboard state, or isolate test data.
My conclusion in an interview
“I use Jenkins logs and Playwright traces as my primary debugging tools. I compare the local and CI environments, verify synchronization and test-data isolation, and check network and resource constraints. # Q : What is your strategy when a release feature changes mid-sprint?
==> When a release feature changes mid-sprint, my strategy is to understand the impact of the change, reassess testing priorities, and collaborate with the developers, Product Owner, and Business Analyst to ensure the updated requirements are validated without compromising release quality.
My approach
1. Understand the requirement change

First, I discuss the change with the Product Owner or Business Analyst to clarify the updated acceptance criteria, expected behavior, and business impact. I identify what has changed compared with the original requirement.

2. Perform impact analysis

I identify the affected test cases, existing automation scripts, API validations, and dependent modules. I also check whether the change impacts shared components or existing regression scenarios.

3. Prioritize testing based on risk

I prioritize the following:
- Critical business workflows and updated acceptance criteria.
- Impacted functional and integration test cases.
- API and UI validations related to the changed feature.
- Regression testing for related modules.
- Low-risk scenarios, which can be tested later if time is limited.
4. Update the Playwright automation framework

I update the affected page objects, reusable methods, locators, test data, and assertions. If the API contract changes, I also update API validation and mocking logic where required.

For example, if the login flow changes from email-based login to email plus OTP, I update the login page methods, add OTP-related test scenarios, and validate successful login, invalid OTP, expired OTP, and relevant regression flows.

5. Collaborate with the team

I communicate the testing impact, additional effort, risks, and potential release blockers during sprint discussions. If the change introduces significant additional work, I discuss scope and timeline adjustments with the team rather than silently reducing test coverage.

6. Execute focused regression testing

2. Read the browser in Playwright configuration
Create a browser configuration file, for example, support/browser.ts:
import {
  chromium,
  firefox,
  webkit,
  Browser,
  BrowserType
} from '@playwright/test';

export async function launchBrowser(): Promise<Browser> {
  const browserName = process.env.BROWSER || 'chromium';

  const browsers: Record<string, BrowserType> = {
    chromium,
    firefox,
    webkit
  };

  const browserType = browsers[browserName];

  if (!browserType) {
    throw new Error(`Unsupported browser: ${browserName}`);
  }

  return await browserType.launch({
    headless: true
  });
}


This helper validates the browser name and launches the corresponding browser.

import { World, IWorldOptions, setWorldConstructor } from '@cucumber/cucumber';

}

# Q : How do you mock 403 Forbidden API response payloads in Playwright route handlers?
==> To mock a 403 Forbidden API response payload in Playwright, you leverage the page.route() or context.route() handler along with the route.fulfill() method. This stops the request from reaching the actual server and returns your custom status code, custom headers, and mock payload directly.

1. Basic JSON Payload Mocking

For standard JSON APIs, specify the exact endpoint (or glob pattern), set the status to 403, and pass your error payload inside the json option.
javascript
test('should display access denied message on 403 API response', async ({ page }) => {
  // 1. Set up the route handler BEFORE triggering the network call
  await page.route('**/api/v1/user/profile', async route => {
    await route.fulfill({
      status: 403,
      contentType: 'application/json',
      // Playwright automatically converts JavaScript objects passed to 'json' into a string
      json: {
        success: false,
        error: 'Forbidden',
        code: 'INSUFFICIENT_PERMISSIONS',
        message: 'Your account does not have the required role to view this profile.'
      }
    });
  });

  // 2. Trigger the network request (e.g., via page navigation or a button click)
  await page.goto('/profile-settings');

  // 3. Assert that your frontend UI gracefully handles the mocked payload
  await expect(page.locator('.alert-danger')).toContainText('Your account does not have the required role');
});
Use code with caution.

2. Mocking Text, HTML, or Custom Error Pages

If your backend or API gateway (like AWS API Gateway, Nginx, or Cloudflare) returns raw text or custom HTML blocks instead of JSON for a 403 error, swap the json field for the body field:
javascript
await page.route('**/api/v1/internal/**', async route => {
  await route.fulfill({
    status: 403,
    contentType: 'text/html', // or 'text/plain'
    body: '<html><body><h1>403 Forbidden: IP address blocked</h1></body></html>'
  });
});
Use code with caution.

3. Simulating Authentication Token Expiration (Dynamic 403)

If you want to allow authentic user requests to pass through initially, but suddenly trigger a 403 error when a user performs an unauthorized method (like trying to POST to an admin path), inspect the route.request() properties:
javascript
await page.route('**/api/v1/documents/*', async route => {
  const method = route.request().method();
  const headers = route.request().headers();

  // If a user tries to delete a file, mock a 403 permission error
  if (method === 'DELETE') {
    await route.fulfill({
      status: 403,
      json: { message: 'Write and delete actions are blocked in read-only mode.' }
    });
  } else {
    // Allow GET requests to hit the real network/server normally
    await route.continue();
  }
});
Use code with caution.

Pro Tip: Validating the Network Interception

To ensure your frontend actually received the 403 payload exactly as expected, combine your actions with page.waitForResponse() to catch the intercepted payload event explicitly:
javascript
// Set up the tracker
const responsePromise = page.waitForResponse('**/api/v1/user/profile');

// Click the button that causes the API call
await page.getByRole('button', { name: 'Fetch Profile' }).click();

// Wait for the response event and check the intercepted properties
const response = await responsePromise;
expect(response.status()).toBe(403);

const responseBody = await response.json();
expect(responseBody.code).toBe('INSUFFICIENT_PERMISSIONS');
Use code with caution.

# Q : Can you explain a real scenario where inheritance caused an issue?
==> In Playwright TypeScript/JavaScript, a notorious real-world scenario where inheritance causes massive headaches is over-abstracting the Page Object Model (POM) using deep hierarchical inheritance.
In Test Automation, developers often fall into the trap of matching their automation code hierarchy exactly to the visual layout of the application using extends. This leads to the Fragile Base Class problem.

The Scenario: The "Dashboard Nested Component" Trap


1. The Setup (The Visual Illusion)

Imagine you are testing a complex Enterprise Dashboard application. An automation engineer designs the framework by mimicking the UI hierarchy using inheritance:
1. BasePage: Contains the global layout (Top Navbar, Side Sidebar).
2. DashboardPage extends BasePage: Contains components unique to the dashboard view (date filters).
3. AnalyticsDashboard extends DashboardPage: Contains metrics, charts, and detailed analytical components.
typescript
// ❌ Anti-pattern: Deeply Nested Page Object Hierarchy
class BasePage {
    protected page: Page;
    readonly sideMenuButton = () => this.page.locator('.sidebar-toggle');
    
    constructor(page: Page) { this.page = page; }
    
    async navigateTo(url: string) { await this.page.goto(url); }
}

class DashboardPage extends BasePage {
    readonly dateFilter = () => this.page.locator('.date-picker');

    async selectDateRange() {
        // Relies on parent setup
        await this.sideMenuButton().click(); 
        await this.dateFilter().click();
    }
}

class AnalyticsDashboard extends DashboardPage {
    readonly exportCsvButton = () => this.page.locator('#export-csv');

    async exportReport() {
        // Inherits everything from DashboardPage AND BasePage
        await this.selectDateRange(); 
        await this.exportCsvButton().click();
    }
}
Use code with caution.

2. The Issue: The Ripple Effect (Fragile Base Class)

A few months later, the frontend development team updates the application's layout. For performance reasons, they change how the application shell works:
• They replace the .sidebar-toggle button in the main layout with a personalized user menu.
• To fix this, an engineer changes the locator or the logic inside BasePage.sideMenuButton().
The Fallback:
Because AnalyticsDashboard is deeply coupled via inheritance, changing BasePage subtly modifies how selectDateRange() executes inside DashboardPage.
• The AnalyticsDashboard test suite suddenly breaks with timeouts.
• Because the error occurs 3 layers deep, the stack trace becomes highly confusing, masking exactly where the execution failed.
• Furthermore, if you want to instantiate AnalyticsDashboard, Playwright must carry over all methods and locators from DashboardPage and BasePage, flooding your IDE auto-complete with dozens of irrelevant actions. This makes writing tests harder for junior team members.

The Architecture Comparison

Problem Dimension	Deep Inheritance (extends DashboardPage)	Composition (has-a Components)
Coupling	Tight: A change to the top-level BasePage breaks all child and grandchild pages.	Loose: Components are decoupled modules. A change to one doesn't affect others.
Readability	Obscured: Tracking down where a locator or function is declared requires traversing multiple files.	Explicit: You see exactly which component is being interacted with in the test.
Flexibility	Rigid: If a new page needs the sidebar but not the date filter, it cannot easily inherit from DashboardPage.	Fluid: You mix and match exactly the building blocks a specific test needs.


The Playwright Fix: Composition using Fixtures

Instead of relying on an extends hierarchy, Playwright provides a powerful, built-in feature designed exactly to avoid inheritance: Custom Fixtures.
By breaking the page down into separate, self-contained components and injecting them via fixtures, you decouple your architecture.

1. Define Independent Components (No extends)

typescript
// component/Sidebar.ts
export class SidebarComponent {
    constructor(private page: Page) {}
    readonly toggleButton = this.page.locator('.sidebar-toggle');
    async open() { await this.toggleButton.click(); }
}

// component/DateFilter.ts
export class DateFilterComponent {
    constructor(private page: Page) {}
    readonly picker = this.page.locator('.date-picker');
    async selectToday() { await this.picker.click(); }
}

// page/AnalyticsPage.ts
export class AnalyticsPage {
    constructor(private page: Page) {}
    readonly exportCsvButton = this.page.locator('#export-csv');
    async export() { await this.exportCsvButton.click(); }
}

2. Bundle them in a Custom Playwright Fixture

typescript
// fixtures/testFixtures.ts
import { test as base } from '@playwright/test';
import { SidebarComponent } from '../component/Sidebar';
import { DateFilterComponent } from '../component/DateFilter';
import { AnalyticsPage } from '../page/AnalyticsPage';

type MyFixtures = {
    sidebar: SidebarComponent;
    dateFilter: DateFilterComponent;
    analyticsPage: AnalyticsPage;
};

export const test = base.extend<MyFixtures>({
    sidebar: async ({ page }, use) => { await use(new SidebarComponent(page)); },
    dateFilter: async ({ page }, use) => { await use(new DateFilterComponent(page)); },
    analyticsPage: async ({ page }, use) => { await use(new AnalyticsPage(page)); },
});
Use code with caution.

3. Use Them Explicitly in the Test

Now, your test explicitly calls exactly what it needs. If the sidebar changes, it only breaks the SidebarComponent file, without creating a cascading failure across your analytics pages.
typescript
// specs/analytics.spec.ts
import { test } from '../fixtures/testFixtures';

test('should export analytics report successfully', async ({ sidebar, dateFilter, analyticsPage, page }) => {
    await page.goto('/analytics');
    
    // Explicit, readable, and highly maintainable:
    await sidebar.open();
    await dateFilter.selectToday();
    await analyticsPage.export();
});

# Q : what is LaunchOptions in playwright typescript ?
==> In Playwright with TypeScript, LaunchOptions is an interface/type that defines the configuration settings passed when starting a browser instance (such as Chromium, Firefox, or WebKit) via browserType.launch(), or configured globally inside playwright.config.ts.

What LaunchOptions Controls

It configures low-level browser process parameters rather than individual page or context settings. Common properties include:
• headless: A boolean (true or false) to run the browser with or without a visible UI window.
• slowMo: A number that slows down Playwright operations by a specified number of milliseconds (useful for debugging and watching test execution).
• args: An array of strings containing additional command-line arguments to pass to the browser process (e.g., ['--disable-gpu', '--no-sandbox']).
• executablePath: A string pointing to a custom browser executable path instead of Playwright’s bundled browser.
• channel: A string specifying a browser distribution channel like 'chrome', 'msedge', 'chrome-beta', or 'msedge-dev'.
• proxy: An object configuring network proxy settings (server, bypass rules, username, and password).
• timeout: Maximum time in milliseconds to wait for the browser instance to start up.
• env: An object specifying environment variables for the launched browser process.

How to Use LaunchOptions


1. In Playwright Test Configuration (playwright.config.ts)

You can pass launchOptions inside the use block of your global config:
typescript
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    launchOptions: {
      slowMo: 50,
      headless: false,
      args: ['--start-maximized'],
    },
  },
});
Use code with caution.

2. Programmatically in a script (chromium.launch)

You can pass an object typed with LaunchOptions directly when launching a browser manually:
typescript
import { chromium, LaunchOptions } from '@playwright/test';

const options: LaunchOptions = {
  headless: false,
  slowMo: 100,
  args: ['--disable-infobars'],
};

(async () => {
  const browser = await chromium.launch(options);
  const page = await browser.newPage();
  await page.goto('https://example.com');
  await browser.close();
})();
Use code with caution.

# Q : Explain in detail about nodejs variable process with syntax and examples
====> In Node.js, process is a global object that provides information about, and control over, the current Node.js process. Because it is a global object, it is available in every file automatically without using require() or import.
It acts as a bridge between your JavaScript application and the underlying operating system.

Core Syntax and Properties

The process object contains dozens of built-in properties, methods, and events. The most critical properties include:

Property / Method	     | Description
1. process.env	     | An object containing the user environment variables (like API keys, ports, or deployment stages).
2. process.argv	     | An array containing the command-line arguments passed when the Node.js process was launched.
3. process.cwd()      | A method that returns the current working directory of the Node.js process (where you ran the terminal command).
4. process.exit()	  | A method that forces the Node.js process to terminate immediately.
5. process.platform  | A string identifying the operating system platform (e.g., 'darwin', 'win32', 'linux').

Detailed Code Examples

1. Managing Configuration with Environment Variables (process.env)

process.env is heavily used in production applications to keep secrets, database credentials, and configuration flags out of the source code.
javascript
// app.js
// 1. Set a default port if the environment variable isn't provided
const PORT = process.env.PORT || 3000;

// 2. Fetch a sensitive API key safely
const apiKey = process.env.SECRET_API_KEY;

if (!apiKey) {
  console.error("Error: SECRET_API_KEY is missing!");
  process.exit(1); // Stop execution with an error code
}

console.log(`Server running on port ${PORT}`);
#-----------------------------------------------#
How to run it in the terminal:
bash
# On Linux/macOS
PORT=8080 SECRET_API_KEY=my_secure_token node app.js

# On Windows (PowerShell)
$env:PORT=8080; $env:SECRET_API_KEY="my_secure_token"; node app.js
#------------------------------------------------------#

2. Reading Command-Line Arguments (process.argv)

When you launch a script with extra flags or words, process.argv captures them.
• process.argv[0] is always the path to the Node executable.
• process.argv[1] is always the path to the JavaScript file being executed.
• process.argv[2] and onwards are your custom arguments.

javascript
// greet.js
// Capture arguments passed after the filename
const args = process.argv.slice(2); 
const username = args[0] || 'Guest';

console.log(`Hello, ${username}!`);
console.log("Full argument array:", process.argv);
Use code with caution.
How to run it in the terminal:
bash
node greet.js Alice
Use code with caution.
Output:
text
Hello, Alice!
Full argument array: [
  '/usr/local/bin/node',
  '/Users/project/greet.js',
  'Alice'
]

3. Graceful Termination & OS Detection (process.exit & process.platform)

You can use process to write scripts that behave differently depending on the operating system, or to exit cleanly when a condition fails.
javascript
// os-check.js
console.log(`This script is running on: ${process.platform}`);

// Example: Restrict execution to specific operating systems

  console.log("Windows setup completed.");
} else if (process.platform === 'darwin') {
  console.log("macOS setup completed.");
} else {

  process.exit(1); // 0 means success, 1 (or non-zero) means an error occurred
}

# Q : Write code to find Broken Links in playwright typescript
==> Here’s a solid broken-link checker for Playwright with TypeScript. It collects every <a href> on a page, normalizes and de-duplicates them, then validates each one using Playwright’s APIRequestContext (no page navigation needed, so it’s much faster).

tests/brokenLinks.spec.ts

typescript
import { test, expect, APIRequestContext } from '@playwright/test';

interface LinkResult {
  url: string;
  status: number | string;
  ok: boolean;
}

const BASE_URL = 'https://www.example.com';

// Skip non-HTTP schemes
const isCheckable = (href: string): boolean =>
  !!href &&
  !href.startsWith('#') &&
  !href.startsWith('mailto:') &&
  !href.startsWith('tel:') &&
  !href.startsWith('javascript:');

async function checkLink(request: APIRequestContext, url: string): Promise<LinkResult> {
  try {
    // HEAD is lighter; fall back to GET if server rejects HEAD
    let response = await request.head(url, { timeout: 15000, maxRedirects: 5 });
    if (response.status() === 405 || response.status() === 501) {
      response = await request.get(url, { timeout: 15000, maxRedirects: 5 });
    }
    return { url, status: response.status(), ok: response.status() < 400 };
  } catch (error) {
    return { url, status: (error as Error).message, ok: false };
  }
}

test('Find broken links on the page', async ({ page, request }) => {
  await page.goto(BASE_URL, { waitUntil: 'domcontentloaded' });

  // 1. Collect all hrefs (resolved to absolute URLs by the browser)
  const hrefs: string[] = await page.$$eval('a[href]', (anchors) =>
    anchors.map((a) => (a as HTMLAnchorElement).href)
  );

  // 2. Filter + de-duplicate
  const uniqueLinks = [...new Set(hrefs.filter(isCheckable))];
  console.log(`Total unique links found: ${uniqueLinks.length}`);

  // 3. Check in parallel batches to avoid hammering the server
  const batchSize = 10;
  const results: LinkResult[] = [];

  for (let i = 0; i < uniqueLinks.length; i += batchSize) {
    const batch = uniqueLinks.slice(i, i + batchSize);
    const batchResults = await Promise.all(batch.map((url) => checkLink(request, url)));
    results.push(...batchResults);
  }

  // 4. Report
  const brokenLinks = results.filter((r) => !r.ok);
  const validLinks = results.filter((r) => r.ok);

  console.log(`Valid links  : ${validLinks.length}`);
  console.log(`Broken links : ${brokenLinks.length}`);
  brokenLinks.forEach((l) => console.log(`BROKEN -> ${l.url} [${l.status}]`));

  // 5. Fail the test if any link is broken
  expect(brokenLinks, `Broken links found:\n${JSON.stringify(brokenLinks, null, 2)}`).toHaveLength(0);
});

Run it:

bash
npx playwright test tests/brokenLinks.spec.ts

How it works (good to explain in an interview):

page.$$eval('a[href]', ...) runs inside the browser and returns anchor.href, which is already an absolute URL, so you don’t need to resolve relative paths yourself.
Set removes duplicates so each URL is only checked once.
request.head() uses Playwright’s APIRequestContext to hit the URL without loading the page in a browser, which is far faster than page.goto() per link. If a server doesn’t support HEAD (405/501), it falls back to GET.
Status >= 400 is treated as broken (404, 500, etc.). Network errors like DNS failures or timeouts are caught and also reported as broken.
Batching with Promise.all gives parallelism without flooding the server or triggering rate limits (429).

Common follow-up points interviewers ask:

Why not page.goto() for each link? It’s slow and heavy, since it renders the whole page. request is an HTTP-only call.
Internal links only? Add a filter: new URL(url).origin === new URL(BASE_URL).origin.
Multiple pages? Wrap the logic in a function and loop over a list of page URLs, or crawl recursively with a visited Set.
Broken images? Same approach with page.$$eval('img[src]', ...), or check naturalWidth === 0 in the browser.
Some sites return 403/429 to bots (LinkedIn, for example). Treat these as warnings, or add a custom User-Agent header via request.head(url, { headers: {...} }).
Reporting: use test.step() per link or attach the broken list with testInfo.attach('broken-links.json', { body: JSON.stringify(brokenLinks), contentType: 'application/json' }).

Bonus: soft assertions so every broken link is listed (not just the first):

typescript
for (const link of results) {
  expect.soft(link.ok, `${link.url} returned ${link.status}`).toBeTruthy();
}

This way the report shows all failures in one run instead of stopping at the first.

# Q :  Suppose you have 200 test case and 49 test failed , how would you collect the data of only failed test cases
==> In Playwright, there are a few layers to this, and I’d pick based on whether I need the data during the run, after the run, or for re-running the failures.

1. Built-in reporters (my first choice)

Playwright’s JSON reporter writes every result with its status, so I can filter out only the failures:

ts
// playwright.config.ts
reporter: [
  ['html'],
  ['json', { outputFile: 'test-results/results.json' }],
],

Then a small script reads the JSON and extracts only the failed ones:

ts
import fs from 'fs';

const data = JSON.parse(fs.readFileSync('test-results/results.json', 'utf-8'));
const failed: any[] = [];

function walk(suite: any) {
  suite.specs?.forEach((spec: any) => {
    spec.tests.forEach((t: any) => {
      const last = t.results[t.results.length - 1];
      if (last.status === 'failed' || last.status === 'timedOut') {
        failed.push({
          title: spec.title,
          file: spec.file,
          error: last.error?.message,
          retries: t.results.length - 1,
        });
      }
    });
  });
  suite.suites?.forEach(walk);
}
data.suites.forEach(walk);

fs.writeFileSync('failed-tests.json', JSON.stringify(failed, null, 2));
console.log(`Failed: ${failed.length}`);

So out of 200 tests, I’d get a clean JSON of the 49 failures with test name, file, and error message.

2. Custom reporter (best for real-time collection)

If I want to collect failures while the run is in progress, I’d implement a custom reporter using the Reporter interface and its onTestEnd hook:

ts
// failed-reporter.ts
import { Reporter, TestCase, TestResult } from '@playwright/test/reporter';
import fs from 'fs';

class FailedReporter implements Reporter {
  failed: any[] = [];

  onTestEnd(test: TestCase, result: TestResult) {
    if (result.status === 'failed' || result.status === 'timedOut') {
      this.failed.push({
        title: test.title,
        file: test.location.file,
        error: result.error?.message,
        duration: result.duration,
      });
    }
  }

  onEnd() {
    fs.writeFileSync('failed-tests.json', JSON.stringify(this.failed, null, 2));
  }
}
export default FailedReporter;
ts
reporter: [['./failed-reporter.ts']]

Playwright has this built in. It saves last-run info in test-results/.last-run.json, so I can do:

This re-runs only the 49 failed tests, which is handy for confirming whether they’re real bugs or flaky.

To make the failure data actually useful for debugging, I’d configure:

In the pipeline, I’d publish the JSON/HTML report as an artifact, and use if: failure() / if: always() steps to upload failed-tests.json and traces. I can also use it to auto-create defects in Jira or send a Slack summary with only the failed test names and errors.

One important point: when retries are enabled, I always check the last result of each test, not the first. A test that failed once and passed on retry is flaky, not failed, and I’d report it in a separate category.

So in short: JSON reporter or a custom reporter to collect the data, --last-failed to re-run, and screenshots/traces for debugging.”

# Q : How do you differentiate flaky from genuinely failed tests?”
==> In Playwright, I rely on retries plus the outcome Playwright assigns to each test. I don’t judge from a single run.

1. Enable retries

ts
// playwright.config.ts
retries: process.env.CI ? 2 : 1,

Without retries, every failure looks the same. With retries, Playwright can tell me what actually happened across attempts.

2. Use Playwright’s built-in outcome classification

Each test ends up with one of four outcomes:

expected: passed on the first attempt
unexpected: failed on every attempt, so it’s a genuine failure
flaky: failed at least once, then passed on a retry
skipped: not executed

The HTML report shows flaky tests under a separate “Flaky” tab, and the console summary also prints something like 3 flaky, 46 failed, 151 passed.

3. Detect it in a custom reporter

ts
onTestEnd(test: TestCase, result: TestResult) {
  const outcome = test.outcome();   // 'expected' | 'unexpected' | 'flaky' | 'skipped'

  if (outcome === 'flaky') {
    this.flaky.push({ title: test.title, attempts: test.results.length });
  } else if (outcome === 'unexpected') {
    this.failed.push({ title: test.title, error: result.error?.message });
  }
}

One thing to note: onTestEnd fires after every attempt, so I’d make the final classification at the last retry, or collect in onEnd by iterating suites, so I don’t count the same test twice.

4. Fail on flaky tests if needed

ts
failOnFlakyTests: true

This makes the run fail when any test is flaky, so flakiness doesn’t hide behind a green build.

5. Confirm with repeat runs

To verify a suspected flaky test locally, I run it many times:

bash
npx playwright test login.spec.ts --repeat-each=20
Fails 20 out of 20 → genuine bug (or broken locator or environment)
Fails 3 out of 20 → flaky
Passes consistently now but failed earlier → possibly environment or data related

I also run it in headed mode and with --workers=1. If it passes alone but fails in parallel, that points to test dependency or shared data issues.

6. Analyze the root cause using traces

I enable trace: 'on-first-retry' and compare the failed attempt with the passing one in the trace viewer. Common flaky causes I’ve seen:

Hard waits (waitForTimeout) instead of auto-waiting or web-first assertions
Race conditions with network calls, fixed by waitForResponse or expect(locator).toBeVisible()
Shared test data or tests depending on each other’s state
Unstable locators (dynamic IDs or index-based selectors)
Animations or overlays blocking clicks
Slow or unstable test environment

7. Handle them differently

Genuine failures: raise a defect with the screenshot, trace and error
Flaky tests: tag them (for example @flaky), track them separately, fix the root cause, and not just bump the retry count. I’d only quarantine one temporarily with test.fixme(), with a ticket linked, so it doesn’t block the pipeline.

The key point is that retries are a diagnostic tool, not a fix. If I rely on retries to make tests green, I’m hiding the problem rather than solving it.”

Possible next follow-up: “What’s the difference between trace: 'on-first-retry' and 'retain-on-failure'?” Short answer: on-first-retry records a trace only when a test is retried, which saves disk and runtime. retain-on-failure records every run but keeps the trace only for failed ones, which is heavier but gives you the trace even with retries off.

#====================================================================================================
# Q : What’s the difference between trace: 'on-first-retry' and 'retain-on-failure'?”
==> Both options control when Playwright keeps a trace, but they differ in when recording happens and what gets saved.

trace: 'on-first-retry'

The first attempt of a test runs with no tracing.
Only if that test fails and Playwright retries it does it record a trace, for the first retry.
The trace is kept for that retry attempt, whether it passes or fails.
It needs retries to be at least 1. With retries set to 0, you never get a trace.

trace: 'retain-on-failure'

Every test is recorded on every attempt, including the first.
When the attempt ends, Playwright keeps the trace only if the test failed and discards it if it passed.
It works even with retries: 0.
ts
use: {
  trace: 'on-first-retry',        // lightweight, CI-friendly
  // trace: 'retain-on-failure',  // heavier, but trace for every failure
},

Key differences
				| on-first-retry				| retain-on-failure
1. Recorded on first attempt	| No					| Yes
2. Needs retries enabled		| Yes					| No
3. Performance overhead		| Low, since only retried tests are traced	| Higher, since all tests are traced
4. Trace of the original failure	| No, you get the retry’s trace instead	| Yes, the actual failed attempt
5. Disk usage			| Small					| Larger during the run, but only failures are kept

When I use which

on-first-retry is my default for large suites in CI. With 200 tests, tracing everything slows the run and uses a lot of storage, and tracing only retries gives me debugging data for the failures at minimal cost. It’s also the Playwright-recommended default.
retain-on-failure is what I use when:
I’m debugging locally and want the trace of the exact failing run
retries are disabled
the failure is hard to reproduce, so a retry might pass and I’d lose the evidence of what went wrong the first time
I have a smaller suite where the overhead doesn’t matter

One trade-off worth mentioning

With on-first-retry, if a test is flaky and passes on the retry, I get a trace of a passing run, which is less useful for finding the cause. With retain-on-failure, I always get the trace of the failing attempt, which is what I actually need for flaky tests. So for investigating flakiness I temporarily switch to retain-on-failure, or use 'on-all-retries', which records every retry attempt.

There’s also trace: 'on', which records and keeps everything. I avoid it in regular runs because of the size and slowdown.”

# Q : How do you open and analyze a trace?
==> I’d open it in one of three ways, depending on where the test ran.

1. Ways to open a trace

bash
# a) Directly from the CLI
npx playwright show-trace test-results/login-spec-chromium/trace.zip

# b) From the HTML report (click the trace icon/attachment under the failed test)
npx playwright show-report

# c) Drag and drop trace.zip into https://trace.playwright.dev

The trace.playwright.dev viewer runs entirely in the browser, so nothing is uploaded to a server.
Traces sit in test-results/<test-folder>/. Retry attempts get their own folder with a -retry1 suffix, so I make sure I’m opening the right attempt.

2. What the viewer shows

Actions panel (left): every step (click, fill, expect, goto) with its duration. Failed steps are highlighted in red.
Timeline (top): a filmstrip of screenshots over time. I can hover or drag to scrub through the run.
Snapshot area (centre): a live DOM snapshot with three tabs: Before, Action (shows where the click or fill happened), and After.
Bottom tabs:
Call: locator used, timeout, wait time, and the exact error
Log: actionability checks, for example “waiting for element to be visible, enabled and stable” or “element intercepts pointer events”
Errors: the assertion or timeout message with the code frame
Console: browser console errors and warnings
Network: every request with status, timing, headers and response body
Source: the test code with the failing line highlighted
Attachments: screenshots, videos and anything I attached

3. How I analyze a failure

Start at the red step. I read the error in the Errors tab, such as a timeout or expect(locator).toHaveText mismatch.
Check the Before/After snapshots. Was the element actually on the page? Was a popup, overlay or loader covering it? Was the page in the state I expected?
Read the Log tab. It tells me why the action stalled, for example element not visible, not enabled, or intercepts pointer events.
Check the Network tab. A 500 or 401 on an API call, a failed or slow request, or a wrong response payload often explains a UI failure. Then it’s an application or environment issue, not a test issue.
Check the Console tab. JavaScript errors point to a front-end bug.
Use the locator picker. If the locator is wrong or ambiguous (strict mode violation), I pick the element in the snapshot and Playwright suggests a better locator. I can then copy it straight into the test.
Compare with a passing run. For flaky tests, I open the failing trace and the passing trace side by side and look at timing and network differences. That usually reveals a race condition or a missing wait.

4. Example from practice

A test failed with a timeout on click('#submit'). In the trace, the Log tab said ‘<div class="loader"> intercepts pointer events’, and the Network tab showed the API behind the loader taking 8 seconds. So the root cause was a slow backend call with no proper wait in the test. I fixed it by waiting for the response with waitForResponse and asserting the loader was hidden, instead of increasing the timeout.

# Q : How do you handle flaky tests caused by dynamic elements or waits in Playwright?
==> My approach is to fix the root cause with Playwright’s built-in waiting and stable locators, not to add sleeps or raise timeouts. I’d look at four areas: locators, waits, assertions and test design.

1. Use stable locators for dynamic elements

Dynamic IDs, auto-generated class names and index-based XPath are the biggest source of flakiness, so I avoid them.

ts
// Fragile
await page.locator('#btn-83921').click();
await page.locator('//div[3]/button[2]').click();

// Stable
await page.getByRole('button', { name: 'Submit' }).click();
await page.getByTestId('submit-order').click();
await page.getByLabel('Email').fill('user@test.com');
Preference order: getByRole, getByLabel, getByTestId, then CSS as a last resort.
I ask developers to add data-testid attributes where the UI has no stable hook.
For lists or repeated elements, I filter by content instead of position:
ts
await page.getByRole('row').filter({ hasText: 'Order #1042' })
  .getByRole('button', { name: 'View' }).click();

2. Rely on auto-waiting

Before every action (click, fill, check), Playwright automatically waits for the element to be attached, visible, stable (not animating), enabled, and able to receive events (not covered by an overlay). So I don’t add manual waits before actions.

3. Use web-first assertions, not one-time checks

ts
// Flaky: checks once, no retry
expect(await page.locator('.status').textContent()).toBe('Done');
expect(await page.locator('.toast').isVisible()).toBe(true);

// Reliable: retries until it passes or times out
await expect(page.locator('.status')).toHaveText('Done');
await expect(page.locator('.toast')).toBeVisible();

Web-first assertions (toBeVisible, toHaveText, toHaveCount, toHaveURL) keep retrying until the condition is met. Reading a value first and then asserting on it is a common cause of flakiness.

For values that need polling, such as a backend status, I use:

ts
await expect.poll(async () => {
  const res = await request.get('/api/orders/42');
  return (await res.json()).status;
}, { timeout: 15000 }).toBe('COMPLETED');

4. Wait on specific conditions, never on time

ts
// Bad
await page.waitForTimeout(5000);

// Good: wait for the actual event
const responsePromise = page.waitForResponse(
  r => r.url().includes('/api/search') && r.status() === 200
);
await page.getByRole('button', { name: 'Search' }).click();
await responsePromise;

await expect(page.locator('.spinner')).toBeHidden();
await page.waitForURL('**/dashboard');
await page.waitForLoadState('networkidle'); // only when really needed

Note that I register waitForResponse before the action that triggers it, otherwise the response can arrive before I start listening, which creates a race condition.

5. Handle specific dynamic-element scenarios

Loaders and overlays: assert the spinner is hidden before interacting with what’s behind it.
Animations: Playwright waits for stability, and for CSS animations I can set animations: 'disabled' in screenshot options or disable transitions in the test environment.
Elements that re-render: locators are lazy and re-queried each time, so I don’t store ElementHandle objects. That avoids stale element errors.
Dynamic lists or tables: wait for the expected count with toHaveCount, then act.
Iframes: use frameLocator, not switching contexts.
New tabs or popups: use const popupPromise = page.waitForEvent('popup') before the click.
Toasts that disappear quickly: assert immediately after the action with a web-first assertion, and not after other steps.

6. Mock or control unstable dependencies

If a flaky test depends on a slow or inconsistent third-party API, I use page.route() to mock it:

ts
await page.route('**/api/recommendations', route =>
  route.fulfill({ status: 200, json: { items: [] } })
);

This makes the test deterministic. I keep a few unmocked end-to-end tests as well, so real integration is still covered.

7. Improve test design

Keep each test independent, with its own data and its own login. I use storageState to reuse authentication safely without sharing browser state.
Create test data through the API, not through long UI flows.
Avoid depending on execution order or on shared data between parallel workers.
Use unique data per run, for example a timestamp or UUID in usernames.

8. Detect and track flakiness

Retries (retries: 2 in CI) plus the flaky outcome in the report show which tests are unstable.
--repeat-each=20 confirms whether a fix really worked.
Trace viewer (on-first-retry or retain-on-failure) shows what was on the screen and in the network when it failed.
I tag unstable tests, fix the root cause, and use test.fixme() with a ticket only as a short-term quarantine.

One thing I avoid: increasing the global timeout to hide a flaky test. It makes failures slower and doesn’t fix anything. I’d only raise a timeout for a specific step that is legitimately slow, for example { timeout: 30000 } on one assertion for a report-generation step.

Quick example from my experience: a search results test failed about 1 in 10 runs. The trace showed the assertion ran while the old results were still displayed, before the new API response arrived. I replaced the waitForTimeout(3000) with a waitForResponse on the search API and a toHaveCount assertion on the results list, and it passed 50 out of 50 times with --repeat-each.”

That avoids repeating the UI login and makes tests faster and more stable.

# Q : How do you handle authentication or login across multiple tests in Playwright?
==> My approach is to log in once, save the authenticated session, and reuse it everywhere. That removes repeated UI logins, which are slow and a common source of flakiness, while each test still gets its own fresh browser context.

1. Core idea: storageState

After login, Playwright can save cookies and localStorage to a JSON file. Other tests load that file into a new context, so they start already logged in.

2. Setup project (my preferred approach)

ts
// tests/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/user.json';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill(process.env.USER_NAME!);
  await page.getByLabel('Password').fill(process.env.USER_PASSWORD!);
  await page.getByRole('button', { name: 'Login' }).click();

  await expect(page).toHaveURL(/dashboard/);
  await page.context().storageState({ path: authFile });
});
ts
// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  {
    name: 'chromium',
    use: {
      ...devices['Desktop Chrome'],
      storageState: 'playwright/.auth/user.json',
    },
    dependencies: ['setup'],
  },
],

The setup project runs first, saves the session, and every test in the chromium project starts authenticated. Because it’s a normal project, it also shows up in the HTML report and traces, which makes login failures easy to debug. I prefer this over globalSetup for that reason.

3. Never commit the auth file

# .gitignore
playwright/.auth

The file contains live session tokens. Credentials come from environment variables or CI secrets, never hardcoded.

4. Multiple roles (admin, user, read-only)

ts
// auth.setup.ts
setup('login as admin', async ({ page }) => { /* ... */ await page.context().storageState({ path: 'playwright/.auth/admin.json' }); });
setup('login as user',  async ({ page }) => { /* ... */ await page.context().storageState({ path: 'playwright/.auth/user.json' }); });
ts
// in a spec file
test.describe('admin features', () => {
  test.use({ storageState: 'playwright/.auth/admin.json' });
  test('can delete users', async ({ page }) => { /* ... */ });
});

test.describe('guest checks', () => {
  test.use({ storageState: { cookies: [], origins: [] } }); // not logged in
  test('redirects to login', async ({ page }) => { /* ... */ });
});

For tests that need two roles at once, such as admin approving a user’s request, I create two contexts with different storageState files in the same test.

5. API login for speed

If the app has a login endpoint, I authenticate through the API instead of the UI:

ts
setup('authenticate via API', async ({ request }) => {
  const res = await request.post('/api/auth/login', {
    data: { username: process.env.USER_NAME, password: process.env.USER_PASSWORD },
  });
  expect(res.ok()).toBeTruthy();
  await request.storageState({ path: authFile });
});

This is faster and avoids UI flakiness. I keep one separate UI test that covers the actual login page.

6. Token-based apps (JWT in headers or localStorage)

If the token is stored in localStorage or cookies, storageState already captures it.
If the app needs an Authorization header, I fetch the token via API in a setup step or fixture and send it with extraHTTPHeaders, or attach it in an API request context.
For sessionStorage, which storageState does not save, I inject it with page.addInitScript or context.addInitScript.

7. Fixtures for more control

For per-worker accounts, I use a worker-scoped fixture that logs in once per worker with a unique account, which avoids collisions when tests mutate user data in parallel:

ts
export const test = base.extend<{}, { workerStorageState: string }>({
  storageState: ({ workerStorageState }, use) => use(workerStorageState),
  workerStorageState: [async ({ browser }, use) => {
    const id = test.info().parallelIndex;
    const file = `playwright/.auth/${id}.json`;
    // log in with account `user${id}` and save state to file
    await use(file);
  }, { scope: 'worker' }],
});

8. Things I watch for

Session expiry: if tokens expire during a long run, the setup project re-runs on each execution, so I get a fresh session every time. For very long suites, I’d refresh through a fixture.
Shared accounts and parallel runs: if tests change the same user’s data (password, profile, cart), they interfere with each other, so I use separate accounts or create data per test.
MFA/CAPTCHA: I ask for a test environment where they are disabled, or a test account with a fixed OTP or bypass token. I don’t automate CAPTCHA.
Stale auth file: if tests suddenly all fail with login redirects, I delete playwright/.auth and re-run to rule out an expired session.

Why this approach

Faster, since login happens once and not 200 times
More stable, because the UI login isn’t a dependency of every test
Tests stay isolated, because each gets a new context, with just the cookies and storage pre-loaded”

Playwright recommends setup projects for authentication.

# Q : What is the difference between globalSetup and a setup project?
==> Both run once before the main tests, but they differ in how they run. A setup project is a normal Playwright project made of regular tests. globalSetup is a plain function that runs outside the test runner.

1. globalSetup

ts
// global-setup.ts
import { chromium, FullConfig } from '@playwright/test';

async function globalSetup(config: FullConfig) {
  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto('https://app.com/login');
  await page.getByLabel('Username').fill(process.env.USER_NAME!);
  await page.getByLabel('Password').fill(process.env.USER_PASSWORD!);
  await page.getByRole('button', { name: 'Login' }).click();
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
  await browser.close();
}
export default globalSetup;
ts
// playwright.config.ts
globalSetup: require.resolve('./global-setup'),
It’s just a function. I launch the browser and manage its lifecycle myself.
It runs once before all projects, and can return a teardown function, or I can use globalTeardown.
It doesn’t get Playwright’s test fixtures like page, request or context.

2. Setup project

ts
// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/, teardown: 'cleanup' },
  { name: 'cleanup', testMatch: /.*\.teardown\.ts/ },
  {
    name: 'chromium',
    use: { storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup'],
  },
],
ts
// auth.setup.ts
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  // login steps using the normal page fixture
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
It’s a regular test, so it uses fixtures (page, request, custom fixtures), expect, retries and timeouts.
Other projects declare dependencies: ['setup'], so it runs first, and if it fails the dependent projects are skipped.
Teardown is supported via the teardown property, which is a project that runs after all dependents finish.

3. Key differences

				| globalSetup				| Setup project
1. What it is			| Plain function outside the runner	| Regular test in a project
2. Fixtures (page, request)		  | No, I create the browser manually		  | Yes
3. Shows in HTML report		| No					| Yes
4. Trace viewer, screenshots, video| No, unless I wire it up myself		| Yes, same as any test
5. Retries and timeouts		| No					| Yes
6. Run it alone or filter it	| No					| Yes, --project=setup
7. Teardown			| globalTeardown			| teardown project
8. Runs per project/browser	| Once for the whole run			| Once, but can depend on per-project config

4. Why I prefer a setup project

Debuggability: if login fails in CI, I open the trace of the setup test. With globalSetup, a failure is just a stack trace with no report entry, so it’s much harder to see what went wrong.
Fixtures and config reuse: I use the same baseURL, use options and fixtures as the other tests.
Visibility: setup and teardown steps show up in the HTML report and in UI mode.
Dependencies are explicit: it’s clear from the config which projects need the setup.

5. When globalSetup still makes sense

Work that has nothing to do with a browser, for example seeding a database, starting a mock server, or setting up environment variables.
Very simple one-off setup where I don’t need reporting or tracing.
Older projects that already use it and work fine.

Even for those cases, I’d consider a setup project first, since it gives better visibility. One limitation to keep in mind: a setup project runs as part of the test run, so if I use a filter like --grep, I need to make sure the setup project is still included, or I run the dependent project through its dependency chain.

So in short: globalSetup is a bare function with no reporting, and a setup project is a first-class test with traces, fixtures and retries, which is why Playwright recommends it for authentication and I use it by default.”

#====================================================================================================
# Q : How do you run tests in parallel in Playwright, and how do you control it?”
==> “Playwright runs in parallel by default, and I control it at three levels: across files, within a file, and across machines.

1. Default behavior

Playwright starts multiple worker processes, each with its own browser instance.
Test files run in parallel across workers. Tests inside one file run sequentially, in order, in the same worker.
Each test gets its own isolated browser context, so cookies and storage don’t leak between tests.
By default, the worker count is about half the logical CPU cores.

2. Controlling the number of workers

ts
// playwright.config.ts
workers: process.env.CI ? 2 : undefined,   // fewer on CI, default locally
bash
npx playwright test --workers=4
npx playwright test --workers=1     # fully serial, useful for debugging
npx playwright test --workers=50%   # percentage of CPU cores

I keep CI workers conservative, since shared runners have limited CPU and memory, and too many workers cause timeouts that look like flakiness.

3. Parallel tests within a single file

ts
// config: applies to everything
fullyParallel: true,

// or per file/describe
test.describe.configure({ mode: 'parallel' });

With this, individual tests in the same file are distributed across workers. The tests must be fully independent for this to work.

4. Serial mode for dependent tests

ts
test.describe.configure({ mode: 'serial' });

test.describe('checkout flow', () => {
  test('add to cart', async ({ page }) => { /* ... */ });
  test('pay', async ({ page }) => { /* ... */ });
});
Tests run in order in one worker, and if one fails, the rest are skipped.
Serial mode is a last resort. I prefer making tests independent, for example creating the cart through the API in each test. If a serial test fails and retries, the whole group re-runs together.

5. Sharding across machines

bash
npx playwright test --shard=1/4
npx playwright test --shard=2/4

In CI, I run a matrix of shards as separate jobs, then merge the results:

ts
reporter: process.env.CI ? 'blob' : 'html',
bash
npx playwright merge-reports --reporter html ./all-blob-reports

Each shard produces a blob report, and I merge them into one HTML report at the end. With fullyParallel: true, sharding balances better because it splits by test, not by file.

6. Parallelism across projects

Projects (for example chromium, firefox, webkit) also run in parallel. Using dependencies makes one project wait for another, such as the auth setup project, which runs first.

7. What I need to ensure for safe parallel runs

Independent tests: no reliance on execution order or on state left by another test.
Unique test data: a timestamp or UUID in usernames, emails and order names, so parallel workers don’t collide.
Separate accounts when data is mutated: a worker-scoped fixture with testInfo.parallelIndex or workerIndex to pick a different account per worker.
No shared files: if tests write to the same file or a shared DB record, they’ll conflict. I write to worker-specific paths instead.
Resource limits: the app and test environment must handle the concurrent load, otherwise I see random timeouts and 429 or 500 responses.

8. Useful extras

test.describe.parallel and test.describe.serial were older APIs, so I use test.describe.configure({ mode }) now.
--grep @smoke combined with workers lets me run a fast subset in parallel on every PR.
testInfo.workerIndex and parallelIndex are useful for per-worker data and for debugging which worker ran what.
maxFailures or --max-failures=10 stops the run early if too many tests fail, which saves CI time.

Trade-offs I consider

More workers means faster runs, but also more CPU and memory, a higher chance of exposing hidden test dependencies, and more load on the app under test. When I moved a suite to fullyParallel with 4 workers and sharding, the run time dropped significantly, but I first had to fix a few tests that shared test data. If tests fail only in parallel but pass with --workers=1, that’s my signal there’s a data or order dependency.”

# Q : Element is not clickable due to overlay – how will you handle it?
==> First I’d find out what the overlay is, because the right fix depends on it. I never jump straight to force: true.

1. Diagnose first

When Playwright can’t click, it retries and then times out with a log like:

- waiting for element to be visible, enabled and stable
- <div class="loader"> intercepts pointer events
- retrying click action

That message tells me which element is blocking. I confirm it with the trace viewer (the Log tab and the DOM snapshot at the failing step) or by running --debug. The overlay is usually one of these:

a loading spinner or backdrop
a cookie banner, promo popup or chat widget
a sticky header or footer covering the element
an animation or transition that hasn’t finished
a modal from a previous step that was never closed

2. Most common fix: wait for the overlay to go away

ts
await expect(page.locator('.loader')).toBeHidden();
await page.getByRole('button', { name: 'Submit' }).click();

Playwright’s auto-wait already checks that the element can receive events, but being explicit about the spinner makes the test’s intent clear and gives a better failure message. If the spinner is tied to an API call, I wait for the actual response instead:

ts
const responsePromise = page.waitForResponse(r => r.url().includes('/api/data') && r.ok());
await page.getByRole('button', { name: 'Load' }).click();
await responsePromise;
await expect(page.locator('.loader')).toBeHidden();

3. Close or accept the blocking element

For a cookie banner or popup, I dismiss it like a user would:

ts
await page.getByRole('button', { name: 'Accept all' }).click();
await expect(page.locator('#cookie-banner')).toBeHidden();

If it appears randomly, I register a handler that runs automatically whenever it shows up:

ts
await page.addLocatorHandler(
  page.getByRole('dialog', { name: 'Subscribe' }),
  async () => {
    await page.getByRole('button', { name: 'Close' }).click();
  }
);

addLocatorHandler fires when the overlay appears during an action, so I don’t need if checks scattered through the test. For cookie banners, I’d also pre-set the consent cookie in storageState or set it through context.addCookies, so the banner never shows.

4. Sticky header or footer covering the element

Playwright scrolls the element into view, but a fixed header can still cover it. Options:

ts
await locator.scrollIntoViewIfNeeded();
await locator.evaluate(el => el.scrollIntoView({ block: 'center' }));
await locator.click();

Scrolling to the center of the viewport usually clears the header. If it doesn’t, I check whether a more specific locator or a different element is the right target.

5. Animations or transitions

Playwright waits for the element to be stable (not moving), so most animation cases resolve on their own. If a long animation causes timeouts, I either wait for the end state with an assertion, or disable animations in the test environment with a CSS injection:

ts
await page.addStyleTag({ content: '*, *::before, *::after { transition: none !important; animation: none !important; }' });

6. Last resorts (with caution)

ts
await locator.click({ force: true });      // skips actionability checks
await locator.dispatchEvent('click');      // fires the click event directly
await locator.evaluate(el => (el as HTMLElement).click());
force: true bypasses the check that the element is visible, enabled and not covered. The click lands on whatever is at that point, which may be the overlay itself.
A real user could not click that element, so a forced click can hide a genuine bug where the button is permanently covered.
I only use these when I’ve confirmed the overlay is a known, harmless artifact, such as a non-functional test-environment banner, and I add a comment explaining why.

7. Question whether it’s a real defect

If the overlay shouldn’t be there, such as a loader stuck forever or a modal covering the page after the flow completed, the test is correctly catching an application bug. In that case I don’t work around it, I raise a defect with the trace and screenshot.

My order of preference

Read the log or trace to identify the overlay
Wait for the overlay to disappear (assertion or API response)
Close or accept it, or use addLocatorHandler for random popups
Fix scroll or position issues for sticky elements
Disable animations if timing is the issue
force: true only as a documented last resort

Example from my work: a checkout button test failed intermittently with ‘overlay intercepts pointer events’. The trace showed a full-page spinner during a pricing API call. Instead of using force: true, I waited for the pricing response and asserted the spinner was hidden before clicking. The flakiness went away, and a few runs later it also helped us notice that the spinner sometimes stayed on screen for 10 seconds, which we reported as a performance issue.”

Possible next follow-up: “What is the difference between toBeVisible, toBeEnabled and Playwright’s actionability checks?” Short answer: toBeVisible and toBeEnabled are assertions that retry until they pass. Actionability checks are built into actions like click, which automatically wait for the element to be attached, visible, stable, enabled and able to receive events before acting.

# Q : Page is loading slowly – how will you handle synchronization?
==> With a slow page, my rule is to wait for specific conditions the test actually needs, never for a fixed time. I’d also first check whether the slowness is a test problem or an application problem.

1. Rely on auto-waiting and web-first assertions

Most slow-page issues are already handled if I write tests the Playwright way:

ts
await page.goto('/dashboard');
await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
await page.getByRole('button', { name: 'Export' }).click();   // waits for actionability
Actions wait for the element to be attached, visible, stable, enabled and able to receive events.
Web-first assertions (toBeVisible, toHaveText, toHaveCount) retry until they pass or time out.
I avoid one-shot checks like expect(await el.isVisible()), which don’t retry and fail on slow pages.

2. Wait for the right signal, not time

ts
// Bad
await page.waitForTimeout(10000);

// Good: wait for the thing the next step depends on
await expect(page.locator('.spinner')).toBeHidden();
await expect(page.getByTestId('results-table')).toBeVisible();
await page.waitForURL('**/dashboard');

3. Wait on network calls for data-driven pages

If content depends on an API, I wait for that response. I register the wait before the trigger so I don’t miss it:

ts
const responsePromise = page.waitForResponse(
  r => r.url().includes('/api/orders') && r.status() === 200
);
await page.getByRole('button', { name: 'Search' }).click();
await responsePromise;
await expect(page.getByRole('row')).toHaveCount(10);

4. Choose the right load state

ts
await page.goto('/report', { waitUntil: 'domcontentloaded' });
The default load waits for all resources, including images and third-party scripts, which can be slow and irrelevant to my test.
domcontentloaded plus an assertion on the element I need is usually faster and more reliable.
I avoid networkidle as a default because it’s discouraged for reliability. Pages with polling, analytics or websockets may never go idle. I use it only for specific pages where it’s proven to work.

5. Increase timeouts selectively

ts
// config: sensible defaults
timeout: 60_000,
expect: { timeout: 10_000 },
use: { actionTimeout: 15_000, navigationTimeout: 30_000 },

// only for a legitimately slow step
await expect(page.getByText('Report ready')).toBeVisible({ timeout: 45_000 });
test.slow();   // triples the timeout for one known-slow test

I don’t raise the global timeout to hide slowness. That makes real failures slower to detect and masks performance regressions.

4b. Poll for backend-driven completion

For long-running processes such as report generation:

ts
await expect.poll(async () => {
  const res = await request.get('/api/reports/42');
  return (await res.json()).status;
}, { timeout: 60_000, intervals: [1000, 2000, 5000] }).toBe('COMPLETED');

6. Speed up what I can control

Use storageState so login isn’t repeated.
Create test data through the API instead of long UI flows.
Block unnecessary heavy resources if they aren’t part of the test:
ts
await page.route('**/*.{png,jpg,jpeg,gif,svg}', route => route.abort());
await page.route('**/analytics/**', route => route.abort());
Mock slow third-party dependencies with page.route() and route.fulfill().

7. Diagnose whether it’s a test issue or an app issue

Open the trace and check the Network tab for slow or failing requests.
Compare local and CI timings. CI runners are often slower, and too many workers can starve the browser, so I may reduce workers on CI.
If the application genuinely takes 20 seconds to load, that’s a performance defect to report, not something to hide with longer waits.
I can assert on performance in a key flow, for example measure with performance.timing or check that a response arrives within an expected threshold.

8. Handling intermittent slowness with retries

retries: 2 on CI gives a safety net, but I treat a test that needs retries as flaky and investigate it, rather than treating retries as the fix.

My order of preference

Auto-waiting and web-first assertions
Wait for a specific element, URL or network response
Use domcontentloaded and avoid networkidle
Poll for backend-driven states
Extend timeout for the specific slow step only
Reduce load: storage state, API data setup, blocking or mocking heavy calls

Example from my work: a reports page took up to 15 seconds under CI load, and tests failed with timeouts on a waitForTimeout(5000) followed by a table check. I replaced it with waitForResponse on the reports API plus toHaveCount on the table rows, and set a 30-second timeout for just that assertion. The tests became stable, and the trace data also showed the API itself was slow, which we raised with the backend team.”

Possible next follow-up: “What is the difference between waitForLoadState, waitForSelector and waitForURL?” Short answer: waitForLoadState waits for a page lifecycle state (load, domcontentloaded, networkidle), waitForSelector is the older element wait that has been replaced by locat

# Q : A table contains 100 rows, and you need to find a particular user and click Edit. How would you implement it?
==> As an Automation Engineer with 3.6 years of experience in Playwright TypeScript, I would handle this using dynamic locators and row-based filtering rather than using a hardcoded row index.

My approach is to identify the row containing the particular user's unique information, such as username, email, or user ID, and then click the Edit button within that specific row.
1. Recommended approach: filter({ hasText })
Suppose we have a table containing 100 users:
User ID	Name	Email	Action
101	John	john@gmail.com	Edit
102	David	david@gmail.com	Edit
103	Smith	smith@gmail.com	Edit
104	Uzma	uzma@gmail.com	Edit

I want to find Uzma and click her Edit button.
Playwright TypeScript code
import { test, expect } from '@playwright/test';

test('Find user and click Edit', async ({ page }) => {

    await page.goto('https://example.com/users');

    const userName = 'Uzma';

    // Locate the particular row
    const userRow = page.locator('table tbody tr')
        .filter({ hasText: userName });

    // Verify that the row exists
    await expect(userRow).toHaveCount(1);

    // Click Edit button within that row
    await userRow.getByRole('button', {
        name: 'Edit'
    }).click();

});


Explanation
Step 1: Locate all table rows
const rows = page.locator('table tbody tr');


This identifies all rows in the table.

Step 2: Find the particular user
const userRow = rows.filter({
    hasText: 'Uzma'
});


filter({ hasText }) filters the rows and returns the row containing the specified text.

Step 3: Verify the matching row
await expect(userRow).toHaveCount(1);


This ensures that exactly one row matches the user.

Step 4: Click Edit inside that row
await userRow.getByRole('button', {
    name: 'Edit'
}).click();


This is important because it clicks the Edit button belonging to the matching row, not an Edit button elsewhere in the table.

2. Alternative approach: Using getByRole() with filter()
If the application uses accessible table markup, I prefer semantic locators.
const userRow = page.getByRole('row', {
    name: /Uzma/
});

await expect(userRow).toHaveCount(1);

await userRow.getByRole('button', {
    name: 'Edit'
}).click();


This is more readable and follows Playwright's recommended locator strategy.

3. Alternative approach: Find user using email
Sometimes multiple users have the same name. In that situation, I prefer using a unique identifier such as email or user ID.
const userRow = page.locator('table tbody tr')
    .filter({
        hasText: 'uzma@gmail.com'
    });

await expect(userRow).toHaveCount(1);

await userRow.locator('button.edit-btn').click();


Why? Usernames may not be unique, but email addresses or user IDs are generally unique.

4. Alternative approach: Using locator() and nth()
If the table does not have proper semantic markup, I can use XPath or CSS locators.
const userRow = page.locator(
    "//tr[td[normalize-space()='Uzma']]"
);

await expect(userRow).toHaveCount(1);

await userRow.locator("//button[text()='Edit']").click();


Note: For a locator scoped to userRow, use a relative XPath beginning with .// if using XPath:
await userRow.locator(".//button[normalize-space()='Edit']").click();


I would avoid nth(5) or other hardcoded indexes because row positions can change when sorting, filtering, or pagination is applied.

5. What if the table has pagination or 1000 records?
If the user is not present on the current page, I would handle pagination.
async function findUserAndEdit(
    page: import('@playwright/test').Page,
    email: string
) {

    while (true) {

        const userRow = page.locator('table tbody tr')
            .filter({ hasText: email });

        if (await userRow.count() === 1) {

            await userRow.getByRole('button', {
                name: 'Edit'
            }).click();

            return;
        }

        const nextButton = page.getByRole('button', {
            name: 'Next'
        });

        if (
            await nextButton.count() === 0 ||
            !(await nextButton.isEnabled())
        ) {
            throw new Error(`User not found: ${email}`);
        }

        await nextButton.click();
    }
}


This example assumes the application updates the table after each Next click. In a production framework, I would also wait for a reliable pagination or loading-state change before checking the next page.

6. What if there are multiple Edit buttons?
Suppose every row has an Edit button. If I write:
await page.getByRole('button', {
    name: 'Edit'
}).first().click();


It will click the first Edit button, which might belong to the wrong user.

Instead:
const userRow = page.getByRole('row', {
    name: /uzma@gmail\.com/
});

await userRow.getByRole('button', {
    name: 'Edit'
}).click();


This scopes the action to the correct user.

Interview-ready answer
"In my Playwright framework, I handle this using dynamic locators rather than hardcoded row indexes.

First, I locate all table rows using locator('table tbody tr'). Then I use filter({ hasText: username }) to identify the row containing the particular user.

After identifying the row, I verify that exactly one matching row exists using toHaveCount(1). Finally, I scope the Edit button locator to that row and click it.

If multiple users have the same name, I use a unique identifier such as email or user ID. If the table has pagination, I iterate through the pages until I find the required user.

This approach makes the automation reusable, reliable, and independent of the user's position in the table."

Best practice
 Always locate the user first, scope the Edit button to that user's row, and verify the matching row is unique before clicking

# Q :  An element takes 5–10 seconds to appear randomly. How would you handle this 
==> As an Automation Engineer with 3.6 years of experience in Playwright TypeScript, I would handle this using Playwright's auto-waiting mechanism and web-first assertions, rather than using hardcoded waits like waitForTimeout().

If an element takes 5–10 seconds to appear randomly, it could be due to API response time, network latency, asynchronous JavaScript execution, or backend processing.

My approach is to wait for the actual condition that indicates the element is ready.

1. Recommended approach: Auto-waiting
Playwright automatically waits for elements to become actionable before performing actions such as click, fill, and check.
import { test, expect } from '@playwright/test';

test('Handle randomly appearing element', async ({ page }) => {

    await page.goto('https://example.com');

    await page.getByRole('button', {
        name: 'Submit'
    }).click();

    await page.getByText('Success').click();

});
For example, if the Success element appears after 5–10 seconds, Playwright automatically waits for it to become actionable, subject to the configured timeout.
However, if I only need to verify that an element appears, I prefer an explicit web-first assertion.

2. Use expect().toBeVisible() with timeout
This is my preferred approach when an element appears asynchronously.
test('Wait for element visibility', async ({ page }) => {

    await page.goto('https://example.com');

    await expect(
        page.locator('#success-message')
    ).toBeVisible({
        timeout: 15000
    });

});

How it works:
1. Playwright checks whether the element is visible.
2. If it is not visible, Playwright retries the assertion.
3. It continues checking until the element becomes visible.
4. If the element does not appear within 15 seconds, the test fails.
I use a timeout of 15 seconds here because the expected delay is 5–10 seconds, with some additional buffer.

3. Use locator.waitFor()
If I specifically need to wait for an element to reach a particular state before performing an action, I can use waitFor().

test('Wait for element before clicking', async ({ page }) => {

    await page.goto('https://example.com');

    const submitButton = page.locator('#submit');

    await submitButton.waitFor({
        state: 'visible',
        timeout: 15000
    });

    await submitButton.click();

});


Available states:
State		| Meaning
attached	| Element is present in the DOM
detached	| Element is removed from the DOM
visible		| Element is visible
hidden		| Element is hidden or detached

Important: waitFor({ state: 'visible' }) only ensures visibility. The subsequent click still performs Playwright's actionability checks.

4. What if the element appears after an API response?
Sometimes the UI element appears only after an API request completes.

In that situation, I can wait for the API response instead of waiting blindly for the UI.
test('Wait for API response before validating UI', async ({ page }) => {

    await page.goto('https://example.com/dashboard');

    const responsePromise = page.waitForResponse(response =>
        response.url().includes('/api/users') &&
        response.status() === 200
    );

    await page.getByRole('button', {
        name: 'Load Users'
    }).click();

    await responsePromise;

    await expect(
        page.locator('#user-table')
    ).toBeVisible();

});

Here, I wait for the relevant API response and then verify that the user table is visible.
This is more reliable than waiting for an arbitrary number of seconds.

5. What if the element appears randomly because of network delays?
If I suspect network instability, I investigate the request and response timing.
page.on('requestfailed', request => {

    console.log(
        'Failed Request:',
        request.url(),
        request.failure()?.errorText
    );

});

page.on('response', response => {

    console.log(
        'Response:',
        response.status(),
        response.url()
    );

});

I also use Playwright Trace Viewer to inspect:
- API request and response timing.
- DOM snapshots.
- Screenshots.
- Failed actions.
- Network activity.
This helps me identify whether the delay is caused by the frontend, backend, or network.
6. What if the element is visible but not clickable?
Sometimes an element appears in the DOM but another element overlays it, or an animation is still running.

I use:
const button = page.getByRole('button', {
    name: 'Submit'
});

await expect(button).toBeVisible();

await expect(button).toBeEnabled();

await button.click({
    timeout: 15000
});


Playwright's click action checks important actionability conditions:
- Element is visible.
- Element is stable.
- Element receives pointer events.
- Element is enabled.
If clicking still fails, I inspect overlays, animations, and the element's actual state instead of immediately using { force: true }.
7. What I avoid: waitForTimeout()
I would avoid this approach:
await page.waitForTimeout(10000);

await page.locator('#success-message').click();

Why do I avoid it?
- If the element appears in 2 seconds, the remaining 8 seconds are wasted.
- If it appears after 12 seconds, the test still fails.
- It increases overall execution time.
- It does not identify the actual reason for the delay.
I use fixed waits only when there is a specific reason to pause, such as testing a timed behavior.
8. Important: Configure global and assertion timeouts
In my Playwright framework, I configure reasonable timeout values centrally.
// playwright.config.ts

import { defineConfig } from '@playwright/test';

export default defineConfig({

    timeout: 60000,

    expect: {
        timeout: 15000
    },

    use: {
        actionTimeout: 15000,
        navigationTimeout: 30000
    }

});


These settings serve different purposes:
Configuration		| Purpose
1. timeout		| Maximum duration for an individual test
2. expect.timeout	| Maximum duration for auto-retrying assertions
3. actionTimeout	| Maximum duration for actions such as click and fill
4. navigationTimeout	| Maximum duration for navigation operations

Note that the test timeout includes the time spent in its actions and assertions.

Interview-ready answer
"If an element takes 5–10 seconds to appear randomly, I don't use hardcoded waits like waitForTimeout(10000).

First, I identify why the element is delayed, whether it is due to an API response, network latency, or asynchronous rendering.

For normal UI interactions, I rely on Playwright's built-in auto-waiting. If I need to verify that an element appears, I use web-first assertions such as expect(locator).toBeVisible({ timeout: 15000 }).

If the element depends on an API call, I use page.waitForResponse() to synchronize with the relevant API response and then validate the UI.

I also use Trace Viewer, screenshots, and network logs to investigate intermittent failures.

My goal is to synchronize the test with the actual application behavior rather than introducing unnecessary fixed delays."

Best practice
 Prefer condition-based waiting over time-based waiting. It improves test stability and reduces unnecessary execution time.

# Q : An element is inside a shadow DOM. How would you automate it?
==> As an Automation Engineer with 3.6 years of experience in Playwright TypeScript, I handle Shadow DOM elements using Playwright's built-in locator support.

Unlike Selenium, where we generally need to switch into a Shadow Root using getShadowRoot(), Playwright can automatically pierce open Shadow DOM elements using standard CSS locators.
1. What is Shadow DOM?
Shadow DOM is a web technology used to encapsulate HTML, CSS, and JavaScript inside a component.

For example, a web application might contain:
<user-login>
    #shadow-root (open)
        <input id="username">
        <input id="password">
        <button id="login">Login</button>
</user-login>


Here, the username, password, and login button are inside the Shadow DOM of the user-login component.
2. How do you automate Shadow DOM in Playwright?
Playwright's CSS locators automatically pierce open Shadow DOM boundaries.

We don't need to explicitly access the shadow root.
Example 1: Locate elements inside Shadow DOM
import { test, expect } from '@playwright/test';

test('Handle Shadow DOM elements', async ({ page }) => {

    await page.goto('https://example.com');

    // Locate username inside Shadow DOM
    await page.locator('user-login #username')
        .fill('testuser');

    // Locate password inside Shadow DOM
    await page.locator('user-login #password')
        .fill('password123');

    // Click login button
    await page.locator('user-login #login')
        .click();

});


Explanation:
- user-login identifies the custom web component.
- #username identifies the username input inside its Shadow DOM.
- Playwright automatically traverses the open Shadow DOM.
- We can interact with the elements using normal locator methods.
3. How do you handle nested Shadow DOM?
Sometimes an element is inside multiple Shadow DOM components.

Example:
<app-container>
    #shadow-root (open)

    <user-login>
        #shadow-root (open)

        <input id="username">
        <button id="login">Login</button>

    </user-login>
</app-container>


We can use:
const username = page.locator(
    'app-container user-login #username'
);

await username.fill('testuser');

const loginButton = page.locator(
    'app-container user-login #login'
);

await loginButton.click();


Playwright automatically pierces both open Shadow DOM boundaries.
4. Can we use XPath inside Shadow DOM?
No. Playwright XPath locators do not pierce Shadow DOM boundaries.

For example, this XPath approach will not work when the element is inside a Shadow DOM:
// Not supported for crossing Shadow DOM boundaries
await page.locator(
    '//user-login//input[@id="username"]'
).fill('testuser');


Instead, I use CSS locators or Playwright's other supported locator strategies.
await page.locator(
    'user-login #username'
).fill('testuser');


5. What if the Shadow DOM is closed?
This is an important interview question.

There are two types of Shadow DOM:
Type			| Description					| Playwright support
Open Shadow DOM		| Shadow root is accessible through the component	| Supported
Closed Shadow DOM		| Shadow root is not accessible through the standard DOM APIs	 | Not supported by normal Playwright locators

Example:
class LoginComponent extends HTMLElement {

    constructor() {
        super();

        const shadow = this.attachShadow({
            mode: 'closed'
        });

        shadow.innerHTML = `
            <input id="username">
        `;
    }

}
Here, the Shadow DOM is closed.

Playwright's normal locators cannot access elements inside it.

How would I handle it?
1. Request developers to expose a test-friendly interface or use an open Shadow DOM if appropriate.
2. Interact through publicly exposed component APIs.
3. Validate behavior through accessible UI or backend APIs.
4. Avoid changing application internals just to make tests pass.
Playwright also documents a special limitation: closed Shadow Roots are not supported by its normal locators.
6. What about iframe containing Shadow DOM?
This is another commonly asked scenario.

Suppose an application contains an iframe, and inside that iframe there is a Shadow DOM component.

In this case, I first locate the iframe using frameLocator() and then locate the Shadow DOM element inside it.
const username = page
    .frameLocator('#login-frame')
    .locator('user-login #username');

await username.fill('testuser');


Here:
- frameLocator() enters the iframe's document.
- .locator() locates the custom element and its open Shadow DOM child.
- Playwright automatically pierces the open Shadow DOM.

7. Selenium vs Playwright: Shadow DOM handling
Feature			| Selenium Java					| Playwright TypeScript
Open Shadow DOM		| Explicit Shadow Root access generally required	| Automatically supported
Closed Shadow DOM		| Not accessible through standard Shadow Root API	| Not supported by normal locators
Nested Shadow DOM		| Multiple getShadowRoot() calls			| CSS locator can pierce nested open roots
XPath			| Cannot directly cross Shadow DOM boundaries	| Cannot pierce Shadow DOM
Iframe + Shadow DOM	| Switch frame, then access Shadow Root		| frameLocator() followed by locator

Selenium example for comparison
WebElement shadowHost = driver.findElement(
    By.cssSelector("user-login")
);

SearchContext shadowRoot = shadowHost.getShadowRoot();

WebElement username = shadowRoot.findElement(
    By.cssSelector("#username")
);

username.sendKeys("testuser");

Interview-ready answer
"In Playwright, handling Shadow DOM is straightforward because Playwright automatically pierces open Shadow DOM boundaries when using supported locators.

For example, if I have a custom web component called user-login containing username and password fields inside its open Shadow DOM, I can directly use page.locator('user-login #username') and interact with it without explicitly accessing the Shadow Root.

For nested Shadow DOM, I can chain CSS locators, and Playwright handles the open Shadow DOM boundaries automatically.

One limitation is that XPath locators do not pierce Shadow DOM. Also, closed Shadow DOM is not supported by normal Playwright locators.

If an iframe contains a Shadow DOM, I first use frameLocator() to access the iframe and then locate the element inside the open Shadow DOM.

Compared with Selenium, Playwright makes Shadow DOM automation easier because it handles open Shadow DOM traversal automatically."

Key point to remember: Open Shadow DOM → directly use Playwright locators. Closed Shadow DOM → normal Playwright locators cannot access it.

# Q : How would you handle an element whose position changes dynamically on every execution?
==> As an Automation Engineer with 3.6 years of experience in Playwright TypeScript, I would handle dynamically changing element positions using stable attributes, dynamic locators, and relationship-based locators rather than relying on fixed indexes or coordinates.

For example, suppose a table contains 100 users, and the Edit button for a particular user appears at a different row position every time because the application sorts the records dynamically.

I would identify the user using a unique attribute, locate the corresponding row, and then click the Edit button within that row.
1. Approach: Use unique attributes
Suppose the element has a dynamically changing position but a stable ID or test attribute.
<button data-testid="edit-user">Edit</button>


Playwright code:
await page.getByTestId('edit-user').click();


This is the simplest approach because the locator does not depend on the element's position.
2. Approach: Use text-based locators
If the element has dynamic positioning but stable visible text, I use getByText() or getByRole().
await page.getByRole('button', {
    name: 'Submit'
}).click();


Even if the button moves from the top to the bottom of the page, Playwright can locate it using its accessible role and name.
3. Approach: Use relationship-based locators
Consider a table where user records change their positions on every execution.
User ID	Name	Action
103	David	Edit
101	John	Edit
105	Uzma	Edit
102	Smith	Edit

I want to click Edit for Uzma.
import { test, expect } from '@playwright/test';

test('Click Edit for dynamically positioned user', async ({ page }) => {

    await page.goto('/users');

    const userRow = page.locator('table tbody tr')
        .filter({ hasText: 'uzma@gmail.com' });

    await expect(userRow).toHaveCount(1);

    await userRow.getByRole('button', {
        name: 'Edit'
    }).click();

});


Why this approach?
- It doesn't depend on row position.
- It works even if the table is sorted differently.
- It identifies the correct user's Edit button.
- It makes the automation reusable.
4. Approach: Handle dynamically generated IDs
Sometimes applications generate dynamic IDs.

For example:
<input id="input-12345">
<input id="input-67890">


If the ID changes on every execution, I avoid using the complete ID.

Instead, I identify stable attributes.
await page.locator('input[name="username"]')
    .fill('testuser');


If there is a stable prefix:
await page.locator('input[id^="input-"]')
    .fill('testuser');


CSS attribute selectors:
Selector	Meaning
[id^="input-"]	ID starts with input-
[id$="-field"]	ID ends with -field
[id*="username"]	ID contains username

I would verify that the locator uniquely identifies the intended element before interacting with it.
5. Approach: Handle dynamically positioned elements using CSS relationships

# Q : An element is present but not visible. Which wait would you use and why?
==> As an Automation Engineer with 3.6 years of experience in Playwright TypeScript, first I would understand whether the element is present in the DOM but hidden, or whether it is present but not yet displayed because of some application condition.

If an element is present in the DOM but not visible, I would use:
await locator.waitFor({
    state: 'visible',
    timeout: 15000
});


However, the correct wait depends on the expected behavior.
1. Difference between attached and visible
Consider the following HTML:

    Login Successful
</div>


Here, the element exists in the DOM, but it is not visible to the user.

Playwright provides four locator wait states:
State	Meaning
attached	Element exists in the DOM
visible	Element exists and is visible
hidden	Element is hidden or detached
detached	Element is removed from the DOM

2. If the element is present but hidden, and I expect it to become visible
I use waitFor({ state: 'visible' }).
import { test, expect } from '@playwright/test';

test('Wait for hidden element to become visible', async ({ page }) => {

    await page.goto('https://example.com');

    // Wait until element becomes visible
    await successMessage.waitFor({
        state: 'visible',
        timeout: 15000
    });

    // Validate the message
    await expect(successMessage).toHaveText('Login Successful');

});


How it works:
1. Playwright checks whether the element exists.
2. If it exists but is hidden, Playwright continues waiting.
3. Once it becomes visible, execution continues.
4. If it remains hidden for 15 seconds, the test fails.
3. Alternative: Use expect().toBeVisible()

await expect(
    page.locator('#success-message')
).toBeVisible({
    timeout: 15000
});


Difference:
- locator.waitFor() waits for a locator to reach a particular state.
- expect(locator).toBeVisible() waits and asserts that the element is visible.
For validation-oriented test cases, I prefer web-first assertions because they automatically retry until the assertion passes or times out.
4. What if the element is hidden initially and becomes visible after clicking a button?

    name: 'Show Details'
}).click();

});


Here, I perform the action that should make the element visible and then verify the expected UI behavior.

# Q : You have AJAX calls that don't refresh the page. How would you wait for the operation to complete?
==> As a Playwright TypeScript Automation Engineer with 3.6 years of experience, I handle AJAX calls using page.waitForResponse(), page.waitForRequest(), and Playwright's auto-waiting assertions, depending on what I need to validate.

Since AJAX calls update only part of the page without a full page reload, I don't wait for navigation. Instead, I wait for the relevant API response or the expected UI change.
1. Using page.waitForResponse() – Preferred approach
I use this when I want to ensure that a particular API call has completed successfully.

Example: Clicking Search triggers an AJAX request.
import { test, expect } from '@playwright/test';

test('Wait for AJAX response', async ({ page }) => {

    await page.goto('https://example.com');

    // Start waiting for the API response
    const responsePromise = page.waitForResponse(response =>
        response.url().includes('/api/users') &&
        response.request().method() === 'GET' &&
        response.status() === 200
    );

    // Trigger AJAX request
    await page.getByRole('button', { name: 'Search' }).click();

    // Wait for API response
    const response = await responsePromise;

    console.log('API Status:', response.status());

    // Validate updated UI
    await expect(page.locator('#user-table')).toBeVisible();
});


How it works:
1. I register waitForResponse() before clicking the button.
2. I trigger the action that sends the AJAX request.
3. Playwright waits until the matching response is received.
4. I validate the response status and the updated UI.
Important: I register the response listener before triggering the action to avoid missing a fast response.
2. Using page.waitForRequest()
I use this when I only need to verify that the browser has sent a particular AJAX request.
const requestPromise = page.waitForRequest(request =>
    request.url().includes('/api/users') &&
    request.method() === 'POST'
);

await page.getByRole('button', { name: 'Create User' }).click();

const request = await requestPromise;

console.log('Request URL:', request.url());
console.log('Request Method:', request.method());


Difference: waitForRequest() confirms that the request was sent, whereas waitForResponse() waits for the corresponding response.
3. Using Playwright auto-waiting assertions
Sometimes I don't need to validate the API response directly. I only need to verify that the AJAX operation updated the UI.

In that case, I use web-first assertions.
await page.getByRole('button', { name: 'Load Users' }).click();

await expect(page.locator('#loading')).toBeHidden();

await expect(page.locator('#user-table tbody tr'))
    .toHaveCount(5);


Playwright automatically retries the assertions until the expected condition is met or the timeout is reached.
4. Handling AJAX calls with loading indicators
For applications that display a loader while processing an AJAX request, I wait for the loader to disappear and then verify the updated data.
await page.getByRole('button', { name: 'Submit' }).click();

// Wait until loader disappears
await expect(page.locator('.loader')).toBeHidden();

// Verify success message
await expect(page.getByText('Data saved successfully'))
    .toBeVisible();


This is useful for search results, form submissions, dashboards, and dynamically loaded tables.
5. Handling multiple AJAX calls
If clicking a button triggers multiple API calls, I can wait for all expected responses.
const usersPromise = page.waitForResponse(response =>
    response.url().includes('/api/users') &&
    response.status() === 200
);

    response.url().includes('/api/roles') &&
    response.status() === 200
);

const [usersResponse, rolesResponse] = await Promise.all([
    usersPromise,
    rolesPromise
]);

expect(rolesResponse.ok()).toBeTruthy();


Which approach would I choose?
Method		    | When I use it
waitForResponse()		| Wait for a specific API response
waitForRequest()		| Verify that an AJAX request was triggered
expect()				| Wait for the expected UI update
Loader disappearance | Wait until background processing finishes
Promise.all()			| Wait for multiple independent API responses

What I avoid
I avoid using fixed waits such as:   await page.waitForTimeout(5000);

This is unreliable because the AJAX operation may complete in 500 ms or take 8 seconds. A fixed wait either wastes execution time or causes flaky tests.

# Q : Clicking a link opens a new browser tab. How would you switch to the new tab?
==> o switch to a new tab in Playwright with TypeScript, you must listen for the page or popup event before or during the click action, which yields a new Page object representing the new tab. Unlike other frameworks, Playwright does not require you to manually manage window handles by index—you simply interact with the new Page object directly.
Here are the two standard patterns to achieve this:

1. The Promise.all Pattern (Recommended)

This approach triggers the event listener and the click action concurrently, safely capturing the event without race conditions.
typescript
import { test, expect } from '@playwright/test';

test('Switch to new tab using Promise.all', async ({ context, page }) => {
  await page.goto('https://example.com');

  // Start waiting for the new page event and trigger the click simultaneously
  const [newPage] = await Promise.all([
    context.waitForEvent('page'),             // 1. Listen for the new tab event
    page.getByText('Open New Tab').click(),   // 2. Perform the action that opens it
  ]);

  // Optional: Wait for the new tab to completely finish loading
  await newPage.waitForLoadState(); 

  // You are now interacting with the new tab
  await expect(newPage).toHaveURL('https://example.com');
  await newPage.getByRole('button', { name: 'Submit' }).click();

  // Switch back to the original tab by just using the original 'page' object
  await page.bringToFront(); 
});
Use code with caution.

2. The Defer Promise Pattern

Alternatively, you can assign the event promise to a variable before running the click step.
typescript
test('Switch to new tab using deferred promise', async ({ context, page }) => {
  await page.goto('https://example.com');

  // Set up the listener first (Do NOT use 'await' here)
  const pagePromise = context.waitForEvent('page');

  // Click the link that triggers the tab

  // Await the promise to resolve into the new page object
  const newPage = await pagePromise;

  // Interact with the new tab
  console.log(await newPage.title());
});
Use code with caution.

• context.waitForEvent('page'): Listens context-wide for any new page or tab creation. You can also use page.waitForEvent('popup') if the new tab is triggered strictly as a popup window.
• newPage.bringToFront(): Brings the tab into active view. While Playwright commands work on newPage in the background without it, this is required if your test behavior depends on element visibility triggers or if you are running in non-headless mode and want to watch the execution.

# Q : There are three browser windows open. How would you switch to a specific window?
==> To switch to a specific browser window out of multiple open ones in Playwright, you do not use indexes or click commands. Instead, you find the window matching a specific property (like its URL or title) within the browser context's array of open pages.
Every time a new window or tab opens, Playwright tracks it inside context.pages().
Here is how you search through all open windows and switch your target interaction to the correct one:

The "Find by Title or URL" Pattern

Instead of relying on the order the windows opened, iterate through context.pages() to locate your target window.
typescript
import { test, expect } from '@playwright/test';

test('Switch to a specific window out of multiple open windows', async ({ context, page }) => {
  await page.goto('https://example.com');

  // ... actions that trigger two more windows to open ...

  // 1. Get an array of all currently open windows/tabs
  const allWindows = context.pages(); 
  console.log(`Total open windows: ${allWindows.length}`); // Outputs: 3

  // 2. Define a variable to hold our target window
  let targetWindow;

  // 3. Loop through them to find the one matching your criteria (e.g., Title or URL)
  for (const win of allWindows) {
    const title = await win.title();
    if (title === 'Target Dashboard Window') {
      targetWindow = win;
      break;
    }
  }

  // 4. Ensure the window was actually found
  if (!targetWindow) {
    throw new Error('Could not find the specific target window!');
  }

  // 5. Optional: Bring it visually to the front (useful for non-headless debugging)
  await targetWindow.bringToFront();

  // 6. Interact with the specific window safely
  await expect(targetWindow.locator('h1')).toHaveText('Welcome to the Dashboard');
  await targetWindow.getByRole('button', { name: 'Logout' }).click();
});
Use code with caution.

Alternative: A Cleaner Functional Approach

If you prefer clean TypeScript, you can replace the for...of loop with an asynchronous find strategy:
typescript
const allWindows = context.pages();

// Find the page where the URL contains a specific path
const targetWindow = allWindows.find(win => win.url().includes('/settings'));

if (targetWindow) {
  await targetWindow.bringToFront();
  // Interact here
}
Use code with caution.

Key Things to Remember

• No Window Handles: Unlike Selenium or WebDriverIO, you don't need to pass string tokens or switch context modes globally. Whichever Page object variable you call commands on (page, targetWindow, popup) is the window Playwright interacts with.
• Race Conditions: If the windows are opened dynamically via clicks right before you switch, make sure to use await page.waitForTimeout(1000) or wait for the specific page events to resolve first so that context.pages() accurately reflects all 3 windows.

# Q : After completing a test in a child window, how would you return to the parent window?
==> o return to the parent window in Playwright, you do not need to execute an explicit "switch back" command. Because Playwright isolates pages into distinct variables, you simply call your next commands directly on your original page object variable while using bringToFront() if you need to visually focus it.
Here is the cleanest way to finish your work in a child window, close it, and instantly resume testing on the parent page:

The Return Pattern

typescript
import { test, expect } from '@playwright/test';

test('Interact with child window and return to parent', async ({ context, page }) => {
  // 'page' is your parent window
  await page.goto('https://example.com');

  // 1. Open the child window
  const [childWindow] = await Promise.all([
    context.waitForEvent('page'),
    page.getByText('Open Child Window').click(),
  ]);
  await childWindow.waitForLoadState();

  // 2. Perform your tests inside the child window
  await expect(childWindow.locator('h1')).toHaveText('Child Window Dashboard');
  await childWindow.getByRole('button', { name: 'Save Changes' }).click();

  // 3. Close the child window (Best practice to free up browser memory)
  await childWindow.close();

  // 4. Return to the parent window
  // If running in headed mode, this brings the parent window back into visual focus
  await page.bringToFront(); 

  // 5. Instantly resume interacting with the parent window
  await expect(page).toHaveURL('https://example.com');
  await page.getByRole('link', { name: 'Next Step' }).click();
});
Use code with caution.

Why it Works This Way

Unlike legacy frameworks like Selenium (which use a global driver state requiring driver.switchTo().window(parentHandle)), Playwright is object-driven.
• The variable page always points to your parent window.
• The variable childWindow points to the new popup.
• Even if childWindow is currently open and active on the screen, running await page.click(...) will automatically execute against the parent window in the background.

# Q : How would you automate file download validation using Playwright typescript?
==> To automate file download validation in Playwright with TypeScript, you must handle the download asynchronously by listening for the download event before or during the trigger action.
Playwright manages downloads by caching them in a temporary directory. You can then access the download object to validate the filename, save it to a permanent directory, or read its contents.
Here are the most reliable patterns to automate this process.

1. The Standard Promise.all Download Pattern

This approach handles the download event and the user action (like a button click) concurrently to prevent race conditions.
typescript
import { test, expect } from '@playwright/test';
import * as path from 'path';
import * as fs from 'fs';

test('Download a file and validate its properties', async ({ page }) => {
  await page.goto('https://example.com');

  // 1. Start waiting for the download event and trigger the click simultaneously
  const [download] = await Promise.all([
    page.waitForEvent('download'),

  // 3. Define where you want to save the file permanently
  const downloadPath = path.join(__dirname, '../downloads', filename);

  // 4. Save the file from the temporary cache to your path
  await download.saveAs(downloadPath);

  // 5. Assert that the file physically exists on the disk
  expect(fs.existsSync(downloadPath)).toBeTruthy();
});

The Nested Frame Locator Pattern

• Main Page
	• iframe#outer-frame
		• iframe[name="inner-frame"]
			• <button id="submit-btn">Click Me</button>

typescript
import { test, expect } from '@playwright/test';

test('Interact with an element inside nested iframes', async ({ page }) => {

  // 5. To go back to the main page, just use the original 'page' object again

# Q : How would you handle confirmation and prompt alerts?
==> To handle confirmation and prompt alerts in Playwright with TypeScript, you must register a page.on('dialog') listener before the user action triggers the alert.
Inside the listener, you can check the type of dialog (dialog.type()), validate its text content, and then decide whether to approve it (dialog.accept()) or cancel it (dialog.dismiss()).
Here is how you handle both scenarios:

1. Handling Confirmation Dialogs (OK / Cancel)

Confirmation alerts give the user two choices. You can either use .accept() to click OK or .dismiss() to click Cancel.
typescript
import { test, expect } from '@playwright/test';

test('Handle a Confirmation Alert (Accept and Dismiss)', async ({ page }) => {
  await page.goto('https://example.com');

  // 1. Setup the listener to CLICK OK (Accept)
  page.on('dialog', async (dialog) => {
    // Optional check: Ensure it is a confirmation type
    if (dialog.type() === 'confirm') {
      expect(dialog.message()).toBe('Are you sure you want to delete this file?');
      await dialog.accept(); // Clicks "OK"
    }
  });

  // Trigger the confirmation alert
  await page.getByRole('button', { name: 'Delete File' }).click();
  await expect(page.getByText('File successfully deleted')).toBeVisible();

  // -------------------------------------------------------------
  // 2. Setup a clean listener to CLICK CANCEL (Dismiss)
  // Remove the previous listener first if you are doing this in the same test
  page.removeAllListeners('dialog');

  page.on('dialog', async (dialog) => {
    expect(dialog.message()).toBe('Are you sure you want to delete this file?');
    await dialog.dismiss(); // Clicks "Cancel"
  });

  // Trigger the confirmation alert again
  await page.getByRole('button', { name: 'Delete File' }).click();
  await expect(page.getByText('File successfully deleted')).not.toBeVisible();
});
Use code with caution.

2. Handling Prompt Dialogs (Entering Text)

Prompt alerts ask the user to type text into an input field. To simulate a user typing and clicking OK, pass your text string directly into dialog.accept('your text here').
typescript
test('Handle a Prompt Alert by entering text', async ({ page }) => {
  await page.goto('https://example.com');

• Playwright's default behavior: If you do not register a listener, Playwright will automatically dismiss all standard confirmation and prompt dialogs in the background so your code doesn't hang. # Q : What would you do if an alert appears randomly and not on every execution?
==> If an alert appears randomly and unpredictably, you cannot rely on sequential, step-by-step test code because you never know when to wait for it.
To handle this cleanly without causing your tests to flake or freeze, you must establish a persistent, global background event listener using page.on('dialog') at the very beginning of your test execution.
Here is the exact pattern to catch and handle random alerts dynamically:

The Global "Catch-All" Event Listener

By attaching a listener right after creating or loading the page, Playwright runs a background process that actively monitors the browser thread. The moment a random alert springs up, this listener intercepts it, dismisses or accepts it, and then lets your main test script keep running smoothly.
typescript
import { test, expect } from '@playwright/test';

test('Handle unpredictable, random alerts seamlessly', async ({ page }) => {
  // 1. Establish the global background listener FIRST
  page.on('dialog', async (dialog) => {

    // Dynamically choose how to handle it based on text or type
    if (dialog.message().includes('Session Timeout Warning')) {
      await dialog.accept(); // Keep session alive
    } else {
      await dialog.dismiss(); // Safely dismiss any other random popups
    }
  });

  // 2. Proceed with your regular, linear test workflow
  await page.goto('https://example.com');

  // The alert could happen here, or 3 steps later—the listener above will catch it
  await page.getByRole('button', { name: 'Load Data' }).click();

Therefore, you only need to explicitly write the global page.on('dialog') handler if:
1. The random alert breaks your app state unless you explicitly click "OK" (Accept).
2. You want to log the alert text into your CI/CD console to debug why your environment is throwing random errors.

# Q : The table pagination contains 20 records per page, but your required record may be on any page. How would you automate it?
==> To automate finding and interacting with a record hidden across multiple pages of a paginated table, you must implement an asynchronous while loop.
This loop searches the current page for your target row. If found, it breaks out and interacts with it; if not, it checks if a "Next" button is enabled, clicks it, waits for the table to reload, and repeats the process.
Here is the robust, bulletproof pattern to handle multi-page dynamic table searching in Playwright with TypeScript:

The Multi-Page Table Search Pattern

typescript
import { test, expect } from '@playwright/test';

test('Locate and interact with a record across multiple pages', async ({ page }) => {
  await page.goto('https://example.com');

  const targetRecordText = 'Invoice #9042'; // The specific item you are looking for
  let recordFound = false;

  // 1. Keep looping until the record is found or we run out of pages
  while (!recordFound) {
    // Locate the row containing your target text on the current page
    const targetRow = page.locator('table tbody tr').filter({ hasText: targetRecordText });

    // 2. Check if the element exists and is visible on the current page
    if (await targetRow.isVisible()) {
      console.log(`🎉 Record found! Interacting with row...`);
      
      // Perform your action (e.g., click a view button inside that specific row)
      await targetRow.getByRole('button', { name: 'View' }).click();
      recordFound = true;
      break; 
    }

    // 3. If not found on this page, look for the 'Next' pagination button
    const nextButton = page.getByRole('button', { name: 'Next' });

    // 4. Critical check: Is there a next page, and is it clickable?
    // This checks both visibility and ensures it doesn't have a 'disabled' attribute/class
    if (await nextButton.isVisible() && await nextButton.isEnabled()) {
      console.log('Record not on this page. Clicking "Next" page...');
      
      // Click the next page and wait for the network/table to update
      await Promise.all([
        page.waitForResponse(response => response.url().includes('/api/records') && response.status() === 200), // Change to your app's network call if applicable
        nextButton.click()
      ]);
      
      // Alternative if no network call: wait for the old rows to detach or a loading spinner to disappear
      // await page.waitForLoadState('networkidle'); 
    } else {
      // If the Next button is disabled or missing, we have hit the last page
      break; 
    }
  }

  // 5. Final assertion to fail the test clearly if the item doesn't exist anywhere
  expect(recordFound).toBeTruthy();
});
Use code with caution.

💡 3 Golden Rules for Pagination Automation

• Wait for the Page Transition: Simply clicking "Next" isn't enough. If your script loops faster than the table can redraw its rows, Playwright might accidentally re-read the old data and think it hit a dead end. Always pair the click with a page.waitForResponse(), page.waitForSelector(), or a short state wait.
• The .filter({ hasText: ... }) Strategy: Instead of mapping rows to an index number, target the exact structural row instantly by filtering the table rows by your unique text string.
• Prevent Infinite Loops: Ensure your loop breaks out cleanly if nextButton.isEnabled() returns false. If your "Next" button never gets a disabled attribute when reaching the end, track a counter variable (let pageCount = 0) and throw an error manually if it exceeds a reasonable limit (e.g., pageCount > 50).

# Q : How would you retrieve all values from a dynamic web table?
==> o retrieve all values from a dynamic web table in Playwright with TypeScript, you should use the .allTextContents() locator method to extract cell values efficiently in parallel batches rather than looping through every element cell-by-cell.
Looping through elements with sequential await calls causes severe test slowdowns due to multiple browser round-trips. Fetching rows as grouped arrays is significantly faster and more reliable.
Here are the standard patterns to extract all table values, depending on whether you want a single flat array or a structured two-dimensional (2D) grid representing rows and columns.

1. Extract as a 2D Array (Structured Rows and Columns)

This is the best approach if you want to validate data column-by-column, match specific rows, or export the data cleanly.
typescript
import { test, expect } from '@playwright/test';

test('Retrieve structured 2D array of all table data', async ({ page }) => {
  await page.goto('https://example.com');

  // 1. Wait for the table rows to be rendered and visible
  const rowLocator = page.locator('table tbody tr');
  await rowLocator.first().waitFor({ state: 'visible' });

  // 2. Get an array of all row element handles
  const allRows = await rowLocator.all();
  
  // 3. Map through rows and extract all cell values simultaneously
  const tableData: string[][] = await Promise.all(
    allRows.map(async (row) => {
      // Find all cell elements (td) inside this specific row
      return await row.locator('td').allTextContents();
    })
  );

  // 4. Output the structured table data
  console.log(tableData); 
  /* Outputs:
     [
       ['#101', 'John Doe', 'Paid'],
       ['#102', 'Jane Smith', 'Pending'],
       ['#103', 'Bob Johnson', 'Failed']
     ]
  */

  // 5. Example Assertions on the retrieved data
  expect(tableData.length).toBeGreaterThan(0); // Ensure table is not empty
  expect(tableData[0][1]).toBe('John Doe');    // Assert exact cell position value
});
Use code with caution.

2. Extract as a Flat Array (Quick Text Match)

If you only need to verify that certain strings exist anywhere inside the table body and you don't care about row structure, you can grab all cells in a single line of code.
typescript

Use code with caution.

💡 Key Tips for Dynamic Tables

• Auto-Waiting: Dynamic tables that load via APIs can initially render empty. Always add await page.locator('table tbody tr').first().waitFor() to give the backend an extra second to populate rows before calling your mapping functions.
• Header Matching: If you also need the column header labels, you can extract them using await page.locator('table thead th').allTextContents(); and pair them up with your data columns.

# Q : A dropdown loads its values from an API after you click it. How would you automate it?
===> To automate a dropdown that fetches its values dynamically from an API upon clicking, you must coordinate your click action with Playwright's network interceptors and structural waits.
If you try to select an option immediately after clicking, your test will likely fail because the browser thread operates faster than the API response can arrive and render the HTML options.
Here are the standard, reliable patterns to handle this scenario:

1. The Network-First Pattern (Recommended)

This is the most robust approach. It forces Playwright to wait until the specific background API response returns a 200 OK status before trying to interact with the freshly loaded options.
typescript
import { test, expect } from '@playwright/test';

test('Select an option from an API-driven dynamic dropdown', async ({ page }) => {
  await page.goto('https://example.com');

  const dropdownTrigger = page.getByRole('combobox', { name: 'Select Country' });

  // 1. Intercept the network call and click the dropdown simultaneously
  await Promise.all([
    // Adjust the URL string/regex to match your application's actual API endpoint
    page.waitForResponse(response => response.url().includes('/api/countries') && response.status() === 200),
    dropdownTrigger.click() 
  ]);

  // 2. Locate the dynamically rendered option
  const targetOption = page.getByRole('option', { name: 'India' });

  // 3. Wait for the element to physically attach and become visible in the DOM
  await targetOption.waitFor({ state: 'visible' });

  // 4. Click the option to select it
  await targetOption.click();

  // 5. Assert the selection was successful
  await expect(dropdownTrigger).toHaveValue('India'); // or use .toHaveText() depending on markup
});
Use code with caution.

2. The Element-Attached Pattern (No Network Dependency)

If you don't know the exact API endpoint URL or if it's unstable, you can look for a structural cue in the UI—such as the appearance of a loading spinner disappearing or a specific option element attaching to the DOM.
typescript
test('Select an option using element waiting', async ({ page }) => {
  await page.goto('https://example.com');

  // 1. Open the dropdown menu
  await page.locator('#dynamic-dropdown-trigger').click();

  // 2. Target the specific element container where options appear
  const firstOption = page.locator('.dropdown-menu .dropdown-item').first();

  // 3. Playwright will auto-wait for this element to be attached and actionable
  await firstOption.waitFor({ state: 'visible', timeout: 5000 });

  // 4. Select your item out of the list once populated
  await page.locator('.dropdown-menu').getByText('United States').click();
});
Use code with caution.

💡 Crucial Tips for Dynamic Dropdowns

• Standard HTML vs. Custom Components: If your dropdown is a native HTML <select> tag, you can use page.selectOption(). However, API-driven dropdowns are almost always custom components (like React-Select, Angular Material, or Select2) built out of <div>, <ul>, and <li> tags. For these, use explicit .click() steps instead of .selectOption().
• Inspect the Network Tab: Open your browser's Developer Tools (F12), head to the Network tab, and click your dropdown manually. Look for the XHR/fetch request that triggers—this will give you the exact URL string to drop into your page.waitForResponse() hook.

# Q : A search result appears dynamically after typing into a search box. How would you select the correct result?
==> To automate a dynamic search box that populates results as you type, you must simulate realistic user keystrokes using locator.pressSequentially() and then wait for the specific result to appear or stabilize in the UI.
Modern autocomplete/search elements (like Google Search, Algolia, or custom React combos) trigger an API call on every keystroke or after a slight delay (debounce). If you type too fast or try to click instantly, your test will miss the result list entirely.
Here are the standard patterns to handle this scenario reliably in Playwright with TypeScript.

1. The Real Keystroke & Auto-Wait Pattern (Recommended)

This approach mimics an actual human typing, which gives the application’s underlying JavaScript event handlers (like onKeyPress or debouncing) time to fire properly.
typescript
import { test, expect } from '@playwright/test';

test('Type and select from a dynamic autocomplete search result', async ({ page }) => {
  await page.goto('https://example.com');

  // 1. Locate the search box input
  const searchInput = page.getByPlaceholder('Search products...');
  await searchInput.click();

  // 2. Type sequentially with a slight delay between keys (mimicking a user)
  await searchInput.pressSequentially('Playwright Cookbook', { delay: 100 });

  // 3. Locate the results container or list container
  const resultsContainer = page.locator('.search-results-list');
  
  // 4. Narrow down to the specific item you want to click
  // .filter() ensures you hit the row containing your exact string
  const targetResult = resultsContainer
    .locator('.search-item')
    .filter({ hasText: 'Playwright Cookbook (Advanced Edition)' });

  // 5. Explicitly wait for that dynamic item to become visible in the UI
  await targetResult.waitFor({ state: 'visible', timeout: 5000 });

  // 6. Click the specific result item
  await targetResult.click();

  // 7. Verify the page transitioned or loaded the expected search item
  await expect(page).toHaveURL(/.*products\/playwright-cookbook/);
});

Use code with caution.

2. The Keyboard Navigation Pattern (Arrow Down + Enter)

In many applications, clicking a dynamically moving dropdown list can cause flakiness if the list updates right as the mouse goes to click it. Selecting the item via keyboard keys is often a bulletproof alternative.
typescript
test('Select dynamic search results using keyboard actions', async ({ page }) => {
  await page.goto('https://example.com');

  const searchInput = page.locator('#global-search-input');
  
  // Type the search phrase
  await searchInput.pressSequentially('iPhone 15', { delay: 50 });

  // Wait for the popup results panel to exist and show content
  const firstResult = page.locator('.autocomplete-dropdown .suggestion-item').first();
  await firstResult.waitFor({ state: 'visible' });

  // Press ArrowDown to highlight the first suggestion, then press Enter to select it
  await searchInput.press('ArrowDown');
  await searchInput.press('Enter');

  // Verify search completed
  await expect(page.locator('h1')).toContainText('Search Results for "iPhone 15"');
});

Use code with caution.

💡 Pro-Tips for Dynamic Search Fields

• Avoid .fill(): Do not use await page.fill() for autocomplete fields. .fill() injects the entire string into the element instantly all at once, which frequently fails to trigger keyup or input JavaScript listeners in frontend frameworks.
• Mind the Debounce: Many search fields wait for a user to stop typing for 300ms–500ms before sending the network request. If your test acts too quickly, it checks the results before the debounce timer finishes. Adding the { delay: 100 } option to pressSequentially natively cushions against this.
• Keyboard over Mouse: If your search dropdown disappears or moves slightly when a mouse moves over it, switching to the Keyboard Navigation Pattern removes mouse coordinates from the equation entirely.

# Q : An application uses infinite scrolling instead of pagination. How would you find an element that may be far down the page?
==> To find an element on a page that uses infinite scrolling, you must programmatically scroll down the window iteratively and wait for new content to load until the target element becomes visible in the viewport.
Because infinite scroll layouts only render elements dynamically as the scrollbar approaches the bottom, standard Playwright actions like .click() will throw a timeout error if the element doesn't exist in the DOM yet.
The most reliable way to handle this is an asynchronous while loop combined with a failsafe scroll limit to prevent an infinite loop.

1. The Dynamic Scrolling Pattern (Recommended)

This pattern scrolls down the page step-by-step, checking for the element's visibility after each scroll action.
typescript
import { test, expect } from '@playwright/test';

test('Locate an element in an infinite scrolling feed', async ({ page }) => {
  await page.goto('https://example.com');

  const targetLocator = page.getByRole('heading', { name: 'Target Article Title' });
  
  let isFound = false;
  let scrollAttempts = 0;
  const maxScrollAttempts = 50; // Safety guard rails to prevent an infinite loop

  while (!isFound && scrollAttempts < maxScrollAttempts) {
    // 1. Check if the element is visible on the current screen view
    if (await targetLocator.isVisible()) {
      isFound = true;
      console.log(`🎉 Element found after ${scrollAttempts} scrolls!`);
      break;
    }

    // 2. Locate the last item currently rendered to use as a scroll anchor
    const feedItems = page.locator('.feed-item');
    const lastItem = feedItems.last();

    if (await lastItem.count() > 0) {
      // Scroll the last visible item into view to trigger the next API batch load
      await lastItem.scrollIntoViewIfNeeded();
      scrollAttempts++;

      // 3. Wait for the loading spinner to disappear or network activity to settle
      // Adjust the selector or API string to match your application
      await page.waitForTimeout(500); 
    } else {
      // Fallback: Scroll the window directly if there are no distinct items
      await page.evaluate(() => window.scrollBy(0, window.innerHeight));
      scrollAttempts++;
      await page.waitForTimeout(500);
    }
  }

  // 4. Fail the test with a clear message if the item was never found
  expect(isFound, 'Target element was not found within the scroll limits').toBeTruthy();

  // 5. Interact with your item safely now that it is rendered
  await targetLocator.click();
});
Use code with caution.

2. Advanced: Fast Network-Level Interception

If you are scraping data or just verifying an item exists, scrolling 50 times can slow down your test suite. A significantly faster alternative is to intercept the API response that provides the infinite scroll payload.
Instead of moving the browser UI, you monitor the background network data:
typescript
test('Validate infinite scroll data via API interception', async ({ page }) => {
  const matchingDataPromise = page.waitForResponse(async (response) => {
    if (response.url().includes('/api/v1/feed-items') && response.status() === 200) {
      const json = await response.json();
      // Check if the network payload contains your specific record data
      return json.items.some((item: any) => item.title === 'Target Article Title');
    }
    return false;
  });

  await page.goto('https://example.com');

  // Perform a couple of quick scrolls to trigger network calls
  await page.evaluate(() => window.scrollTo(0, document.body.scrollHeight));

  // Await the network promise to confirm the backend actually served the item
  const interceptedResponse = await matchingDataPromise;
  expect(interceptedResponse).toBeDefined();
});
Use code with caution.

💡 Best Practices for Infinite Scrolling

• Use scrollIntoViewIfNeeded(): Instead of calculating arbitrary pixel values (window.scrollBy(0, 1000)), target the last list container or item. This mimics standard user behavior perfectly.
• Cushion with Short Delays: Frontend frameworks require a brief window (typically 200ms–500ms) to resolve the scroll layout event and paint the new elements into the DOM tree.
• Always implement a maxAttempts guard: If an item gets deleted from the database or never renders, a raw while(true) loop will hang your CI/CD pipeline until it reaches hard execution timeouts.

# Q : How would you verify that a particular row was added to a table after submitting a form?
==> To verify that a row was successfully added to a table after form submission, you must handle the verification asynchronously to avoid race conditions. Since forms usually trigger either a page reload or a background API request, checking the table immediately after clicking "Submit" can lead to flaky tests.
The most resilient way to automate this is by combining a specific row locator with a web-first visibility assertion or intercepting the creation network response.
Here are the standard patterns to verify added data:

1. The Dynamic Row Visibility Pattern (Recommended)

This approach relies on Playwright's auto-waiting mechanism. It targets the specific row based on the unique text you just submitted and waits for it to appear in the UI.
typescript
import { test, expect } from '@playwright/test';

test('Fill a form, submit, and verify the row is added to the table', async ({ page }) => {
  await page.goto('https://example.com');

  const uniqueId = `INV-${Date.now()}`; // Creates a unique runtime string to avoid data conflicts

  // 1. Fill out and submit the form
  await page.getByLabel('Invoice Number').fill(uniqueId);
  await page.getByLabel('Amount').fill('250.00');
  await page.getByRole('button', { name: 'Add Invoice' }).click();

  // 2. Locate the specific row containing your unique data
  // This filters all table body rows down to the single one holding your text
  const addedRow = page.locator('table tbody tr').filter({ hasText: uniqueId });

  // 3. Web-First Assertion: Playwright will automatically retry this line 
  // until the row renders and becomes visible (default timeout: 5s)
  await expect(addedRow).toBeVisible();

  // 4. Optional: Assert on specific cell content inside that newly added row
  await expect(addedRow.locator('td')).toContainText(['', uniqueId, '$250.00']);
});
Use code with caution.

2. The Network Interception + Row Count Pattern

If you want to verify both the data layout and that your table rows incremented by exactly one, you can intercept the API creation request while monitoring the table structure.
typescript
test('Verify row addition by tracking network and row count', async ({ page }) => {
  await page.goto('https://example.com');

  // Count the rows before submitting the form
  const initialRowCount = await page.locator('table tbody tr').count();

  // Fill out the form fields
  await page.getByPlaceholder('Enter item name').fill('Automated Test Item');

  // Intercept the API save request and click submit concurrently
  await Promise.all([
    page.waitForResponse(response => response.url().includes('/api/items') && response.status() === 201),
    page.getByRole('button', { name: 'Save Item' }).click()
  ]);

  // Assert that the total row count has increased by exactly 1
  const updatedRows = page.locator('table tbody tr');
  await expect(updatedRows).toHaveCount(initialRowCount + 1);

  // Assert that the very last row contains the data you just created
  await expect(updatedRows.last()).toContainText('Automated Test Item');
});
Use code with caution.

💡 Best Practices for Row Verifications

• Inject Unique Runtime Data: Hardcoding string values like "Test Item" will eventually break your environment if the table doesn't clear out between test runs. Using timestamps (Date.now()) or custom UUIDs ensures your assertion targets only the data created by the current test execution.
• Avoid Hardcoded Breaks: Never use await page.waitForTimeout(2000) right after clicking submit. Playwright's await expect(locator).toBeVisible() or toHaveCount() handles the variable timing of server-side state saves automatically
