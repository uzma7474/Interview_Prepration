# Q : Explain your Playwright framework architecture. Why did you choose it?
===> In my current project, I have designed and worked with a modular Playwright automation framework using TypeScript, the Page Object Model (POM), and Playwright Test Runner. The main objective was to make the framework scalable, maintainable, reusable, and easy to integrate with CI/CD pipelines.

1. Framework Architecture
My framework follows a layered architecture, where each component has a specific responsibility.
Test Layer
Test Specs · Test Scenarios · Assertions

Page Object Layer
Locators · Page Actions · Reusable Methods

Core / Utility Layer
Fixtures · API Helpers · Test Data · Custom Utilities

Playwright Engine
Browser · Context · Page · Network Interception

Execution & Reporting
CI/CD · Parallel Execution · HTML Reports · Traces


2. Folder Structure
A typical structure I use is:
playwright-framework/
├── tests/
│   ├── login.spec.ts
│   ├── checkout.spec.ts
│   └── api.spec.ts
├── pages/
│   ├── LoginPage.ts
│   ├── HomePage.ts
│   └── CheckoutPage.ts
├── fixtures/
│   └── test-fixtures.ts
├── utils/
│   ├── api-helper.ts
│   └── test-data.ts
├── test-data/
│   └── users.json
├── api/
│   └── api-client.ts
├── playwright.config.ts
├── package.json
└── tsconfig.json


3. Responsibilities of Each Layer
- Test layer: Contains test scenarios, test steps, and assertions. I keep business validation in the test cases rather than putting it inside page classes.
- Page Object Model: Each page has a separate class containing locators and reusable actions, such as login, search, or checkout.
- Fixtures: I use custom fixtures to initialize page objects, share common setup, and manage test-specific dependencies.
- Utilities: Contains reusable functions for API calls, test data generation, date handling, and common operations.
- API layer: I use Playwright's APIRequestContext for API validation, test-data setup, and cleanup.
- Configuration: playwright.config.ts manages browsers, base URL, timeouts, retries, parallel execution, screenshots, traces, and reporting.
- Reporting and CI/CD: I generate HTML reports, capture traces and screenshots for failures, and execute tests through Jenkins or another CI/CD pipeline.

4. Why Did I Choose This Architecture?
I chose this architecture for the following reasons:
  1. Maintainability: If a locator changes, I generally update it in one page object instead of multiple test cases.
  2. Reusability: Common actions, fixtures, API helpers, and utilities can be reused across tests.
  3. Parallel execution: Playwright supports parallel testing with isolated browser contexts, helping reduce execution time.
  4. TypeScript support: Static typing, interfaces, and IDE autocomplete help catch mistakes early and improve code readability.
  5. Reliable execution: Auto-waiting, web-first assertions, and locator strategies help reduce flaky tests.
  6. API and UI integration: I can create test data through APIs and validate the same data through the UI without performing every setup step manually.
  7. Debugging: Playwright traces, screenshots, videos when configured, and HTML reports make failures easier to investigate.
  8. CI/CD integration: The framework can run automatically on every build or deployment and provide feedback to the development team.

5. Example: How the Components Work Together
For example, consider a login test.
LoginPage.ts
import { Page, Locator, expect } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly username: Locator;
  readonly password: Locator;
  readonly loginButton: Locator;

  constructor(page: Page) {
    this.page = page;
    this.username = page.getByLabel('Username');
    this.password = page.getByLabel('Password');
    this.loginButton = page.getByRole('button', {
      name: 'Login'
    });
  }

  async login(user: string, pass: string): Promise<void> {
    await this.username.fill(user);
    await this.password.fill(pass);
    await this.loginButton.click();
  }
}


login.spec.ts
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test('User should log in successfully', async ({ page }) => {
  const loginPage = new LoginPage(page);

  await page.goto('/login');
  await loginPage.login('testuser', 'Password123');

  await expect(page).toHaveURL(/dashboard/);
});


Here, the test class handles the scenario and assertion, while LoginPage handles the page interactions. This separation makes the framework easier to maintain and extend.
6. How I Execute the Framework

1. Run all tests :	npx playwright test
2. Run a specific test file :	npx playwright test tests/login.spec.ts
3. Run in headed mode :	npx playwright test --headed
4. Run tests in parallel :	npx playwright test --workers=4
5. Open HTML report :	npx playwright show-report
6. Debug a test	: npx playwright test --debug

7. Real-Project Challenges I Handle
At my experience level, I also focus on practical challenges such as:
- Handling dynamic elements using role-based locators and stable test IDs.
- Mocking API responses using page.route() when testing error scenarios or edge cases.
- Managing authentication using saved storage state where appropriate.
- Using environment variables for QA, staging, and other environments.
- Configuring retries and collecting traces for failed tests without hiding genuine defects.
- Running smoke and regression suites separately in CI/CD.

Final interview summary
“To summarize, I use a modular Playwright framework with TypeScript, Page Object Model, custom fixtures, reusable utilities, and Playwright Test Runner. I chose this architecture because it provides maintainability, reusability, type safety, parallel execution, and efficient debugging. I also integrate API testing, network mocking, reporting, and CI/CD execution. # Q : Tests pass locally but fail intermittently in CI/CD. How would you debug?
===> In my experience, if tests pass locally but fail intermittently in CI/CD, I treat it as a potential flaky test issue. I don't immediately increase retries or add hard waits. First, I investigate the failure using logs, screenshots, traces, and the CI environment details to identify the root cause.
I follow a systematic approach.

1. Analyze the CI/CD failure
First, I check the CI/CD execution logs and identify:
- Which test cases are failing?
- Is the failure consistent or intermittent?
- Is it a timeout, locator issue, assertion failure, API error, or environment issue?
- Does it happen only in headless mode or during parallel execution?
- Did the failure start after a recent code or application change?
For example, if a login test fails because the dashboard does not load within the expected time, I investigate whether the application is slow, the login API failed, or the test navigated incorrectly.

2. Use Playwright debugging artifacts
I configure screenshots, traces, and HTML reports to investigate failures in CI.
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  timeout: 30_000,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,

  use: {
    headless: true,
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },

  reporter: [
    ['list'],
    ['html', { open: 'never' }],
  ],
});


How I use these artifacts:
- Trace: Inspect the sequence of actions, locator resolution, network requests, and timing.
- Screenshot: Check the actual UI state at failure time.
- Video: Observe the sequence of interactions leading to the failure.
- HTML report: Identify failed tests, errors, and retry results.
I download the CI artifacts and open the trace using:
npx playwright show-trace trace.zip

This helps me determine whether the failure comes from the test script, application behavior, or execution environment.

3. Check synchronization and auto-waiting
A common cause is that the test interacts with an element before the application is ready.
Unreliable approach:
await page.waitForTimeout(5000);
await page.locator('#submit').click();

This adds a fixed delay and may still fail when the application takes longer than five seconds.
Better approach:
const submitButton = page.getByRole('button', {
  name: 'Submit',
});

await expect(submitButton).toBeVisible();
await expect(submitButton).toBeEnabled();
await submitButton.click();

await expect(
  page.getByText('Order submitted successfully')
).toBeVisible();

Playwright automatically waits for actionability conditions when performing actions such as click(). Web-first assertions also retry until their conditions are satisfied or time out.
I use explicit waits for meaningful application states rather than arbitrary sleep statements.

4. Investigate parallel execution and test data
Tests may pass individually but fail when executed together because of shared state or test data.
For example:
- Two tests update the same user account.
- Multiple workers create records with the same email address.
- One test deletes data required by another.
- Tests depend on execution order or share mutable global variables.

My approach:
1. Run the failing test individually.
2. Run it repeatedly to check whether it is intermittent.
3. Run the suite with one worker.
4. Check for shared test data and dependencies.
5. Use unique test data and isolated browser contexts.
# Run the specific test
npx playwright test tests/checkout.spec.ts

# Repeat the test to reproduce intermittent failures
npx playwright test tests/checkout.spec.ts --repeat-each=10

# Check whether parallel execution causes the issue
npx playwright test --workers=1
If the test passes with one worker but fails with multiple workers, I investigate race conditions, shared resources, and test isolation.

5. Compare local and CI environments
I compare the following settings between local and CI environments:
Area	:	What I investigate
1. Browser :	Browser version and headless behavior
2. Environment :	Base URL, credentials, environment variables
3. Performance : 	CPU, memory, network latency, and timeouts
4. Dependencies	: Node.js version, lockfile, installed packages
5. Test data :	Availability, permissions, and shared state
6. Infrastructure :	Service health, API responses, and network restrictions
I also try to reproduce the CI conditions locally by running tests in headless mode and, when applicable, inside the same Docker image used by the pipeline.

6. Investigate API and network failures
If the UI depends on backend services, I inspect failed API requests, response status codes, and request timing.
For example:
const responsePromise = page.waitForResponse(response =>
  response.url().includes('/api/orders') &&
  response.request().method() === 'POST'
);

await page.getByRole('button', {
  name: 'Place order',
}).click();

const response = await responsePromise;

expect(response.status()).toBe(201);
This helps distinguish a backend failure from a UI synchronization issue. I also verify that the application has completed the relevant operation before asserting the final UI state.

7. Use retries carefully
I may enable a limited number of retries in CI to collect additional diagnostic information. However, a retry is not the permanent fix.
For example, Playwright can classify tests as passed, flaky, or failed based on the initial result and retry outcomes. I monitor flaky results and investigate recurring failures rather than treating retry success as proof that the test is reliable.

My debugging workflow
Step 1: Identify the failure
CI logs, error message, failed assertion

Step 2: Inspect artifacts
Trace, screenshot, video, network activity

Step 3: Reproduce the failure
Run individually, repeat, compare workers

Step 4: Fix the root cause
Synchronization, isolation, data, environment, or application bug

Step 5: Validate the fix
Repeat the test and run the full regression suite in CI


Real-world example you can explain in an interview
“Suppose my checkout test passes locally but intermittently fails in Jenkins. I first inspect the HTML report and trace. I find that the checkout button is clicked, but the confirmation message is not displayed. I check the network requests and discover that the order API sometimes takes longer to respond in CI. I replace any fixed sleep with an appropriate response or UI-state wait, verify the API result, and ensure the test data is isolated for parallel execution. Then I rerun the test repeatedly and execute the regression suite in CI to confirm the fix. If the API itself returns an error, I report it as a possible application or environment defect instead of hiding it with retries.”
Only use this example as your own project experience if it reflects a scenario you have actually encountered.
Strong closing statement
“My approach is to identify the root cause rather than simply make the test pass. In Playwright, I rely on traces, screenshots, HTML reports, web-first assertions, proper test isolation, and environment comparison. I use retries for diagnosis, but I fix the underlying issue to make the automation suite stable and reliable in CI/CD.”

# Q : A button becomes enabled after multiple API calls. How would you handle it without `waitForTimeout()`?
==> If a button becomes enabled only after multiple API calls are completed, I would avoid waitForTimeout() because the response time can vary between local and CI/CD environments.
Instead, I would use Playwright's web-first assertions to wait for the button to become enabled, or wait for specific API responses if I need to verify that the required API calls have completed.

Approach 1: Wait until the button is enabled (my preferred approach)
import { test, expect } from '@playwright/test';

test('Button should become enabled after loading', async ({ page }) => {
  await page.goto('/checkout');

  const submitButton = page.getByRole('button', {
    name: 'Submit Order',
  });

  // Automatically retries until the button is enabled or times out
  await expect(submitButton).toBeEnabled();

  await submitButton.click();
});

Why do I use this approach?
- toBeEnabled() automatically retries until the button becomes enabled or the assertion times out.
- It does not depend on a hardcoded delay.
- It is simple and reliable when I only care about the final UI state.

Approach 2: Wait for multiple API responses
If the requirement specifically says that three API calls must complete before the button is enabled, I can wait for those responses explicitly.
import { test, expect } from '@playwright/test';

test('Enable button after required API calls', async ({ page }) => {
  const requiredApis = [
    '/api/user',
    '/api/products',
    '/api/permissions',
  ];

  const responsePromises = requiredApis.map((endpoint) =>
    page.waitForResponse((response) =>
      response.url().includes(endpoint) &&
      response.ok()
    )
  );

  await page.goto('/checkout');

  // Wait for all three successful API responses
  await Promise.all(responsePromises);

  const submitButton = page.getByRole('button', {
    name: 'Submit Order',
  });

  await expect(submitButton).toBeEnabled();
  await submitButton.click();
});
Important: I register the response listeners before navigation so I don't miss requests triggered during page loading. This example assumes all three endpoints are requested during navigation and each returns a successful response. If they are triggered by a user action, I register the listeners before that action instead.

Approach 3: Wait for a specific API response and then verify the UI
When a particular API determines whether the button can be enabled, I wait for that response and assert the UI state.
const permissionsResponse = page.waitForResponse(response =>
  response.url().includes('/api/permissions') &&
  response.request().method() === 'GET'
);

await page.getByRole('button', { name: 'Load Data' }).click();

const response = await permissionsResponse;
expect(response.ok()).toBeTruthy();

const submitButton = page.getByRole('button', {
  name: 'Submit Order',
});

await expect(submitButton).toBeEnabled();


This approach is useful when a user action triggers the API call.
Which approach would I choose?
Scenario : 	Approach
1. Only the final button state matters : 	await expect(button).toBeEnabled()
2. All required API calls must complete : 	Promise.all() with waitForResponse()
3. A user action triggers an API call :	Register waitForResponse() before the action
4. API calls are dynamic or repeated : 	Track the relevant requests or wait for a meaningful application state

My interview conclusion:
“I prefer waiting for the expected UI state using Playwright's web-first assertions. If the requirement depends on multiple backend calls, I explicitly wait for the relevant responses using Promise.all() and then verify that the button is enabled. This avoids hard waits and makes the test more reliable in CI/CD.”

# Q : How do you handle multiple browser tabs and validate data between them?
==>  In Playwright, I handle multiple browser tabs using context.waitForEvent('page') or page.waitForEvent('popup'), depending on how the new tab is opened.
I register the event listener before clicking the link or button to avoid missing the new tab event. Once the new tab opens, I can interact with both pages and validate that the data is consistent between them.
1. Scenario: Open a new tab and validate data between tabs
For example, suppose I have an application where clicking View Order Details opens a new tab. I need to validate that the order ID displayed in the first tab matches the order ID in the second tab.
import { test, expect, Page } from '@playwright/test';

test('Validate order data between multiple tabs', async ({ page }) => {
  await page.goto('https://example.com/orders');

  // Get the order ID from the first tab
  const orderId = await page.locator('#orderId').innerText();

  // Register the listener before clicking
  const newTabPromise = page.waitForEvent('popup');

  await page.getByRole('link', { name: 'View Order Details', }).click();

  // Capture the newly opened tab
  const newTab = await newTabPromise;

  await newTab.waitForLoadState();

  // Validate the order ID in the second tab
  await expect(newTab.locator('#orderDetailsId')).toHaveText(orderId);

  // Validate the second tab's page
  await expect(newTab).toHaveURL(/order-details/);
});

Why use page.waitForEvent('popup')?
- It captures a new tab opened by the current page.
- Registering the listener before the click prevents race conditions.
- It gives me a separate Page object to interact with the new tab.
The selectors and URL in this example are placeholders; I would replace them with the application's actual locators.

2. Scenario: Handle multiple tabs opened from the browser context
If the application opens a new tab through a mechanism where I want to listen at the browser-context level, I use context.waitForEvent('page').
import { test, expect } from '@playwright/test';

test('Handle multiple pages', async ({ context, page }) => {
  await page.goto('https://example.com');

  const newPagePromise = context.waitForEvent('page');

  await page.getByRole('link', { name: 'Open Report', }).click();

  const reportPage = await newPagePromise;

  await reportPage.waitForLoadState();

  await expect(reportPage).toHaveTitle(/Report/);

  // Both pages can be used independently
  await expect(page).toHaveURL(/example\.com/);
  await expect(reportPage).toHaveURL(/report/);
});


The difference is:
- page.waitForEvent('popup') is appropriate when the new tab is opened by a specific page.
- context.waitForEvent('page') listens for a new page created anywhere within that browser context.

3. How do I validate data between tabs?
Suppose a user selects a product in the first tab and opens its details in the second tab. I compare the values from both pages.
const productName = await page.locator('[data-testid="product-name"]').innerText();
const productPrice = await page.locator('[data-testid="product-price"]').innerText();
await expect(newTab.locator('[data-testid="detail-name"]')).toHaveText(productName);
await expect(newTab.locator('[data-testid="detail-price"]')).toHaveText(productPrice);

This approach is useful for validating:
- Order IDs between order and invoice tabs.
- Product names and prices between listing and detail tabs.
- User information between profile and account tabs.
- Transaction details between payment and confirmation tabs.
For values that load asynchronously, I prefer Playwright's retrying assertions rather than extracting text too early and comparing immediately.

4. Important interview points
Question :	Answer
1. How do you capture a new tab? :	page.waitForEvent('popup')
2. How do you capture a page at context level? :	context.waitForEvent('page')
3. Can you interact with both tabs? :	Yes, using their separate Page objects.
4. How do you validate data between tabs? :	Read the source value and compare it with a web-first assertion in the target tab.
5. How do you avoid race conditions? :	Register the event listener before triggering the action.

My interview conclusion:
“In my Playwright framework, I handle multiple tabs using page.waitForEvent('popup') for page-triggered popups and context.waitForEvent('page') when I need to capture a new page at the browser-context level. I maintain separate page references and validate business data between tabs using Playwright assertions. This helps me automate workflows such as order details, invoices, payment confirmations, and product comparisons reliably.”

# Q : How would you implement reusable authentication to avoid repeated login?
==> In my Playwright framework, I use Playwright's storageState feature to avoid logging in before every test case. After a successful login, I save the authentication state, including cookies and local storage, into a JSON file. Then, I reuse that state to authenticate other tests without repeating the login steps.
This reduces execution time and makes the automation framework more efficient.
1. How does the authentication flow work?
1. Authentication setup
Log in once using a dedicated setup test

2. Save authentication state
playwright/.auth/user.json

3. Reuse in test cases
Configure storageState in Playwright

4. Execute authenticated tests
Open protected pages without repeating UI login


2. Step 1: Create the authentication setup
Create tests/auth.setup.ts.
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/user.json';

setup('authenticate user', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Username').fill( process.env.TEST_USERNAME!);

  await page.getByLabel('Password').fill(process.env.TEST_PASSWORD!);

  await page.getByRole('button', {name: 'Login', }).click();

  await expect(page).toHaveURL(/dashboard/);

  // Save authentication state
  await page.context().storageState({ path: authFile, });
});


Here, I use environment variables for credentials instead of hardcoding usernames and passwords in the test scripts.
3. Step 2: Configure authentication in playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',

  projects: [
    {
      name: 'setup',
      testMatch: /auth\.setup\.ts/,
    },
    {
      name: 'chromium',
      use: {
        ...devices['Desktop Chrome'],
        storageState: 'playwright/.auth/user.json',
      },
      dependencies: ['setup'],
      testIgnore: /auth\.setup\.ts/,
    },
  ],
});


How it works:
- The setup project performs the login.
- The authentication state is saved in user.json.
- The Chromium project depends on the setup project.
- Playwright loads the saved state for each test, avoiding repeated UI login.
For a real project, I add .auth/ to .gitignore because authentication state files may contain sensitive cookies or tokens.
4. Step 3: Use authentication in test cases
Now, I can directly test authenticated functionality without logging in again.
import { test, expect } from '@playwright/test';

test('User can access dashboard', async ({ page }) => {
  await page.goto('/dashboard');

  await expect( page.getByRole('heading', { name: 'Dashboard' }) ).toBeVisible();
});

test('User can access profile', async ({ page }) => {
  await page.goto('/profile');

  await expect(
    page.getByRole('heading', { name: 'My Profile' })).toBeVisible();
});


Both tests use the configured authentication state.
5. Important considerations
At my experience level, I also consider these points:
- Token expiration: If the session expires, I refresh or regenerate the authentication state.
- Test isolation: Each test gets its own browser context by default, so changes to cookies or local storage in one test generally do not affect another test's context.
- Multiple user roles: I maintain separate authentication states for admin, standard user, and other roles when required.
- Security: I never commit credentials or generated authentication files to Git.
- Session storage: Playwright's standard storageState supports cookies and local storage, but not session storage by default. If the application relies on session storage, I handle it separately.
- Independent tests: Tests should not depend on another test's changes to shared backend data, even when they reuse authentication.
6. What if I have admin and user roles?
I can create separate state files:
playwright/.auth/
├── admin.json
└── user.json


Then configure separate projects or fixtures with the appropriate storageState for each role.
Interview-ready conclusion:
“In my Playwright framework, I implement reusable authentication using storageState. I log in once through a setup project, save the browser authentication state, and reuse it across authenticated test cases. This reduces execution time, avoids repetitive login steps, and improves CI/CD efficiency. I also manage token expiration, role-based authentication, test isolation, and secure storage of authentication files.”

# Q : How do you handle shadow DOM inputs in Playwright vs Selenium?
==> In my automation projects, I handle Shadow DOM elements differently in Playwright and Selenium.
A Shadow DOM is used in web components to encapsulate HTML, CSS, and JavaScript. Sometimes, normal DOM inspection or traditional locators cannot directly access elements inside a shadow root.
The main difference is that Playwright supports locating elements inside open Shadow DOMs by default, whereas Selenium generally requires locating the shadow root first and then finding the elements inside it.
1. Playwright with TypeScript
Suppose the application contains this structure:
<login-component>
  #shadow-root (open)
    <input id="username">
    <input id="password">
    <button id="login">Login</button>
</login-component>


In Playwright, I can directly locate the input fields using CSS selectors or other supported locators without explicitly accessing the shadow root.
import { test, expect } from '@playwright/test';

test('Handle Shadow DOM inputs', async ({ page }) => {
  await page.goto('https://example.com');

  const username = page.locator(
    'login-component #username'
  );

  const password = page.locator(
    'login-component #password'
  );

  await username.fill('testuser');
  await password.fill('password123');

  await page.locator(
    'login-component #login'
  ).click();

  await expect(page).toHaveURL(/dashboard/);
});


Why does this work?
Playwright's CSS locators and most other locators, such as role and label locators, pierce open Shadow DOM boundaries automatically.
There are exceptions: XPath does not pierce Shadow DOM boundaries, and closed Shadow DOM roots are not accessible through Playwright's normal locators.
2. Selenium with Java
In Selenium, I explicitly retrieve the shadow root using getShadowRoot() and then locate the input fields inside it.
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.SearchContext;

public class ShadowDOMExample {
    public static void main(String[] args) {
        WebDriver driver = new ChromeDriver();

        try {
            driver.get("https://example.com");

            // Locate the web component host
            WebElement host = driver.findElement(By.cssSelector("login-component") );

            // Access its open shadow root
            SearchContext shadowRoot = host.getShadowRoot();

            // Locate elements inside the shadow root
            WebElement username = shadowRoot.findElement(By.cssSelector("#username"));

            WebElement password = shadowRoot.findElement(By.cssSelector("#password") );

            WebElement loginButton = shadowRoot.findElement(By.cssSelector("#login"));

            username.sendKeys("testuser");
            password.sendKeys("password123");
            loginButton.click();

        } finally {
            driver.quit();
        }
    }
}


Here, SearchContext represents the shadow root context in which Selenium searches for elements.
This approach requires a Selenium version that supports getShadowRoot().

3. Key differences: Playwright vs Selenium
Feature			|	Playwright	|	Selenium
1. Open Shadow DOM	| Supported by default	| Explicitly access shadow root
2. Access shadow root	| Usually not required	| getShadowRoot()
3. Locate nested shadow elements |	Direct locators can pierce open roots |	Access each nested root step by step
4. XPath across shadow boundary	| Does not pierce the boundary	| Cannot cross it directly either
5. Closed Shadow DOM	| Not accessible through normal locators  |	Not directly accessible through standard shadow-root APIs
6. Waiting for elements	| Auto-waiting and retrying assertions |	Usually explicit or implicit waits as needed

4. What if Shadow DOM is nested?
For example:
<outer-component>
  #shadow-root (open)
    <inner-component>
      #shadow-root (open)
        <input id="email">


In Playwright:
const email = page.locator('outer-component inner-component #email');
await email.fill('user@example.com');

In Selenium Java:
WebElement outerHost = driver.findElement( By.cssSelector("outer-component"));

SearchContext outerRoot = outerHost.getShadowRoot();

WebElement innerHost = outerRoot.findElement(By.cssSelector("inner-component"));

SearchContext innerRoot = innerHost.getShadowRoot();

WebElement email = innerRoot.findElement(By.cssSelector("#email"));

email.sendKeys("user@example.com");


In Selenium, I access each shadow root individually because each shadow root creates a separate search context.
5. What if the Shadow DOM input is dynamic?
In Playwright, I use a locator and a web-first assertion rather than a fixed wait:
const email = page.locator('login-component #username');

await expect(email).toBeVisible();

# Q : Fix dynamic element wait issue on fast-loading React forms
==> In React applications, elements may render dynamically, re-render after state updates, or become enabled only after API calls finish. Sometimes, an element appears briefly and gets replaced during a React re-render.
In these situations, I avoid waitForTimeout() and use Playwright locators, web-first assertions, and waits for meaningful application states.
1. Problem: Element gets detached during React re-render
A common mistake is storing an ElementHandle and reusing it after the DOM changes.
Unreliable approach:
const submitButton = await page.locator('#submit').elementHandle();

await page.locator('#name').fill('John');

await submitButton?.click();
React might replace the button after the input changes, leaving the stored handle detached from the DOM.

Better approach:
import { test, expect } from '@playwright/test';

test('Submit dynamic React form', async ({ page }) => {
  await page.goto('/register');

  await page.getByLabel('Name').fill('John');
  await page.getByLabel('Email').fill('john@example.com');

  const submitButton = page.getByRole('button', {name: 'Submit',});

  await expect(submitButton).toBeEnabled();
  await submitButton.click();

  await expect(page.getByText('Registration successful')).toBeVisible();
});


Why? A Playwright Locator resolves the element when it is used, so it can handle DOM replacement better than a previously captured ElementHandle.
2. Problem: Button becomes enabled after API validation
Suppose a React form validates an email address through an API before enabling the Submit button.
const emailInput = page.getByLabel('Email');

await emailInput.fill('john@example.com');

const submitButton = page.getByRole('button', {name: 'Submit',});

// Wait until React enables the button
await expect(submitButton).toBeEnabled();

await submitButton.click();


Here, toBeEnabled() retries until the button becomes enabled or the assertion times out.
If I also need to verify the backend validation request, I wait for its response explicitly:
const validationResponse = page.waitForResponse(response =>
  response.url().includes('/api/validate-email') &&
  response.request().method() === 'POST'
);

await page.getByLabel('Email').fill('john@example.com');

const response = await validationResponse;
expect(response.ok()).toBeTruthy();

await expect(page.getByRole('button', { name: 'Submit' })).toBeEnabled();

This assumes the email input triggers that request. I register the response listener before filling the field so the request is not missed.
3. Problem: Form appears before React finishes rendering
Sometimes, the page loads but the form is still being initialized.
Instead of waiting an arbitrary number of seconds, I wait for a meaningful UI condition.
await page.goto('/register');

const form = page.getByTestId('registration-form');

await expect(form).toBeVisible();
await expect(page.getByLabel('Name')).toBeEditable();

await page.getByLabel('Name').fill('John');


If the application displays a loading indicator, I can also wait for it to disappear:
await expect( page.getByTestId('loading-spinner')).toBeHidden();
await expect(page.getByLabel('Name')).toBeEditable();
This assumes the spinner is present or the application has a reliable loading-state indicator. If it is never rendered, toBeHidden() can pass immediately, so I also verify the actual form state.

4. Problem: Locator matches multiple dynamic elements
React forms may render duplicate controls during transitions or contain hidden template elements.
Instead of blindly using .first(), I identify the correct element using a stable locator.
const submitButton = page.getByTestId('registration-submit');

await expect(submitButton).toHaveCount(1);
await expect(submitButton).toBeVisible();
await expect(submitButton).toBeEnabled();
await submitButton.click();

I prefer accessible roles and labels when they uniquely identify the element; otherwise, I use stable test IDs.
5. My debugging checklist
Issue	:	How I handle it
1. Element detached from DOM	: Use a Locator instead of a stored ElementHandle
2. Button enabled asynchronously :	await expect(button).toBeEnabled()
3. API validation is pending :	Register waitForResponse() before the triggering action
4. React form is still rendering :	Wait for visible, editable, or ready UI state
5. Duplicate elements :	Use specific locators and verify uniqueness
6. CI-only failures :	Inspect traces, screenshots, and network activity

# Q : How would you retry a flaky action only for a specific exception?
===> In Playwright, I would implement a custom retry mechanism using try...catch when I want to retry an action only for a specific, known transient exception. I would not retry every failure because errors such as an assertion failure or invalid locator may indicate a genuine defect.
For normal UI interactions, I first rely on Playwright's built-in auto-waiting. I implement custom retries only when there is a clear reason to retry a particular transient failure.
1. Example: Retry only for a specific exception
Suppose clicking a button intermittently fails because the element becomes detached during a React re-render.
import { test, expect, Page } from '@playwright/test';

async function clickWithRetry( page: Page, selector: string, maxRetries = 3): Promise<void> {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      await page.locator(selector).click();
      return; // Success: stop retrying
    } catch (error) {
      const message = error instanceof Error ? error.message : String(error);

      const isDetachedError =  /element was detached from the DOM/i.test(message);

      // Do not retry unrelated failures
      if (!isDetachedError || attempt === maxRetries) {
        throw error;
      }

      console.log(`Detached element. Retry ${attempt + 1}/${maxRetries}`);
    }
  }
}

test('Retry click for detached element', async ({ page }) => {
  await page.goto('/checkout');

  await clickWithRetry(page, '[data-testid="submit-order"]');

  await expect(page.getByText('Order submitted successfully')).toBeVisible();
});
How it works:
- It attempts the click up to three times.
- It retries only when the error message matches the known detached-element condition.
- It immediately throws unrelated errors.
- It throws the final error when all attempts fail.
This is an illustrative pattern. Playwright's error messages can vary by version and failure type, so I would verify the actual error produced in my environment before relying on message matching.

2. Better approach for most React applications
Instead of retrying a detached-element error manually, I usually use a fresh locator for each attempt and let Playwright handle normal waiting.
const submitButton = page.getByTestId('submit-order');

await expect(submitButton).toBeVisible();
await expect(submitButton).toBeEnabled();

await submitButton.click();

await expect(page.getByText('Order submitted successfully')).toBeVisible();

A locator can resolve the current DOM element when used, and click() already waits for actionability conditions. Therefore, a custom retry loop is not normally needed for standard DOM updates.

3. Important consideration: Avoid duplicate actions
I would be especially careful when retrying operations such as:
- Submitting a payment
- Creating an order
- Deleting a record
- Sending a form that triggers a backend transaction
If the action succeeds on the server but the browser reports an error afterward, retrying may execute the operation twice. I would verify the resulting application state before attempting the action again.

4. What if I want to retry only a timeout?
I can classify the error and rethrow anything that is not the expected transient timeout. However, I would distinguish a timeout while waiting for an element from a timeout after a potentially successful business operation.
The exception classification should be based on the actual failure condition, not merely the fact that an error occurred.

Final interview answer
“In my Playwright framework, I use a custom try...catch retry wrapper when a particular action fails due to a known transient exception. I check the exception, retry only the expected failure, and immediately rethrow unrelated errors. I also limit the number of attempts and avoid blindly retrying non-idempotent operations such as payments or order creation. For normal locator and synchronization issues, I prefer Playwright's built-in auto-waiting and web-first assertions because they are simpler and more reliable.”

Browser
Chromium, Firefox, or WebKit instance

BrowserContext
An isolated browser session: cookies, storage, permissions

A tab or popup where we interact with the application

          name: 'Mobile',
          price: 20000
        }
      ])
    });
  });

  // Open the application after registering the mock
  await page.goto('https://example.com/products');

  // Validate mocked data on the UI
  await expect(page.getByText('Laptop')).toBeVisible();
  await expect(page.getByText('Mobile')).toBeVisible();
  await expect(page.getByText('50000')).toBeVisible();
});
How it works:
- page.route() registers a handler for matching requests.
- route.fulfill() returns the mocked response instead of sending the request to the backend.
- The frontend processes the mock as an API response.
- Playwright assertions verify the rendered UI.
The URL and response structure must match the actual application's API contract for this example to work.

3. Example 2: Mock a 500 Internal Server Error
In real projects, I also test how the application behaves when the backend fails.

test('Display error when product API fails', async ({ page }) => {
  await page.route('**/api/products', async route => {
    await route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({
        message: 'Internal Server Error'
      })
    });
  });

  await page.goto('https://example.com/products');

  await expect(page.getByText('Unable to load products')).toBeVisible();
});

This verifies the frontend's error handling without requiring the actual server to fail.
Other useful mock scenarios include:
- 200 — successful response.
- 401 — unauthorized request.
- 403 — forbidden request.
- 404 — resource not found.
- 500 — internal server error.
- Empty arrays — no products available.
- Delayed responses — loading indicators and timeout behavior.
The error message in the assertion must match what the application actually displays.

4. Example 3: Intercept a request but modify the real response
Sometimes I want to call the actual backend and change only part of its response. For this, I use route.fetch() followed by route.fulfill().
test('Modify real API response', async ({ page }) => {
  await page.route('**/api/products', async route => {
    // Fetch the real API response
    const response = await route.fetch();

    // Read the actual response body
    const products = await response.json();

    // Modify a field for testing
    if (products.length > 0) {
      products[0].name = 'Mocked Laptop';
    }

    // Return the modified response to the UI
    await route.fulfill({
      response,
      json: products
    });
  });

  await page.goto('https://example.com/products');

  await expect(page.getByText('Mocked Laptop')).toBeVisible();
});


This technique is useful when I want to preserve most real backend data but override a specific field. The real API must be reachable, and its response must have the expected structure.

5. Difference between fulfill(), continue(), and fetch()
Method	Purpose
route.fulfill()	 :      Return a mocked response directly
route.continue() :	Send the request to the actual server without further route handling
route.fetch()	 :	Send the request to the actual server and retrieve the response so it can be inspected or modified
Interview tip	 : 	Register the route before navigating to the page or triggering the action. Otherwise, a fast API request may already have completed before interception is configured.
Interview-ready answer
“With my Playwright and TypeScript framework, I use page.route() to intercept API requests and route.fulfill() to return mocked responses. This helps me test positive and negative scenarios independently of backend availability. For example, I can mock product data, return a 500 error, or simulate an empty response and validate the corresponding UI behavior. If I need to modify a real backend response, I use route.fetch() and then route.fulfill(). This improves test reliability and gives me control over scenarios that are difficult to reproduce with a real backend.”
