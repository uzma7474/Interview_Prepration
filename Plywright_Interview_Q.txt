Q. Which design pattern you have used in framework ?
=>  Interview Answer

“In my Playwright TypeScript framework, I primarily use the Page Object Model (POM) design pattern. Along with POM, I use the Factory pattern for browser creation, Fixture pattern for managing Playwright objects and test setup, and Singleton-like management where centralized configuration or shared utilities are required.

The main design pattern is POM because it separates page locators and page-specific actions from test cases. This improves maintainability, reusability, and readability.”

1. Page Object Model — Main Pattern

In my Swag Labs framework, I created separate page classes for different pages:

pages/
 ├── LoginPage.ts
 ├── InventoryPage.ts
 ├── CartPage.ts
 ├── CheckoutInformationPage.ts
 ├── CheckoutOverviewPage.ts
 └── CheckoutCompletePage.ts

For example:

export class LoginPage {
    constructor(private page: Page) {}

    private username = this.page.locator('#user-name');
    private password = this.page.locator('#password');
    private loginButton = this.page.locator('#login-button');

    async login(username: string, password: string) {
        await this.username.fill(username);
        await this.password.fill(password);
        await this.loginButton.click();
    }
}

Then my test doesn't directly contain locators:

const loginPage = new LoginPage(page);

await loginPage.login(
    'standard_user',
    'secret_sauce'
);

This gives me separation of concerns.

2. Base Page Pattern

I also created a BasePage that contains common browser/page operations.

export class BasePage {
    constructor(protected page: Page) {}

    async navigate(url: string) {
        await this.page.goto(url);
    }

    async click(locator: Locator) {
        await locator.click();
    }

    async fill(locator: Locator, value: string) {
        await locator.fill(value);
    }
}

Other page objects can extend it:

export class LoginPage extends BasePage {

    private username = this.page.locator('#user-name');
    private password = this.page.locator('#password');
    private loginButton = this.page.locator('#login-button');

    async login(username: string, password: string) {
        await this.fill(this.username, username);
        await this.fill(this.password, password);
        await this.click(this.loginButton);
    }
}

This avoids duplicating common functionality across page classes.

3. Factory Pattern

For browser creation, I can use a factory approach so that browser selection is centralized.

For example:

class BrowserFactory {

    static async createBrowser(
        browserType: BrowserType,
        headless: boolean
    ) {
        return await browserType.launch({ headless });
    }
}

Then the framework can decide whether to run:

Chromium
Firefox
WebKit

based on configuration.

This is useful when I want to execute the same test suite across multiple browsers without changing test code.

4. Fixture Pattern

Playwright itself provides a powerful fixture mechanism.

For example:

import { test as base } from '@playwright/test';

export const test = base.extend({
    loginPage: async ({ page }, use) => {
        const loginPage = new LoginPage(page);
        await use(loginPage);
    }
});

Then the test becomes cleaner:

test('Login with valid user', async ({ loginPage }) => {

    await loginPage.login(
        'standard_user',
        'secret_sauce'
    );

});

The fixture is responsible for preparing and providing the required objects to the test.

Why did I choose POM?

I would explain it like this in an interview:

“The main reason I use POM is maintainability. Suppose the SauceDemo login button locator changes. Instead of modifying 20 or 30 test cases, I only need to update the locator in LoginPage.

It also improves reusability because common actions such as login, adding a product to the cart, checkout, and logout are implemented once in their respective page classes.”

Q : Explain how do you pick which test cases to automate ?
==>  “I don't automate every test case. I first analyze the test case based on business importance, repeatability, stability, execution frequency, and automation ROI. My goal is to automate scenarios where automation provides long-term value and reduces manual effort.”

For my Swag Labs Playwright TypeScript framework, I generally categorize test cases like this:

1. High-priority and business-critical scenarios

I prioritize functionality that is critical to the application.

For example, in Swag Labs:

Login with valid credentials
Login with invalid credentials
Product search/filter
Add product to cart
Remove product from cart
Checkout
Order completion
Validation of mandatory checkout fields

These flows are good candidates because if they fail, the application has a significant functional issue.

2. Repetitive test cases

If a test needs to be executed repeatedly during every regression cycle, I prefer automation.

For example:

Login → Select Product → Add to Cart → Checkout

Instead of manually executing this flow for every release, Playwright can execute it consistently.

3. Regression test cases

I strongly prioritize regression scenarios.

For example, after a change in the checkout functionality, I would automatically execute:

Login
   ↓
Inventory
   ↓
Cart
   ↓
Checkout Information
   ↓
Checkout Overview
   ↓
Order Completion

This helps identify whether a new change has broken existing functionality.

4. Data-driven scenarios

Test cases with multiple combinations are also good candidates.

For example, login:

standard_user
locked_out_user
problem_user
performance_glitch_user

Instead of creating completely separate automation code, I can parameterize the test data.

const users = [
    { username: 'standard_user', password: 'secret_sauce' },
    { username: 'locked_out_user', password: 'secret_sauce' },
    { username: 'problem_user', password: 'secret_sauce' }
];

Then execute the same test logic with different data.

5. Stable functionality

I prefer automating functionality that is relatively stable.

For example, if the login flow is stable and used throughout the application, it's a good candidate.

But if a feature is still under heavy development and the UI changes every day, I may initially keep it manual until the requirements and UI stabilize.

6. Cross-browser scenarios

Playwright makes it easy to run the same tests against:

Chromium
Firefox
WebKit

So scenarios that are important across browsers are strong candidates for automation.

7. Tests that are difficult or time-consuming manually

For example:

50 products
5 different users
10 checkout combinations
3 browsers

Doing this manually repeatedly is expensive and error-prone.

Automation gives us better consistency and faster execution.

What I generally don't automate

I don't automatically choose every test case.

For example:

One-time exploratory testing

If a tester needs to explore a new feature and understand unexpected behavior, manual exploratory testing is more appropriate.

Frequently changing UI

If the UI is changing continuously, automation may create unnecessary maintenance.

Visual/usability testing

For example:

“Does this page feel user-friendly?”

That's generally better evaluated manually, although automated visual regression can be useful for specific visual requirements.

One-time tests

If a test will be executed only once and takes 30 seconds manually, automation may not provide enough ROI.
