Why abstract classes have a constructor? 

The main purpose of the constructor is to initialize the newly created object. In abstract class, we have an instance variable, abstract methods, and non-abstract methods. We need to initialize the non-abstract methods and instance variables, therefore abstract classes have a constructor.
Also, even if we don’t provide any constructor the compiler will add default constructor in an abstract class.
An abstract class can be inherited by any number of sub-classes, thus functionality of constructor present in abstract class can be used by them.
The constructor inside the abstract class can only be called during constructor chaining i.e. when we create an instance of sub-classes. This is also one of the reasons abstract class can have a constructor.

Why interfaces can not have the constructor?

An Interface is a complete abstraction of class. All data members present in the interface are by default public, static, and final. All the static final fields should be assigned values at the time of declaration, otherwise it will throw compilation error saying “variable variable_Name not initialized in default constructor”.
The methods inside the interface are by default public abstract which means the method implementation cannot be provided by the interface itself, it has to be provided by the implementing class. Therefore, no need of having a constructor inside the interface.
A constructor is used to initializing non-static data members and as there are no non-static data members in the interface, there is no need of constructor
Methods present in the interface are only declared not defined, As there is no implementation of methods, there is no need of making objects for calling methods in the interface and thus no point of having constructor in it.
If we try to create a constructor inside the interface, the compiler will give a compile-time error.

An abstract class is used if you want to provide a common, implemented functionality among all the implementations of the component. Abstract classes will allow you to partially implement your class, whereas interfaces would have no implementation for any members whatsoever

# Q : 

==> In Java, Comparable and Comparator are both interfaces used to sort collections or arrays of objects. However, they serve completely different purposes regarding how and where the sorting logic is defined

The core difference is that Comparable defines the "natural" default ordering of a class internally, whereas Comparator defines custom or alternative sorting logic externally.

1. Understanding Comparable
	Comparable is an interface in Java used to define the natural ordering of objects. A class implements Comparable and overrides the compareTo() method to specify how its objects should be compared and sorted.

Belongs to the java.lang package.
Uses the compareTo() method.
Implemented by the class whose objects need to be sorted.
You use Comparable when a class has an obvious, default way of being sorted. For example, numbers are naturally sorted by value, and strings are naturally sorted alphabetically.
• How it works: The target class implements Comparable<T> and overrides the compareTo() method.
• Limitation: You only get one chance to implement it. If you implement it to sort by ID, you cannot easily change it to sort by Name later using Comparable.

It is present in java.lang.
We implement Comparable<T> in the class.
We override the compareTo() method.
It provides one default sorting order.

Example:
public class Developer implements Comparable<Developer> {
    private int id;
    private String name;

    public Developer(int id, String name) {
        this.id = id;
        this.name = name;
    }

    // Sorts naturally by ID in ascending order
    @Override
    public int compareTo(Developer other) {
        return Integer.compare(this.id, other.id);
    }
}

// Usage:
List<Developer> list = new ArrayList<>();
Collections.sort(list); // Automatically uses compareTo()

2. Understanding Comparator
	Comparator is an interface in Java used to define custom sorting logic for objects. Unlike Comparable, the sorting logic is defined separately from the class, allowing the same objects to be sorted using different criteria.

Belongs to the java.util package.
Uses the compare() method.
Can be used with Collections.sort() and List.sort().

You use Comparator when you need to sort objects using different criteria, or when you are working with a third-party class whose source code you cannot modify to add Comparable.
• How it works: Since Comparator is a functional interface, it is highly flexible and typically implemented via separate classes, anonymous classes, or lambdas.

Comparator is used when we want to define custom or multiple sorting strategies without modifying the original class.

It is present in java.util.
We implement Comparator<T> or use a lambda expression.
We override compare().
We can create multiple sorting orders.


Example (Using Lambdas):

public class Developer {
    public int id;
    public String name;
    // Constructor, getters, setters...
}

// Usage:
List<Developer> list = new ArrayList<>();

// Strategy A: Sort by name
Collections.sort(list, (d1, d2) -> d1.name.compareTo(d2.name));

// Strategy B: Sort by ID (alternative syntax using Comparator factory methods)
list.sort(Comparator.comparingInt(d -> d.id));


Interviewer: Where have you used Comparator?

My answer:

"In my automation framework, if I have a collection of test results or objects such as test execution details, I can use Comparator when I need different sorting criteria—for example, sorting by execution time, test case name, or priority. I prefer Comparator when multiple sorting strategies are required because it keeps the model class independent of the sorting logic."

One-line answer to remember

Comparable = default/natural sorting inside the class.
Comparator = custom/multiple sorting outside the class.

Interview follow-up: If they ask "Which one would you prefer and why?", a good answer is: I prefer Comparable when the class has one obvious natural order; I use Comparator when I need multiple sorting strategies or cannot modify the class.

If they ask “Comparable vs Comparator and where have you used it?”, give this concise answer:

Comparator is used when we need custom or multiple sorting criteria, and we implement Comparator and override compare().

For example, an Employee can implement Comparable to sort naturally by employee ID. If I later need to sort the same employees by salary, name, or joining date, I would use Comparator.

In automation, I can use Comparator when validating sorted UI tables or API response data—for example, extracting employee records from the UI, sorting the expected list by salary using Comparator, and comparing it with the actual UI order.”

In simple words:

When a reference variable is null, but we try to access a method, field, or property through that reference, Java throws NullPointerException.
String name = null;

# Q :  Difference between == and .equals() with real-time scenario.

==> == and .equals() are used for comparison in Java, but they compare different things.

== compares primitive values or object references.

# Q :  How would you optimize your solution instead of using nested loops?
===> I would first identify the purpose of the nested loops and then choose a more efficient data structure or Java 8 feature. Instead of using nested loops, I can use a HashSet, HashMap, or Java Streams to reduce time complexity and improve readability.

For example, if I need to find duplicate values in a list, nested loops take O(n²) time. I can optimize the solution using a HashSet to achieve O(n) average time complexity.

Example 1: Find duplicates without nested loops

Using nested loops — O(n²)

for (int i = 0; i < list.size(); i++) {
    for (int j = i + 1; j < list.size(); j++) {
        if (list.get(i).equals(list.get(j))) {
            System.out.println(list.get(i));
        }
    }
}

Optimized solution using HashSet — O(n) average

import java.util.*;

public class FindDuplicates {
    public static void main(String[] args) {

        List<String> list = Arrays.asList("Java", "Selenium", "Java", "TestNG", "Selenium");

        Set<String> seen = new HashSet<>();
        Set<String> duplicates = new LinkedHashSet<>();

        for (String item : list) {
            if (!seen.add(item)) {
                duplicates.add(item);
            }
        }

        System.out.println("Duplicates: " + duplicates);
    }
}

Output:

Duplicates: [Java, Selenium]

# Q :  Can you explain a real scenario where inheritance caused an issue?
===> Yes. In one of my automation framework scenarios, inheritance caused an issue because multiple test classes shared a common BaseTest class, which contained WebDriver initialization, browser configuration, and teardown logic.

Real-time scenario

Suppose I have a BaseTest class and two test classes, LoginTest and CheckoutTest.

Initially, the framework was designed like this:

public class BaseTest {

    protected WebDriver driver;

    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver();
        driver.manage().window().maximize();
    }

    @AfterMethod
    public void tearDown() {
        driver.quit();
    }
}

Both test classes inherit the base class:

public class LoginTest extends BaseTest {

    @Test
    public void verifyLogin() {
        driver.get("https://example.com/login");
    }
}
public class CheckoutTest extends BaseTest {

    @Test
    public void verifyCheckout() {
        driver.get("https://example.com/checkout");
    }
}

Initially, this worked correctly. However, as the framework grew, we added browser-specific setup, API setup, and different teardown requirements.

What was the issue?

One issue occurred when a child test class overrode the setUp() method but forgot to call the parent implementation.

public class LoginTest extends BaseTest {

    @BeforeMethod
    @Override
    public void setUp() {
        // Browser initialization accidentally omitted
    }
}

Now driver remains null, and the test fails with a NullPointerException.

Another common issue is putting too much functionality into BaseTest. A change intended for one test suite can unexpectedly affect every child class.

How did I resolve it?

1. Keep the base class focused. I keep only genuinely shared WebDriver lifecycle logic in BaseTest, rather than putting all test-specific behavior there.

2. Prefer composition for optional functionality. Instead of extending a large base class to obtain API clients, configuration, or test data utilities, I inject or create those dependencies separately.

3. Avoid unnecessary method overriding. I use clearly named lifecycle methods or separate helper methods when browser initialization should not be customized by individual test classes.

4. Manage driver lifecycle safely. In parallel execution, I use a ThreadLocal<WebDriver>-based driver manager when appropriate so that each test thread gets its own driver.

Better design example
public class BaseTest {

    protected WebDriver driver;

    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver();
        driver.manage().window().maximize();
    }

    @AfterMethod(alwaysRun = true)
    public void tearDown() {
        if (driver != null) {
            driver.quit();
            driver = null;
        }
    }
}

Here, alwaysRun = true helps ensure cleanup is attempted even when a test fails. The null check prevents teardown from failing if driver initialization did not complete.

Interview conclusion

"In my automation framework, inheritance initially helped us reuse common setup and teardown code. However, as the framework grew, overriding inherited lifecycle methods and adding too many responsibilities to the base class made it fragile. I addressed this by keeping the base class minimal, avoiding unnecessary overrides, and using composition for optional services. My principle is to use inheritance for a genuine is-a relationship and composition when I only need to reuse functionality."

# Q : What happens if you use HashMap in multithreading?
===> If I use a HashMap in a multithreaded environment, it is not thread-safe by default. When multiple threads access and modify the same HashMap concurrently, it can cause race conditions, lost updates, and inconsistent results.

1. Real-time automation framework scenario

Suppose I execute 50 TestNG test cases in parallel and store API response data in a shared HashMap.

static Map<String, String> testData = new HashMap<>();

Each thread stores its response:

What problems can occur?

Race condition: Two tests overwrite the same "userId" key.

Lost updates or inconsistent results: Concurrent writes can interfere with each other.

Data leakage between tests: One test may read another test's response data.

Concurrent modification issues: Iterating while another thread modifies the map can result in ConcurrentModificationException in certain circumstances.

Modern Java implementations generally protect the internal structure better than older versions, but that does not make HashMap safe for concurrent modification.

2. How would I solve this problem?

Option 1: Use ConcurrentHashMap

If multiple threads must share a map, I would consider ConcurrentHashMap.

import java.util.concurrent.ConcurrentHashMap;
import java.util.Map;

public class TestDataManager {

    private static final Map<String, String> testData =
            new ConcurrentHashMap<>();

    public static void main(String[] args) {

        Runnable task = () -> {
            String threadName =
                    Thread.currentThread().getName();

            testData.put(threadName, "API response data");

            System.out.println(
                    threadName + " : " + testData.get(threadName));
        };

        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);

        t1.start();
        t2.start();
    }
}

ConcurrentHashMap supports concurrent access and updates without requiring me to synchronize every individual operation manually.

However, it does not solve logical conflicts when two tests use the same key. I would use unique keys or separate test contexts.

For Selenium parallel execution, test-specific data should generally be isolated per test or thread.

public class TestDataManager {

    private static final ThreadLocal<Map<String, String>> testData =
            ThreadLocal.withInitial(HashMap::new);

    public static Map<String, String> getTestData() {
        return testData.get();
    }

    public static void clear() {
        testData.remove();
    }
}

Usage:

Each thread receives its own map, so separate test threads do not overwrite one another's values.

# Q : What is hashmap in java how it internally works
==> A HashMap in Java is a class in java.util that stores data as key-value pairs. It implements the Map interface and gives average O(1) time for put() and get(). It allows one null key and multiple null values, does not guarantee ordering, and is not thread-safe.

java
Map<String, Integer> map = new HashMap<>();
map.put("apple", 10);
map.put("banana", 20);
System.out.println(map.get("apple")); // 10

How it works internally
1. Data structure: array of buckets

Internally, a HashMap is an array of nodes called table. Each slot is a bucket. The default initial capacity is 16 (always a power of 2), and the default load factor is 0.75.

Each entry is stored as a Node<K,V> containing:

hash (the key’s hash)
key
value
next (pointer to the next node, forming a linked list)

2. What happens on put(key, value)
Compute hashCode: calls key.hashCode().
Spread the hash: Java mixes the high bits into the low bits to reduce collisions:

   static int hash(Object key) {
       int h;
       return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
   }
Find the bucket index:

   index = (n - 1) & hash;   // n = table length

This is a fast replacement for hash % n, which works because n is a power of 2.
4. Insert:

If the bucket is empty, a new node is placed there.
If the bucket is occupied (a collision), Java walks the chain. For each node, it checks whether the hash matches and key.equals(existingKey). If a match is found, the old value is replaced. Otherwise the new node is appended to the end of the list.
3. What happens on get(key)
Compute the hash and the bucket index the same way.
Go to that bucket and compare hash and equals() along the chain.
Return the value if found, else null.
4. Collision handling

Different keys can land in the same bucket. Java handles this with separate chaining (a linked list per bucket).

Treeification (Java 8+): if a single bucket’s chain grows to 8 or more nodes and the table capacity is at least 64, the linked list is converted into a Red-Black Tree. This improves worst-case lookup from O(n) to O(log n). If the bucket shrinks to 6 or fewer nodes, it converts back to a list. If the table is smaller than 64, it resizes instead of treeifying.

5. Resizing (rehashing)

When size > capacity × load factor (e.g. 16 × 0.75 = 12 entries), the table doubles in size (16 → 32 → 64...). All entries are redistributed into the new table. In Java 8+, each node either stays at the same index or moves to oldIndex + oldCapacity, determined by one extra bit of the hash, so no full recomputation is needed. Resizing is expensive, so if you know the expected size, set the initial capacity up front: new HashMap<>(expectedSize / 0.75 + 1).

The equals() and hashCode() contract

This is a very common interview topic. For custom objects used as keys:

If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true.
If you override one, override both.

Keys should ideally be immutable (like String, Integer). If a key’s fields change after insertion, its hash changes and you will no longer find it in the map.
Time complexity
Operation			|	Average			|	Worst case
put / get / remove		|	O(1)			|		O(log n) (Java 8+, tree bins), O(n) (before Java 8)
Iteration
			|	O(capacity + size)	
HashMap vs. similar classes
			 HashMap	|	Hashtable		|	ConcurrentHashMap			|   LinkedHashMap	|  TreeMap22
2. Thread-safe	|	No		|  Yes (whole-method locking)	|   Yes (fine-grained: CAS and per-bucket locks)|	No		|  No
3. Null key	|	1 allowed	|  Not allowed			|   Not allowed					|	1 allowed	|  Not allowed
4. Ordering	|	None		|  None				|   None					|     Insertion order	|  Sorted by key
5. Performance	|	O(1)	Slower	|  O(1), 			|   scalable					|     O(1)		|  O(log n)

Common interview follow-ups
Why is capacity a power of 2? So (n-1) & hash can replace the slower modulo operation and distribute indexes evenly.
Why load factor 0.75? It balances space and time: lower values waste memory, higher values increase collisions.
Is HashMap thread-safe? No. Concurrent modification can cause lost updates (and in old Java versions, infinite loops during resize). Use ConcurrentHashMap or Collections.synchronizedMap().
What is fail-fast? HashMap iterators throw ConcurrentModificationException if the map is structurally modified during iteration (except via the iterator’s own remove()).
What happens if two keys have the same hashCode? They go to the same bucket, and equals() distinguishes them.

==> HashMap in Java: What It Is and How It Works Internally
What it is

HashMap<K,V> is a hash-table-based implementation of the Map interface. It stores key-value pairs, allows one null key and multiple null values, is not thread-safe, and gives O(1) average time for get/put/remove. It does not guarantee ordering.

Internal structure

Internally it is an array of nodes (buckets):


transient Node<K,V>[] table;

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;   // linked list for collisions
}
Default initial capacity: 16 (always a power of 2)
Default load factor: 0.75
Threshold = capacity × load factor (16 × 0.75 = 12)
How put(key, value) works
Compute hash: calls key.hashCode() and spreads the bits to reduce collisions:


   static final int hash(Object key) {
       int h;
       return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
   }

XOR-ing the upper 16 bits into the lower 16 means high bits also influence the bucket index.

Find bucket index:
java
   index = (n - 1) & hash;   // n = table length

This is faster than % and works because n is a power of 2.

Insert:
Bucket empty → place a new Node there.
Bucket occupied (collision) → traverse the chain:
If a node has the same hash and equals() returns true → replace the value.
Otherwise → append a new node at the tail.
Treeify (Java 8+): if a single bucket’s chain length reaches 8 (TREEIFY_THRESHOLD) and table capacity is at least 64 (MIN_TREEIFY_CAPACITY), the linked list converts to a Red-Black Tree. Worst-case lookup in that bucket improves from O(n) to O(log n). If capacity is below 64, it resizes instead. When the tree shrinks to 6 nodes (UNTREEIFY_THRESHOLD) it reverts to a list.
Resize: after insertion, if size > threshold, the table doubles in size.
How get(key) works
Compute hash(key) and the bucket index.
Check the first node: same hash and (== or equals) → return value.
Otherwise traverse the linked list or tree.
Not found → return null.
Resizing (rehashing)

When size exceeds the threshold, capacity doubles (16 → 32 → 64...). Each node is redistributed, but Java 8 optimized this: because the capacity is a power of 2, each node either stays at the same index or moves to oldIndex + oldCapacity, decided by one extra bit of the hash (hash & oldCap). No full recomputation is needed, and relative order within a bucket is preserved.

Resizing is costly, so if you know the expected size, pre-size it: new HashMap<>(expectedSize / 0.75f + 1).

The equals/hashCode contract (very commonly asked)
If a.equals(b) is true, then a.hashCode() == b.hashCode() must hold.
Override both together. If you override equals only, two “equal” keys may land in different buckets and lookups fail.
Keys should be immutable (like String, Integer). If a key’s fields change after insertion, its hash changes and the entry becomes unreachable.
Key interview questions

1. What happens with a poor hashCode (e.g., always returns 1)?
All entries land in one bucket, so it degrades to O(n) (or O(log n) with treeification if keys are Comparable).

2. HashMap vs Hashtable vs ConcurrentHashMap?

			|  HashMap		      |	Hashtable			  |	ConcurrentHashMap
1. Thread-safe		|  No			      |	Yes (method-level synchronized)	  |	Yes (fine-grained: CAS + synchronized on bucket head in Java 8+)
2. Null key/value	|  1 null key, null values OK |	Not allowed			  |	Not allowed
3. Performance		|  Fastest (single-thread)    |	Slow (single lock)		  |	Good under concurrency

3. What is fail-fast behavior?
HashMap tracks modCount. If the map is structurally modified during iteration (other than via the iterator’s own remove), it throws ConcurrentModificationException. This is best-effort, not guaranteed.

4. Why is capacity a power of 2?
So (n-1) & hash gives a uniform index cheaply, and resizing can split buckets using a single bit.

5. Why load factor 0.75?
A trade-off between space and time. Lower means fewer collisions but more memory. Higher saves memory but increases collisions.

6. Can HashMap cause an infinite loop?
In Java 7, concurrent resizing could create a circular linked list (head-insertion during transfer), causing infinite loops in get. Java 8 preserves order during resize, which largely avoids this, but HashMap is still unsafe for concurrent use (lost updates, data corruption). Use ConcurrentHashMap.

7. How is null key handled?
hash(null) returns 0, so it is always stored in bucket index 0.

8. HashMap vs LinkedHashMap vs TreeMap?

LinkedHashMap: maintains insertion (or access) order via a doubly linked list.
TreeMap: sorted by key (Red-Black Tree), O(log n) operations, no null keys.

9. How do you make a HashMap thread-safe?
ConcurrentHashMap (preferred) or Collections.synchronizedMap(new HashMap<>()).

Quick example showing the contract
java
class Employee {
    int id; String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Employee)) return false;
        Employee e = (Employee) o;
        return id == e.id && Objects.equals(name, e.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}

# Q : what  is hashtable and how it internally work
==> What it is

Hashtable<K,V> is a legacy class (Java 1.0) that stores key-value pairs using hashing. It was retrofitted to implement Map in Java 1.2. Key traits:

Thread-safe (every public method is synchronized)
No null key and no null values (throws NullPointerException)
Extends the obsolete Dictionary class
No ordering guarantee
Considered legacy: prefer ConcurrentHashMap (or HashMap for single-threaded use)
Internal structure

An array of entries (buckets), with collisions handled by chaining (linked list):

java
private transient Entry<?,?>[] table;

private static class Entry<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    Entry<K,V> next;
}

Defaults:

Initial capacity: 11 (not a power of 2)
Load factor: 0.75
Threshold = capacity × load factor (11 × 0.75 = 8)
How put(key, value) works
java
public synchronized V put(K key, V value) {
    if (value == null) throw new NullPointerException();

    int hash = key.hashCode();              // NPE if key is null
    int index = (hash & 0x7FFFFFFF) % tab.length;
    ...
}
Null check: null key or value throws NullPointerException.
Hash: uses key.hashCode() directly, with no bit-spreading like HashMap’s h ^ (h >>> 16).
Index: (hash & 0x7FFFFFFF) % table.length. The mask clears the sign bit so the index is non-negative, then modulo picks the bucket. Because the capacity isn’t a power of 2, & can’t be used here, so it relies on % (slower than HashMap’s bitwise AND).
Collision handling: traverse the chain. If a node has the same hash and equals() is true, the value is replaced and the old value returned. Otherwise a new entry is added.
Insertion position: new entries are added at the head of the bucket’s chain (HashMap appends at the tail).
Resize (rehash()) happens when the threshold is exceeded.
Resizing (rehash)
java
int newCapacity = (oldCapacity << 1) + 1;   // 11 → 23 → 47 → 95 ...
New capacity = 2n + 1 (stays odd, which tends to be better for modulo distribution than even sizes).
Every entry is rehashed (index recomputed with the new length). HashMap’s Java 8 trick of “same index or index + oldCap” doesn’t apply here.
Entries are re-inserted at the head of the new chain, so order within a bucket reverses.
How get(key) works
Compute hash = key.hashCode() and the index with %.
Traverse the chain, matching hash and equals.
Return the value, or null if not found.

get is also synchronized, so even readers block each other.

No treeification

Unlike HashMap (Java 8+), Hashtable never converts long chains to Red-Black Trees. With heavy collisions, lookup degrades to O(n).

Thread safety: how and the catch

Every method locks on the entire Hashtable object (this). Only one thread can do anything (read or write) at a time. This causes:

High contention, poor scalability
Compound operations are still not atomic:
java
  if (!table.containsKey(k)) {   // two separate synchronized calls
      table.put(k, v);           // another thread can sneak in between
  }

Needs external synchronization, or use ConcurrentHashMap.putIfAbsent() / computeIfAbsent().

Iteration: fail-fast vs not
Iterators from keySet(), values(), entrySet() are fail-fast (ConcurrentModificationException, tracked via modCount).
The legacy Enumeration from keys() and elements() is not fail-fast.

Thread-safe	Yes (whole-object lock)	No	Yes (CAS + bucket-level synchronized, Java 8+)
Null key	No	One allowed	No
Null values	No	Yes	No
Default capacity	11	16	16
Index calculation	(hash & 0x7FFFFFFF) % n	(n-1) & hash	(n-1) & spread(hash)
Resize	2n + 1	2n	2n
Collision structure	Linked list only	List → Red-Black Tree	List → Red-Black Tree
Iterator	Fail-fast + Enumeration	Fail-fast	Weakly consistent (no CME)
Performance	Slowest	Fastest (single thread)	Best under concurrency
Status	Legacy	Standard	Preferred for concurrency
Interview questions

1. Why doesn’t Hashtable allow null keys/values?
key.hashCode() and value == null checks throw NPE. In a concurrent map, get(k) == null would be ambiguous (absent key vs null value), and since you can’t safely follow up with containsKey under concurrency, nulls are banned. ConcurrentHashMap follows the same reasoning.

2. Why is Hashtable’s default capacity 11?
It uses %, and a prime or odd capacity gives better distribution than powers of 2 when hash codes are poorly distributed, since there is no bit-spreading step.

3. Why is Hashtable slow?
A single lock on the entire object, so reads and writes serialize. Plus the % operation and no tree-based collision handling.

4. Is Hashtable fully thread-safe?
Individual operations are, but compound check-then-act sequences are not.

5. Hashtable vs Collections.synchronizedMap(new HashMap<>())?
Both use coarse-grained locking. The synchronized wrapper allows null key/values (since it wraps a HashMap), and lets you synchronize on a shared mutex. Neither is a good choice for high concurrency.

6. What would you use instead today?
ConcurrentHashMap for concurrent access, HashMap for single-threaded use.

map.entrySet().stream()
   .forEach(e -> System.out.println(e.getKey() + " = " + e.getValue()));

Useful when you also want to filter, map, sort or collect:

java
map.entrySet().stream()
   .filter(e -> e.getValue() > 1)
   .sorted(Map.Entry.comparingByKey())
   .forEach(e -> System.out.println(e.getKey()));

parallelStream() is also possible, but rarely worth it for small maps.

8. Iterable.forEach on entrySet() / keySet() / values()
java
map.entrySet().forEach(e -> System.out.println(e.getKey() + " = " + e.getValue()));
map.keySet().forEach(System.out::println);
map.values().forEach(System.out::println);
9. Convert keys to an array/list and use a classic for loop
java
List<String> keys = new ArrayList<>(map.keySet());
for (int i = 0; i < keys.size(); i++) {
    System.out.println(keys.get(i) + " = " + map.get(keys.get(i)));
}

Works, but creates a copy. Useful only if you need index-based access.

10. Enumeration (legacy, mainly for Hashtable)

HashMap doesn’t have keys()/elements(), but you can wrap with Collections.enumeration():

java
Enumeration<String> en = Collections.enumeration(map.keySet());
while (en.hasMoreElements()) {
    System.out.println(en.nextElement());
}

Rarely used.

Summary table
#	Approach	Gives	Can remove while iterating?	Java version
1	for-each on entrySet()	key + value	No	5+
2	for-each on keySet()	key (+ get)	No	5+
3	for-each on values()	value	No	5+
4	Iterator on entrySet()	key + value	Yes (it.remove())	1.2+
5	Iterator on keySet()/values()	key or value	Yes	1.2+
6	map.forEach(BiConsumer)	key + value	No	8+
7	Stream	key + value	No (use removeIf instead)	8+
8	forEach on views	key / value / entry	No	8+
9	List copy + index loop	key (+ get)	Yes (on original map, as you iterate the copy)	1.2+
10	Enumeration wrapper	key or value	No	1.0+
Safe removal while iterating

Modifying the map directly inside a loop throws ConcurrentModificationException:

java
for (String key : map.keySet()) {
    if (key.equals("a")) map.remove(key);   // CME
}

Safe alternatives:

java
// 1. Iterator.remove()
map.entrySet().iterator()...it.remove();

// 2. removeIf (Java 8+), cleanest
map.entrySet().removeIf(e -> e.getValue() == 2);
map.keySet().removeIf(k -> k.equals("a"));
map.values().removeIf(v -> v == 3);

// 3. replaceAll to update values in place
map.replaceAll((k, v) -> v * 10);

Updating a value through entry.setValue() during iteration is allowed, since it isn’t a structural modification:

java
for (Map.Entry<String, Integer> e : map.entrySet()) {
    e.setValue(e.getValue() + 1);
}
Interview points

1. Which is the best way?
entrySet() with for-each (or map.forEach on Java 8+) when you need both key and value. It avoids the extra get() lookup.

2. Is iteration order guaranteed?
Not for HashMap. Use LinkedHashMap for insertion order or TreeMap for sorted order.

3. Time complexity of iteration?
O(capacity + size), since it walks the whole bucket array. A HashMap with a huge capacity but few entries is slow to iterate. This is why you shouldn’t over-size the initial capacity.

4. Fail-fast or fail-safe?
HashMap iterators are fail-fast (checked via modCount). ConcurrentHashMap iterators are weakly consistent: no CME, but they may or may not reflect concurrent updates.

5. keySet() + get() vs entrySet()?
keySet() + get() hashes each key again, so it’s an extra O(1) per element (and worse with collisions). entrySet() hands you the node directly.

One-line summary for interviews

“You can iterate a HashMap via for-each or Iterator over entrySet(), keySet() or values(), Map.forEach, forEach on the views, and Streams. entrySet() is the most efficient for key-value access, and Iterator.remove() or removeIf is the only safe way to remove during iteration.”

# Q : Explain in detail following code in java 
	productNames.stream().map(WebElement::getText).map(String::trim).collect(Collectors.toList());
====>
This line takes a list of Selenium WebElements (product names scraped from a web page), pulls out the visible text from each, trims whitespace, and collects the results into a List<String>.

java
List<String> names = productNames.stream()
        .map(WebElement::getText)
        .map(String::trim)
        .collect(Collectors.toList());
Here productNames is typically obtained like this:

java
List<WebElement> productNames = driver.findElements(By.cssSelector(".product-name"));
Step-by-step breakdown
1. productNames.stream()
Converts the List<WebElement> into a Stream<WebElement>. A stream is a pipeline for processing elements one at a time. It does not modify the original list.

2. .map(WebElement::getText)
map is an intermediate operation. It transforms each element in the stream into something else.

WebElement::getText is a method reference, shorthand for the lambda:

java
.map(element -> element.getText())
After this step the stream type changes from Stream<WebElement> to Stream<String>. getText() returns the visible (rendered) text of the element, with leading and trailing whitespace already stripped by Selenium. It may still contain inner newlines or unusual whitespace.

3. .map(String::trim)
Another transformation, equivalent to:

java
.map(text -> text.trim())
It removes leading and trailing whitespace from each string. The stream stays Stream<String>. This step is largely a safety net, since Selenium’s getText() normally trims already, but it is harmless and common in test code. Note that trim() does not remove whitespace inside the string, and in some cases it misses non-breaking spaces (\u00A0). In Java 11+, strip() handles Unicode whitespace better.

4. .collect(Collectors.toList())
collect is a terminal operation. It triggers the whole pipeline to run and gathers the results into a collection. Collectors.toList() produces a List<String> (an ArrayList in practice, though the spec doesn’t guarantee the type).

Key concepts to know for interviews
Lazy evaluation: Intermediate operations (map, filter, etc.) do nothing until a terminal operation (collect, forEach, count) is called. Nothing is executed until collect runs.

Method reference types:

WebElement::getText is an instance method of an arbitrary object of a particular type. The stream element becomes the receiver of the call.
String::trim is the same kind.
Equivalent traditional loop:

java
List<String> names = new ArrayList<>();
for (WebElement element : productNames) {
    names.add(element.getText().trim());
}
Combining the two maps: You could merge them into one, which is slightly more efficient (though the difference is negligible):

java
.map(e -> e.getText().trim())
Java 16+ alternative: .toList() can replace .collect(Collectors.toList()), but it returns an unmodifiable list, whereas Collectors.toList() returns a mutable one (in practice).

Common follow-ups in Selenium context
You often chain further operations, for example:

java
// Check a product exists
boolean found = productNames.stream()
        .map(WebElement::getText)
        .map(String::trim)
        .anyMatch(name -> name.equalsIgnoreCase("Laptop"));

// Filter and find the matching element itself
WebElement laptop = productNames.stream()
        .filter(e -> e.getText().trim().equals("Laptop"))
        .findFirst()
        .orElseThrow();
Pitfall: StaleElementReferenceException
Each getText() call hits the live DOM. If the page re-renders between locating the elements and running the stream, you may get a StaleElementReferenceException. In that case, re-locate the elements or use explicit waits before streaming.

One-line summary
Convert each WebElement to its text, trim it, and gather all the texts into a list.

# Q : what is map in stream in java how it use when to use it Explain in detail
===> map() in Java Streams
What is map?
map is an intermediate operation on a Stream. It takes each element of the stream, applies a function to it, and produces a new stream containing the transformed results. It is a one-to-one transformation: if you put in N elements, you get N elements out, but each one may be a different value or even a different type.

Signature:

java
<R> Stream<R> map(Function<? super T, ? extends R> mapper)
T is the input element type
R is the output element type
Function<T, R> is a functional interface with one method: R apply(T t)
So map converts Stream<T> into Stream<R>.

Simple mental model
Think of an assembly line. Each item comes in, a machine transforms it, and the transformed item goes out. The number of items stays the same.

[ "a", "b", "c" ]  --map(toUpperCase)-->  [ "A", "B", "C" ]
Basic examples
1. Transform values (same type)

java
List<Integer> nums = List.of(1, 2, 3, 4);

List<Integer> squares = nums.stream()
        .map(n -> n * n)
        .collect(Collectors.toList());
// [1, 4, 9, 16]
2. Change the type (String to Integer)

java
List<String> words = List.of("java", "selenium", "api");

List<Integer> lengths = words.stream()
        .map(String::length)
        .collect(Collectors.toList());
// [4, 8, 3]
3. Extract a field from objects

java
class Employee {
    private String name;
    private int salary;
    // constructor, getters
    public String getName() { return name; }
    public int getSalary() { return salary; }
}

List<String> names = employees.stream()
        .map(Employee::getName)
        .collect(Collectors.toList());
This is probably the most common real-world use of map.

4. Chaining multiple maps

java
List<String> result = names.stream()
        .map(String::trim)
        .map(String::toUpperCase)
        .map(s -> "Hello " + s)
        .collect(Collectors.toList());
Each map receives the output of the previous one.

Ways to write the function
The same transformation can be written three ways:

java
.map(s -> s.toUpperCase())      // lambda
.map(String::toUpperCase)       // method reference
.map(new Function<String, String>() {   // anonymous class (old style)
    public String apply(String s) { return s.toUpperCase(); }
})
Method references are preferred when the lambda just calls a single existing method.

How it works internally
map is lazy. Calling it does not process anything; it only adds a stage to the pipeline.
When a terminal operation (collect, forEach, count, reduce) is called, elements flow through the pipeline one at a time, not stage by stage.
The original source (the list) is never modified.
java
Stream.of("a", "b", "c")
      .map(s -> {
          System.out.println("map: " + s);
          return s.toUpperCase();
      })
      .forEach(s -> System.out.println("forEach: " + s));
Output:

map: a
forEach: A
map: b
forEach: B
map: c
forEach: C
Each element goes through the whole pipeline before the next one starts.

When to use map
Use map when you need to transform every element into something else:

Situation	Example
Extract a property from objects	.map(User::getEmail)
Convert type	.map(Integer::parseInt)
Clean or format data	.map(String::trim), .map(String::toLowerCase)
Compute a derived value	.map(price -> price * 1.18)
Wrap or convert to DTO	.map(e -> new EmployeeDTO(e.getName()))
Selenium: get text from elements	.map(WebElement::getText)
When NOT to use map
1. When you want to remove elements, use filter

java
// filter keeps or drops elements; it doesn't change them
.filter(n -> n > 10)
2. When each element produces multiple results, use flatMap

If your function returns a collection or stream, map gives you a nested structure:

java
List<List<String>> nested = List.of(List.of("a", "b"), List.of("c"));

nested.stream().map(List::stream);
// Stream<Stream<String>>  (nested, usually not what you want)

nested.stream().flatMap(List::stream);
// Stream<String>  -> a, b, c  (flattened)
3. When you only want a side effect, use forEach (e.g. printing). Don’t use map just to print or log.

4. When the transformation involves primitives heavily, prefer the specialized versions to avoid boxing:

java
.mapToInt(String::length)      // IntStream
.mapToDouble(Employee::getSalary)
.mapToLong(...)
These give you sum(), average(), max() directly:

java
int total = employees.stream()
        .mapToInt(Employee::getSalary)
        .sum();
map vs filter vs flatMap
Operation	Input to output	Purpose
map	N elements to N elements	Transform each element
filter	N elements to 0..N elements	Keep elements matching a condition
flatMap	N elements to any number	Transform each into a stream and flatten
Full realistic example (Selenium)
java
List<WebElement> rows = driver.findElements(By.cssSelector("table tr td:nth-child(2)"));

List<Integer> prices = rows.stream()
        .map(WebElement::getText)       // WebElement -> String
        .map(String::trim)              // String -> String
        .map(s -> s.replace("$", ""))   // remove currency symbol
        .map(Integer::parseInt)         // String -> Integer
        .collect(Collectors.toList());
Type changes through the pipeline: Stream<WebElement> to Stream<String> to Stream<String> to Stream<String> to Stream<Integer>.

Common interview points
map is an intermediate, lazy, stateless operation.
It takes a Function<T, R> and returns a Stream<R>.
It does not modify the source collection.
It is one-to-one, unlike flatMap, which is one-to-many.
Use mapToInt/Double/Long for primitives to avoid autoboxing overhead.
Avoid side effects inside map; the function should be pure (same input gives same output, and it changes nothing outside).
If a map function returns null, the null stays in the stream (it is not removed), and it can cause a NullPointerException in later steps like .map(String::trim).
Quick summary
map = “take each element, convert it into something else, and give me a stream of the converted results.”

# Q : How HashMap Works Internally Explain in detail with syntax
==> A HashMap in Java is a data structure from the java.util package that stores data in key-value pairs. It implements the Map interface and allows you to locate, insert, and delete data in constant time (O(1)) on average.
Internally, it works on the principles of hashing, array indexing, and collision resolution via chaining or treeification.

1. Basic Syntax & Code Example

java
import java.util.HashMap;
import java.util.Map;

public class HashMapExample {
    public static void main(String[] args) {
        // 1. Declaration & Initialization: HashMap<KeyType, ValueType>
        Map<String, Integer> inventory = new HashMap<>();

        // 2. Inserting elements: put(key, value)
        inventory.put("Apples", 50);
        inventory.put("Bananas", 20);
        inventory.put("Oranges", 35);
        
        // Overwriting an existing key: updates the value to 55
        inventory.put("Apples", 55); 

        // 3. Accessing elements: get(key)
        System.out.println("Apple stock: " + inventory.get("Apples")); // Output: 55
        System.out.println("Grapes stock: " + inventory.get("Grapes")); // Output: null

        // 4. Checking presence
        System.out.println("Has Bananas? " + inventory.containsKey("Bananas")); // true

        // 5. Removing an element: remove(key)
        inventory.remove("Oranges");

        // 6. Iterating through a HashMap
        for (Map.Entry<String, Integer> entry : inventory.entrySet()) {
            System.out.println(entry.getKey() + ": " + entry.getValue());
        }
    }
}
Use code with caution.

2. The Core Structure: Nodes and Buckets

The backbone of a HashMap is an internal array called the table. Each slot in this array is called a bucket.
• Each bucket holds a node object (Node<K, V>) that implements the Map.Entry<K, V> interface.
• A single node contains four distinct structural fields:
java
// Simplified internal Node class used by HashMap
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;    // The processed hash value of the key
    final K key;       // The actual storage key
    V value;           // The mapped value
    Node<K,V> next;    // Reference link to the next node in the same bucket
}
Use code with caution.

3. Step-by-Step Mechanics of put(key, value)

When you invoke map.put("Apples", 50), Java goes through the following sequence:

Step 1: Calculate the Hash

Java calls the key’s built-in hashCode() method to get an integer. To minimize bad distributions and prevent collisions, HashMap applies an extra supplementary hashing function (bitwise XORing the higher bits downward):
java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
Use code with caution.

Step 2: Calculate the Bucket Index

The calculated hash value is converted into a valid array boundary index using a fast bitwise AND operation:
java
index = hash & (n - 1); // where 'n' is the current capacity of the array table
Use code with caution.

Step 3: Insert the Node

• Case A (Bucket is empty): The node is created and placed directly into that calculated array slot.
• Case B (Collision occurs): If a node already occupies that slot, Java walks through the chain at that bucket, using equals() to evaluate the key:
	• If incomingKey.equals(existingKey) is true, it replaces the old value with the new one.
	• If it evaluates to false for all nodes in the chain, it appends the new node to the end of the line.

4. Collision Resolution & The Java 8 Treeification

When multiple keys evaluate to the exact same array index, it causes a hash collision. HashMap handles this via separate chaining, but optimizes it dynamically:
• Treeify Threshold (8): If a single bucket's linked list grows to more than 8 elements (and the overall map capacity is at least 64), Java automatically transforms that bucket's linked list into a self-balancing Red-Black Tree (TreeNode). This drops the worst-case search complexity from O(n) to \(O(\log n)\).
• Untreeify Threshold (6): If elements are deleted or during a resize the bucket size shrinks down to 6 elements or fewer, the tree converts back into a standard linked list to save memory overhead.

5. Capacity, Load Factor, and Resizing

To maintain its fast execution profile, the HashMap automatically expands itself:
• Initial Capacity (Default: 16): The starting length of the internal array table. It is strictly enforced to be a power of 2 because the index formula hash & (n-1) only acts as a clean modulo boundary when n is a power of 2.
• Load Factor (Default: 0.75): A measure of how full the map is allowed to get before it expands.
• Threshold (Capacity × Load Factor): For example, 16 × 0.75 = 12. When the 13th element is added, a resize triggers.

The Resizing Engine (Rehashing)

When the threshold is breached, the array size doubles (e.g., from 16 to 32). Because the value of n shifts, the index equation hash & (n-1) returns new index fields. Every single element in the map is recalculated and migrated into new bucket positions. This is an expensive O(n) computing block.

# Q : Would you like to see how to properly override hashCode() and equals() when using custom object classes as keys, or examine why ConcurrentHashMap should be used instead in multithreaded systems?

==> Here is a detailed look at both topics to give you a complete understanding of how to implement custom keys correctly and how to safely handle concurrency.

Part 1: Overriding equals() and hashCode() for Custom Keys

When you use a custom class as a key in a HashMap or HashSet, you must override both methods. If you do not, Java uses the default implementation from the Object class, which compares memory addresses. This means two distinct object instances with identical field values would be treated as completely different keys.

The Contract

1. Consistency: If obj1.equals(obj2) is true, then obj1.hashCode() must equal obj2.hashCode().
2. Reverse is not true: If two objects have the same hash code, they are not required to be equal (this is a hash collision).

Code Example: Implementing a Custom Key Class

java
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

// Make the class immutable (final fields) so the hashcode never changes while in the map
final class Student {
    private final int id;
    private final String name;

    public Student(int id, String name) {
        this.id = id;
        this.name = name;
    }

    // 1. Overriding equals()
    @Override
    public boolean equals(Object o) {
        // Reference check: Are they the exact same instance?
        if (this == o) return true;
        
        // Null and Class check
        if (o == null || getClass() != o.getClass()) return false;
        
        // Typecast and field comparison
        Student student = (Student) o;
        return id == student.id && Objects.equals(name, student.name);
    }

    // 2. Overriding hashCode()
    @Override
    public int hashCode() {
        // Generates a hash based on the exact same fields used in equals()
        return Objects.hash(id, name);
    }
}

public class CustomKeyExample {
    public static void main(String[] args) {
        Map<Student, String> studentMap = new HashMap<>();

        Student s1 = new Student(101, "Alice");
        studentMap.put(s1, "A+ Grade");

        // Creating a structurally identical object instance
        Student s2 = new Student(101, "Alice");

        // Without overriding equals/hashCode, this would return 'null'
        System.out.println("Result: " + studentMap.get(s2)); // Output: A+ Grade
    }
}
Use code with caution.

Part 2: Why Use ConcurrentHashMap in Multithreaded Systems?

A standard HashMap is not thread-safe. If multiple threads try to write (put()) or restructure the map at the same time, it can cause data corruption, race conditions, or silent data loss.

Why not just use Hashtable or Collections.synchronizedMap()?

Both Hashtable and SynchronizedMap achieve thread safety using a monolithic lock. They lock the entire map object for every single read or write operation. If Thread A is updating bucket 1, Thread B cannot read bucket 5 until Thread A is completely finished. This creates massive performance bottlenecks.

The ConcurrentHashMap Solution: Lock Striping

ConcurrentHashMap provides full thread safety without locking the entire map. It uses a technique called Lock Striping or Bucket-Level Locking (optimized heavily in Java 8+ using Compare-And-Swap (CAS) operations and synchronized blocks on individual bucket heads).

Attribute	HashMap	Hashtable / SynchronizedMap	ConcurrentHashMap
Thread Safety	No	Yes	Yes
Locking Strategy	None	Whole Map Lock (Single thread access only).	Bucket-Level Lock (Only locks the specific slot being modified).
Read Operations	Not safe	Blocked if a write lock is active.	Lock-Free. Threads can read concurrently without blocking.
Null Support	Key/Value can be null.	No nulls allowed.	No nulls allowed.
Performance	Highest (Single Thread)	Very Low (High Thread Contention)	High (Scales exceptionally well with many threads).


Quick Syntax Example

java
import java.util.concurrent.ConcurrentHashMap;
import java.util.Map;

public class ConcurrentExample {
    public static void main(String[] args) {
        // Instantiate a thread-safe map
        Map<String, Integer> sharedMap = new ConcurrentHashMap<>();
        
        // ConcurrentHashMap introduces useful atomic operations
        sharedMap.put("Counter", 1);
        
        // Atomically update a value safely across multiple threads
        sharedMap.computeIfPresent("Counter", (key, val) -> val + 1);
    }
}
Use code with caution.
