# Status code 
HTTP status codes are three-digit numbers returned by a server to indicate the outcome of an HTTP request. Each code is paired with a standard reason phrase that explains its specific meaning.
The codes are divided into five major categories based on their first digit:

Code Range	Category	General Meaning
1xx		Informational	Request received, continuing process.
2xx		Success	Action  successfully received, understood, and accepted.
3xx		Redirection	Further action needs to be taken to complete the request.
4xx		Client Error	The request contains bad syntax or cannot be fulfilled.
5xx		Server Error	The server failed to fulfill an apparently valid request.


Complete List of Common Standard HTTP Status Codes


1xx Informational

• 100 Continue: The server has received the request headers and the client should proceed to send the request body.

• 101 Switching Protocols: The requester has asked the server to switch protocols (e.g., upgrading to WebSockets).

• 103 Early Hints: Used to return some response headers before the final HTTP message.

2xx Success

• 200 OK: The standard response for successful HTTP requests.

• 201 Created: The request has been fulfilled, resulting in the creation of a new resource.

• 202 Accepted: The request has been accepted for processing, but processing is not complete.

• 204 No Content: The server successfully processed the request but is not returning any content in the response body.

• 206 Partial Content: The server is delivering only part of the resource due to a range header sent by the client.

3xx Redirection

• 301 Moved Permanently: The requested resource has been assigned a new permanent URI.

• 302 Found: The requested resource resides temporarily under a different URI.

• 304 Not Modified: Indicates that the resource has not been modified since the version cached by the client.

• 307 Temporary Redirect: The request should be repeated with another URI, but future requests should still use the original URI.

• 308 Permanent Redirect: The request and all future requests should be repeated using another URI.

4xx Client Error

• 400 Bad Request: The server cannot process the request due to a client error (e.g., malformed request syntax).

• 401 Unauthorized: The request requires user authentication. (Strictly speaking, this means "unauthenticated").

• 403 Forbidden: The server understood the request but refuses to authorize it.

• 404 Not Found: The requested resource could not be found on the server.

• 405 Method Not Allowed: The request method (GET, POST, etc.) is not supported for the requested resource.

• 408 Request Timeout: The server timed out waiting for the request from the client.

• 409 Conflict: The request could not be completed due to a conflict with the current state of the target resource.

• 422 Unprocessable Entity: The request was well-formed but was unable to be followed due to semantic errors.

• 429 Too Many Requests: The user has sent too many requests in a given amount of time (rate-limiting).

301, 302, 307, 308—redirect counts. Spikes can mean misconfigured routing or a deploy that broke canonical URLs.
400—malformed requests. Usually a consumer-side change.
401, 403—auth and permission failures. Often a token, IAM, or WAF change.
404—missing resources. Background noise as one-offs; a release problem in bursts.
408—client timeouts. Worth alerting at sustained rates; signals slow downstream calls.
429—rate limiting. Either you’re being throttled or your throttle is too aggressive.
500, 502, 503, 504—application, upstream, capacity, and gateway timeout failures. These page on-call.
520-526—Cloudflare edge failures. If you’re behind Cloudflare, these are critical signals because they isolate the failure to the edge-to-origin path.

Correct:
PUT /booking/123

Incorrect:
PUT /booking

# Q : how to use objectMapper 

As a 3.5-year experienced Rest Assured + Java automation engineer, I use Jackson's ObjectMapper mainly to convert Java objects to JSON and JSON responses to Java objects.

1. Add Jackson dependency

If you're using Rest Assured, Jackson is commonly used for JSON serialization/deserialization.

<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
</dependency>
2. Java Object → JSON

Suppose I have a POJO:

public class User {

    private String username;
    private String password;

    public User() {
    }

    public User(String username, String password) {
        this.username = username;
        this.password = password;
    }

    // getters and setters
}

I can convert it to JSON using ObjectMapper:

ObjectMapper mapper = new ObjectMapper();

User user = new User("standard_user", "secret_sauce");

String jsonRequest = mapper.writeValueAsString(user);

System.out.println(jsonRequest);

Output:

{
  "username": "standard_user",
  "password": "secret_sauce"
}

This is called serialization.

Java Object
     ↓
ObjectMapper
     ↓
JSON

Suppose the API returns:

{
  "username": "standard_user",
  "password": "secret_sauce"
}

I can convert it back to a Java object:

ObjectMapper mapper = new ObjectMapper();

User user = mapper.readValue(jsonResponse, User.class);

System.out.println(user.getUsername());

This is called deserialization.

JSON
 ↓
ObjectMapper
 ↓
Java Object

@Test

        "secret_sauce"
    );

    ObjectMapper mapper = new ObjectMapper();

    String requestBody = mapper.writeValueAsString(user);

    given()
        .contentType(ContentType.JSON)
        .body(requestBody)
    .when()
        .post("/users")
    .then()
        .statusCode(201);
}

However, Rest Assured can also serialize POJOs automatically if Jackson is available:

given()
    .contentType(ContentType.JSON)
    .body(user)
.when()
    .post("/users");

So I don't always need to explicitly call writeValueAsString().

5. Deserialize API response

Suppose the API response is:

{
    "id": 101,
    "username": "john"
}

POJO:

public class UserResponse {

    private int id;
    private String username;

    // getters and setters

Then:

Response response =

Why do I use ObjectMapper?

In my framework, it is useful when the JSON becomes complex.

Instead of doing:

response.jsonPath().getInt("user.id");
response.jsonPath().getString("user.email");

I can deserialize the entire response into a Java model:

UserResponse user = mapper.readValue(
    response.asString(),
    UserResponse.class
);

Then I work with normal Java objects.

Interview answer

“I use Jackson's ObjectMapper for JSON serialization and deserialization. writeValueAsString() converts a Java POJO into a JSON string, which I can send as an API request body. readValue() converts a JSON response into a Java POJO, which makes response validation easier, especially for complex nested JSON. In Rest Assured, Jackson can also be integrated automatically so Rest Assured can serialize and deserialize POJOs.”

Easy way to remember:

writeValueAsString() → Java Object → JSON
readValue()          → JSON → Java Object

# Q :  How would you store API response data dynamically?
===> In my automation framework, I store API response data dynamically using Rest Assured with JsonPath, Java collections, or POJO classes, depending on how I need to use the response data in subsequent test steps.

For example, if I create a user through a POST API and receive a dynamically generated user ID, I store that ID and use it in subsequent GET, PUT, or DELETE requests rather than hardcoding it.

1. Store API response data using Rest Assured

Suppose a POST request creates a student and returns this response:

{
  "id": 101,
  "name": "Uzma",
  "email": "uzma@example.com"
}

The ID might change each time the test runs, so I extract it dynamically.

import io.restassured.response.Response;
import static io.restassured.RestAssured.given;

public class StudentApiTest {

    public static void main(String[] args) {

        Response response =
            given()
                .header("Content-Type", "application/json")
                .body("{\"name\":\"Uzma\","
                    + "\"email\":\"uzma@example.com\"}")
            .when()
                .post("http://localhost:3000/students")
            .then()
                .statusCode(201)
                .extract()
                .response();

        // Extract dynamically generated response data
        int studentId = response.jsonPath().getInt("id");
        String studentName =
                response.jsonPath().getString("name");
        String email =
                response.jsonPath().getString("email");

        System.out.println("Student ID: " + studentId);
        System.out.println("Student Name: " + studentName);
        System.out.println("Email: " + email);

        // Reuse studentId in a subsequent GET request
        given()
            .pathParam("id", studentId)
        .when()
            .get("http://localhost:3000/students/{id}")
        .then()
            .statusCode(200);
    }
}

Why this approach?

JsonPath extracts individual fields from the JSON response.

The generated ID is stored in a Java variable.

The same ID is reused in the next API request.

This eliminates hardcoded IDs and makes the test repeatable.

The example assumes the API returns HTTP 201 Created and the response contains an integer id.

2. Store response data in a Map

When I need to reuse multiple response values across test steps, I can store them in a Map<String, Object>.

Map<String, Object> testData = new HashMap<>();

testData.put("studentId",  response.jsonPath().getInt("id"));

testData.put("studentName", response.jsonPath().getString("name"));

testData.put("email",  response.jsonPath().getString("email"));

// Retrieve data later
int id = (int) testData.get("studentId");
String name = (String) testData.get("studentName");

This is useful when the response contains several fields that subsequent requests or assertions need.

3. Store response data using a POJO

For larger responses or strongly typed data, I prefer a POJO (Plain Old Java Object).

public class Student {

    private int id;
    private String name;
    private String email;

    public int getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }
}

Deserialize the response into the POJO:

Student student = response.as(Student.class);

int id = student.getId();
String name = student.getName();

This approach is easier to maintain when working with complex JSON responses and multiple API endpoints.

4. Where would I store this data in a framework?

Requirement : Approach
1. Extract a single response field : JsonPath
2. Reuse multiple fields in test steps : Map<String, Object>
3. Handle complex, structured JSON : POJO classes
4. Share data across Cucumber steps : Scenario-scoped context object
5. Share data between TestNG methods : Explicitly managed test context or dependency
6. Persist data across separate executions : Database or external test-data store, if needed

For parallel execution, I avoid using shared mutable static variables because one test could overwrite another test's data. I use scenario-scoped or test-scoped storage instead.

Interview conclusion

"In my Rest Assured framework, I extract dynamically generated values from API responses using JsonPath and store them in variables, maps, or POJOs. For example, after creating a student, I capture its ID and use it in subsequent GET or DELETE requests. This makes the automation data-driven, reusable, and independent of hardcoded test data. I also ensure that stored data has the correct scope when tests execute in parallel."

# Q :  Meaning of 405 status code in Postman , what does it means and how to resolve it?

1. What does 405 mean in Postman?
For example, suppose I send this request in Postman:
GET https://simple-books-api.glitch.me/orders

But the API endpoint supports only POST for the operation I'm trying to perform. The server may return:
405 Method Not Allowed

This means the HTTP method is not allowed for that resource. The response may include an Allow header indicating which methods are supported.
2. Common reasons for a 405 error
- Incorrect HTTP method: Using GET instead of POST, or POST instead of DELETE.
- Incorrect API endpoint: The URL may point to a resource that does not support the selected method.
- API documentation mismatch: The method used in Postman does not match the API contract.
- Server or proxy configuration: The web server, gateway, or proxy may block certain HTTP methods.
- Trailing slash or routing differences: Some server configurations handle routes with and without a trailing slash differently.

3. How to resolve a 405 error in Postman
1. Verify the API documentation and confirm the supported HTTP method.
2. Check the endpoint URL and resource path.
3. Inspect the response headers, especially Allow, if present.
4. Verify that the request body and headers match the API requirements.
5. If the method is correct, ask the backend team to check routing, gateway, or server configuration.

Important: Missing or invalid authentication usually results in 401 or 403, rather than 405, although server implementations can vary.

Incorrect request:
given()
    .baseUri("https://simple-books-api.glitch.me")
.when()
    .put("/status")

    .statusCode(405);

    .baseUri("https://simple-books-api.glitch.me")
.when()
    .get("/status")
.then()
    .statusCode(200);

The expected status code depends on the API's actual contract.
5. Difference between 404 and 405
Status code		|	Meaning
404 Not Found		|	The requested resource or route was not found.
405 Method Not Allowed	|	The resource exists or is recognized, but the HTTP method is not permitted for it.

# Q : What are the different types of API authentication?
===> In API testing, authentication is used to verify the identity of a user or client before allowing access to an API. The main types of API authentication I work with or consider during testing are Basic Authentication, Bearer Token Authentication, API Key Authentication, OAuth 2.0, JWT-based authentication, and client certificate authentication.
1. Types of API authentication
Authentication type : 	How it works :	Example
1. Basic Authentication	: Sends a username and password encoded using Base64 in the Authorization header. :	Authorization: Basic <base64-value>
2. Bearer Token Authentication : Sends an access token in the Authorization header. :	Authorization: Bearer <token>
3. API Key Authentication : 	Uses a key to identify or authorize an API client, commonly through a header. :	x-api-key: abc123
4. OAuth 2.0 : 	Uses access tokens issued through an authorization framework to grant scoped access. :	Access token obtained from an authorization server
5. JWT Authentication :  Uses a signed JSON Web Token that the API validates. Often implemented with bearer tokens. :	Authorization: Bearer <JWT>
6. Client Certificate / mTLS :	Uses client certificates to authenticate the client during a TLS handshake. :	Certificate-based client identity
7. HMAC Authentication	: Uses a cryptographic signature generated from a secret and request data. :	Signature in an authorization header

Important distinction: Bearer authentication describes how a token is presented. JWT describes a token format. OAuth 2.0 is an authorization framework that can issue access tokens, including JWTs or opaque tokens.

# Q : What is JWT token?
===> JWT stands for JSON Web Token. It is a compact, URL-safe token format used to securely transmit claims between two parties. In API testing, JWT is commonly used to authenticate users and carry information about their identity and permissions.
For example, when a user logs in successfully, the server may generate a JWT and return it to the client. The client sends that token in subsequent API requests to access protected resources.
1. Structure of a JWT
A JWT typically consists of three parts separated by dots (.).
Header
Token type and signing algorithm


Payload
Claims such as user ID, role, and expiration


Signature
Used to verify token integrity and authenticity


A JWT looks like this:
xxxxx.yyyyy.zzzzz


- Header: Specifies the signing algorithm, such as HS256.
- Payload: Contains claims such as sub (subject), role, and exp (expiration time).
- Signature: Allows the receiver to verify that the token has not been altered and was signed by a trusted party.

Important: A signed JWT is not automatically encrypted. Its header and payload can usually be decoded, so passwords and other sensitive information should not be stored in them.
2. How does JWT authentication work?
1. The user sends login credentials to the authentication API.
2. The server validates the credentials and generates a signed JWT.
3. The client receives and stores the token securely.
4. The client sends the token with subsequent requests using the Authorization header.
5. The server validates the signature, expiration, and required claims before granting access.
Example request header:
Authorization: Bearer <JWT_TOKEN>

- Valid JWT with insufficient permissions → typically 403 Forbidden.

4. JWT vs. session-based authentication
JWT-based authentication :	Session-based authentication
1. Client sends a token with requests. : 	Client typically sends a session ID in a cookie.

# Q : How do you handle 429 rate limits in API automation tests?
==> In my API automation framework, I handle HTTP 429 – Too Many Requests by implementing retry logic with exponential backoff, respecting the Retry-After header, and controlling the rate of API requests.

A 429 response usually indicates that the API has exceeded its allowed request limit within a specific time window.

My approach involves the following steps:
1. Check the response: Verify whether the API returns status code 429.
2. Read the Retry-After header: If provided, wait for the specified duration before retrying.
3. Implement exponential backoff: If the header is missing, gradually increase the wait time between retries, for example, 1, 2, and 4 seconds.
4. Limit retries: Set a maximum retry count to avoid infinite loops and unnecessary server load.
5. Control parallel execution: Reduce concurrent requests in TestNG or configure rate limiting when multiple scenarios hit the same API.
6. Validate the final response: After retrying, verify the expected status code and response body. If the limit persists, report the failure with useful logs.
I also avoid blindly retrying every failed request. For example, I retry a 429 only according to the API's rate-limit policy, and I handle non-idempotent operations such as POST carefully to avoid creating duplicate records.
Java + Rest Assured example
import io.restassured.RestAssured;
import io.restassured.response.Response;

public class RateLimitHandler {

    public static Response getWithRetry(String endpoint) throws InterruptedException {

        int maxRetries = 3;
        int retryCount = 0;

        while (true) {
            Response response = RestAssured
                    .given()
                    .get(endpoint);

            if (response.statusCode() != 429) {
                return response;
            }

            if (retryCount >= maxRetries) {
                throw new RuntimeException( "API rate limit exceeded after retries. Status: " + response.statusCode()
                );
            }

            String retryAfter = response.getHeader("Retry-After");

            long waitSeconds;

            if (retryAfter != null  && retryAfter.matches("\\d+")) {
                waitSeconds = Long.parseLong(retryAfter);
            } else {
                waitSeconds = (long) Math.pow(2, retryCount);
            }

            System.out.println("Received 429. Retrying after "+ waitSeconds + " seconds."
            );

            Thread.sleep(waitSeconds * 1000);
            retryCount++;
        }
    }

    public static void main(String[] args) throws InterruptedException {

        Response response = getWithRetry("https://api.example.com/users");

        System.out.println("Final status: "+ response.statusCode());

        response.then().statusCode(200);
    }
}

Note: This example assumes Retry-After contains a number of seconds. HTTP also permits an HTTP-date value, which a production implementation should parse. The example uses exponential backoff without jitter; for parallel tests, adding random jitter helps prevent retries from occurring simultaneously.
How I integrate this into a Cucumber framework
I keep retry logic in a reusable API utility or request wrapper rather than duplicating it in every step definition.

For example:
Scenario: Get users when rate limiting occurs
  When I send a GET request to "/users" with rate-limit retry enabled
  Then the response status code should be 200

The step definition calls the reusable Rest Assured method, while TestNG handles test execution and reporting. I log the retry count, response status, Retry-After value, and final outcome for debugging.
Possible interviewer follow-up: Should we always retry a 429?
My answer: No. First, I check whether the test is exceeding the API's documented quota or whether the rate limit is caused by excessive parallel execution. For functional tests, I may validate that the API returns 429 when the limit is exceeded. For normal business-flow tests, I use bounded retries and backoff where appropriate. I also distinguish between an expected rate-limit response and an unexpected one so that retries do not hide genuine defects.

Key point: I handle 429 responses through bounded retries, Retry-After, exponential backoff, and controlled concurrency, while keeping rate-limit validation separate from normal API functional testing

4. Implement dynamic schema validation
import io.restassured.response.Response;
import io.restassured.module.jsv.JsonSchemaValidator;

import java.io.InputStream;

import static org.hamcrest.MatcherAssert.assertThat;
import static io.restassured.module.jsv.JsonSchemaValidator .matchesJsonSchema;

public class SchemaValidator {

    public static void validateSchema( Response response, String schemaFile) {

        String schemaPath = "/schemas/" + schemaFile;

        try (InputStream schema =  SchemaValidator.class.getResourceAsStream(schemaPath)) {

            if (schema == null) {
                throw new IllegalArgumentException("Schema file not found: " + schemaPath );
            }
            assertThat( response.asString(), matchesJsonSchema(schema));

        } catch (java.io.IOException e) {
            throw new RuntimeException("Unable to read schema: " + schemaPath, e );
        }
    }
}
The schemaFile parameter allows the framework to select different schemas at runtime.

    }
}
Here, response is assumed to be populated by the request step. In a real framework, I would share it through scenario-scoped context or dependency injection rather than use a static global response.

import static io.restassured.RestAssured.*;

# Q : How would you store API response data dynamically? in rest assured java
==> In REST Assured (Java), the best way to store API response data dynamically is by extracting the response as a Map<String, Object> (for single JSON objects) or a List<Map<String, Object>> (for JSON arrays). This approach avoids the need to create rigid, predefined POJO classes when the response structure is unpredictable or highly dynamic.
You can achieve this using REST Assured's built-in JsonPath extractor combined with a library like Jackson or Gson on your classpath.

1. Storing a Dynamic JSON Object

If the API returns a standard JSON object { ... } with varying keys, extract it directly into a Java Map.
java
import io.restassured.RestAssured;
import io.restassured.response.Response;
import java.util.Map;

public class DynamicResponseExample {
    public void captureDynamicObject() {
        Response response = RestAssured.get("https://example.com");

        // Extract the response body dynamically into a Map
        Map<String, Object> dynamicData = response.jsonPath().get("$"); 
        // Note: "$" or "" represents the root elements of the JSON

        // You can now iterate over keys or fetch data dynamically
        for (String key : dynamicData.keySet()) {
            System.out.println("Key: " + key + " -> Value: " + dynamicData.get(key));
        }

        // Access specific deep nested values dynamically if needed
        String name = (String) dynamicData.get("name");
    }
}
Use code with caution.

2. Storing a Dynamic JSON Array

If the API returns a list of items [ { ... }, { ... } ] where the structure inside can change, extract it into a List of maps.
java
import io.restassured.RestAssured;
import java.util.List;
import java.util.Map;

public class DynamicArrayExample {
    public void captureDynamicList() {
        // Extract the root array into a List of Maps
        List<Map<String, Object>> dynamicList = RestAssured.get("https://example.com")
                .jsonPath()
                .getList("$");

        // Access elements dynamically
        Map<String, Object> firstProduct = dynamicList.get(0);
        System.out.println("First Product Name: " + firstProduct.get("productName"));
    }
}
Use code with caution.

3. Extracting Specific Nested Blocks Dynamically

If only a specific part of your response is dynamic, you can isolate it by passing a GPath expression directly into jsonPath().get().
java
import io.restassured.RestAssured;
import java.util.Map;

public class NestedDynamicExample {
    public void captureNestedData() {
        // Extracting just the 'metadata' block which changes dynamically based on the request
        Map<String, Object> metadata = RestAssured.get("https://example.com")
                .jsonPath()
                .get("data.profile.metadata");

        System.out.println("Dynamic Metadata Type: " + metadata.get("accountType"));
    }
}
Use code with caution.

Alternative: Storing Raw JSON as a JsonPath Object

If you don't want to cast variables to Map or List immediately, you can store the entire structural layout as a reusable JsonPath instance. This allows you to query fields on the fly using dot-notation.

import io.restassured.RestAssured;

# Q : Are you planning to pass this stored data into a subsequent API request (like chaining a token or ID), or are you trying to assert values against a database? Tell me your end goal so I can show you how to structure the validation steps.
==> Since you are chaining data from one API response into a subsequent request, the most efficient pattern is to use REST Assured's request chaining model using JsonPath.
Here is a complete, production-ready example showing how to extract a dynamic token or ID from a login/creation endpoint and inject it straight into the headers or body of the next API call.

Complete Chaining Example

java
import io.restassured.RestAssured;
import io.restassured.http.ContentType;
import io.restassured.path.json.JsonPath;
import org.testng.annotations.BeforeClass;
import org.testng.annotations.Test;

import java.util.HashMap;
import java.util.Map;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

public class ApiChainingTest {

    private String authToken;
    private int generatedUserId;

    @BeforeClass
    public void setup() {
        RestAssured.baseURI = "https://example.com";
    }

    @Test(priority = 1)
    public void loginAndExtractDataDynamically() {
        // 1. Define login payload
        Map<String, String> credentials = new HashMap<>();
        credentials.put("username", "test_user");
        credentials.put("password", "SecurePass123!");

        // 2. Execute request and extract the raw JsonPath object immediately
        JsonPath responseParser = given()
                .contentType(ContentType.JSON)
                .body(credentials)
            .when()
                .post("/auth/login")
            .then()
                .statusCode(200)
                .extract()
                .jsonPath();

        // 3. Store the dynamic values into class variables
        authToken = responseParser.getString("data.session.token");
        generatedUserId = responseParser.getInt("data.user.id");

        System.out.println("Extracted Token: " + authToken);
        System.out.println("Extracted User ID: " + generatedUserId);
    }

    @Test(priority = 2, dependsOnMethods = {"loginAndExtractDataDynamically"})
    public void useExtractedDataInSubsequentRequest() {
        // 4. Inject the dynamically stored variables into the next request
        given()
            .header("Authorization", "Bearer " + authToken) // Injecting token in header
            .pathParam("userId", generatedUserId)           // Injecting ID as path parameter
            .contentType(ContentType.JSON)
        .when()
            .get("/users/{userId}/profile")
        .then()
            .statusCode(200)
            .body("status", equalTo("success"));
    }
}
Use code with caution.

Best Practices for Dynamic API Chaining

• Use dependsOnMethods (TestNG/JUnit): Always ensure the second test depends on the first. If the data-extraction API fails, the subsequent tests will skip automatically instead of throwing null pointer exceptions.
• Keep Extraction Specific: Instead of mapping the whole response payload into a generic Java Map, use explicit GPath notation (like "data.session.token") on the jsonPath() object to pluck out only the fields you need.
• Handle Data Types Safely: Ensure you match the original JSON type exactly when calling getters (e.g., use .getInt() for unquoted numerical IDs, .getString() for alphanumeric tokens).

# Q : GraphQL API request automation in REST Assured?
===> To automate GraphQL API requests using REST Assured, the core principle is treating the GraphQL request as a standard HTTP POST request. Since GraphQL queries and mutations are not native JSON, they must be wrapped inside a JSON payload payload body under a "query" key before being sent.
Here is a comprehensive breakdown of how to structure your payload, followed by a complete code implementation.

1. Understanding the Payload Structure

Every GraphQL request sent via REST Assured must have:
1. HTTP Method: POST
2. Header: Content-Type: application/json
3. JSON Body Structure:json
{
  "query": "query { ... } or mutation { ... }",
  "variables": { "key": "value" }
}

2. Method 1: Using a Direct String Payload (Quick & Simple)

For simple queries, you can pass the JSON-wrapped GraphQL query directly as an escaped Java string.
java
import io.restassured.RestAssured;
import io.restassured.http.ContentType;
import org.testng.annotations.Test;
import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

public class GraphQLStringTest {

    @Test
    public void testGraphQLQueryString() {
        RestAssured.baseURI = "https://trevorblades.com"; // Example Public GraphQL API

        // 1. Define the wrapped GraphQL query in a valid JSON format
        String jsonPayload = "{\"query\": \"query { country(code: \\\"BR\\\") { name capital currency } }\"}";

        // 2. Automate the request using REST Assured
        given()
            .contentType(ContentType.JSON)
            .body(jsonPayload)
        .when()
            .post("/")
        .then()
            .statusCode(200)
            .body("data.country.name", equalTo("Brazil"))
            .body("data.country.capital", equalTo("Brasília"))
            .log().all();
    }
}

3. Method 2: Using POJOs & Variables (Best Practice for Frameworks)

Hardcoding escaped strings becomes tedious for large queries or dynamic inputs. The standard production approach is creating a reusable POJO (Plain Old Java Object) to model the payload, allowing Jackson/Gson to automatically handle JSON serialization.

Step A: Create the Request POJO

java
public class GraphQLWrapper {
    private String query;
    private Object variables; // Can be a Map or another POJO

    public GraphQLWrapper(String query, Object variables) {
        this.query = query;
        this.variables = variables;
    }

    // Getters and Setters
    public String getQuery() { return query; }
    public void setQuery(String query) { this.query = query; }
    public Object getVariables() { return variables; }
    public void setVariables(Object variables) { this.variables = variables; }
}

Step B: Write the Test Case with Dynamic Variables

java
import io.restassured.RestAssured;
import io.restassured.http.ContentType;
import org.testng.annotations.Test;
import java.util.HashMap;
import java.util.Map;

# Q :  Deserializing nested JSON API response to Java POJO?
==> In my project we deserialize API responses into POJOs rather than working with raw JSON strings, because it gives us type safety, readable assertions and reusable models.

The approach is to mirror the JSON structure with classes. Each nested object becomes its own class, and each JSON array becomes a List<T>. For example, if the response has a user with an address object and a list of orders, I create User, Address and Order classes, and User holds an Address and a List<Order>.

I use Jackson, since REST Assured uses it by default when it’s on the classpath. I annotate the classes with @JsonIgnoreProperties(ignoreUnknown = true) so that if the backend adds a new field, our tests don’t break with an UnrecognizedPropertyException. If a JSON key doesn’t match my Java naming, I use @JsonProperty("order_id").

In REST Assured, I do it in one line:

java
User user = given()
		.spec(requestSpec)
           .when()
		.get("/users/101")
           .then()
		.statusCode(200)
        	.extract()
		.as(User.class);

If I only need a nested part, I use JsonPath:

java
Address address = response.jsonPath().getObject("address", Address.class);
List<Order> orders = response.jsonPath().getList("orders", Order.class);

If the root is an array or a generic type, Class isn’t enough because of type erasure, so I use TypeReference with ObjectMapper:

java
List<User> users = mapper.readValue(json, new TypeReference<List<User>>() {});

Then the assertions become simple and readable:

java
Assert.assertEquals(user.getAddress().getCity(), "Pune");
Assert.assertEquals(user.getOrders().size(), 2);

In Playwright (Java or TypeScript), it’s the same idea. Playwright’s APIResponse gives me the body as text or JSON, and I map it myself. In Java, I call response.text() and pass it to ObjectMapper.readValue(). In TypeScript, I’d use await response.json() and cast it to an interface.

Things I’ve handled in practice:

Missing fields: I use wrapper types like Integer instead of int, so I can tell ‘missing’ (null) from ‘zero’.
Dates: I register JavaTimeModule for LocalDate and LocalDateTime.
Dynamic or unknown structures: I fall back to Map<String, Object> or JsonNode with readTree().
Boilerplate: I use Lombok (@Data) so I don’t write getters and setters by hand, and I can generate POJOs from a sample JSON with tools like jsonschema2pojo.
Same POJOs for requests: I use the same classes for request payloads with writeValueAsString(), so the framework has one model for both directions.”


#--------------------------------#
Short answer: map the JSON structure to a matching class structure, then let Jackson (or Gson) do the work. Nested objects become nested classes, arrays become List<T>.

Sample JSON

json
{
  "id": 101,
  "name": "Uzma",
  "address": {
    "city": "Pune",
    "pincode": "411001"
  },
  "orders": [
    { "orderId": "A1", "amount": 499.5 },
    { "orderId": "A2", "amount": 120.0 }
  ]
}

POJOs (Jackson)

java
import com.fasterxml.jackson.annotation.JsonIgnoreProperties;
import com.fasterxml.jackson.annotation.JsonProperty;
import java.util.List;

@JsonIgnoreProperties(ignoreUnknown = true)
public class User {
    private int id;
    private String name;
    private Address address;
    private List<Order> orders;

    // getters and setters
}

@JsonIgnoreProperties(ignoreUnknown = true)
public class Address {
    private String city;
    private String pincode;

    // getters and setters
}

@JsonIgnoreProperties(ignoreUnknown = true)
public class Order {
    private String orderId;
    private double amount;

    // getters and setters
}

Jackson needs a no-arg constructor plus getters/setters (or public fields). Use @JsonProperty("order_id") when the JSON key differs from the field name.

Deserializing

java
ObjectMapper mapper = new ObjectMapper();

// From a String
User user = mapper.readValue(jsonString, User.class);

// From a REST Assured response
User user = response.as(User.class);
// or
User user = response.jsonPath().getObject("", User.class);

// Only a nested part of the response
Address address = response.jsonPath().getObject("address", Address.class);
List<Order> orders = response.jsonPath().getList("orders", Order.class);

Top-level array or generic types

User.class won’t work when the root is an array, or you have a generic type. Use TypeReference:

java
List<User> users = mapper.readValue(json, new TypeReference<List<User>>() {});
Map<String, Object> map = mapper.readValue(json, new TypeReference<Map<String, Object>>() {});

Common interview follow-ups

Unknown fields: by default Jackson throws UnrecognizedPropertyException. Fix with @JsonIgnoreProperties(ignoreUnknown = true) or mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false).
Different key names: @JsonProperty("first_name") private String firstName;
Wrapped root or deeply nested single value: use mapper.readTree(json).path("a").path("b") and then treeToValue(node, Target.class).
Dates: register JavaTimeModule and use @JsonFormat(pattern = "yyyy-MM-dd") for LocalDate.
Null/missing fields: primitives default to 0/false, wrappers (Integer) stay null, so use wrappers when you need to tell “missing” from “zero”.
Polymorphic types: @JsonTypeInfo and @JsonSubTypes.
Java records (Java 16+): Jackson 2.12+ supports them directly: record Address(String city, String pincode) {}.
Serialization vs deserialization: writeValueAsString() goes POJO to JSON, readValue() goes JSON to POJO.

Gson equivalent

java
Gson gson = new Gson();
User user = gson.fromJson(json, User.class);

Type listType = new TypeToken<List<User>>() {}.getType();
List<User> users = gson.fromJson(json, listType);

Gson ignores unknown fields by default and uses @SerializedName("order_id") for renaming.

One-liner for interviews: “I model the JSON as nested POJOs, use List<T> for arrays, annotate with @JsonIgnoreProperties(ignoreUnknown = true) for resilience, and call ObjectMapper.readValue(). For generics I use TypeReference.

# Q : 1. Why POJO instead of JsonPath?

“It depends on the size and reuse of the response. For one or two values, like grabbing a token or an ID to chain into the next request, I use JsonPath because it’s quick:

java
String token = response.jsonPath().getString("token");

But for anything larger or reused, I prefer POJOs. They give me compile-time safety, so a typo in getAdress() fails at compile time, while a typo in a JsonPath string like "adress.city" only fails at runtime, and often silently returns null. They also support IDE auto-complete and safe refactoring, and the same model can be reused across many tests and for building request payloads. Assertions on the whole object also read better:

java
Assert.assertEquals(user.getAddress().getCity(), "Pune");

The trade-off is that POJOs mean more classes to maintain, and they can break if the contract changes, which I handle with @JsonIgnoreProperties(ignoreUnknown = true). In practice I use both: JsonPath for quick extraction and chaining, POJOs for full response validation.”

2. What if the JSON has a field named class or default?

“Those are reserved keywords in Java, so I can’t use them as field names. I keep the Java name valid and map it with @JsonProperty:

java
public class Product {
    @JsonProperty("class")
    private String className;

    @JsonProperty("default")
    private boolean isDefault;

    // getters and setters
}

The same applies to keys with hyphens or spaces, like first-name, and keys that don’t follow Java naming conventions, like order_id. Jackson uses the annotation value for both serialization and deserialization, so one annotation covers both directions. If many fields need this, I can set a naming strategy such as @JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class) at the class level instead of annotating every field.”

3. Serialization vs deserialization?

“Serialization converts a Java object into JSON, and deserialization converts JSON into a Java object.

In API testing, I use serialization for the request side, when I build a POJO and send it as the body:

java
String json = mapper.writeValueAsString(bookingRequest);

or simply .body(bookingRequest) in REST Assured, which serializes it automatically. I use deserialization on the response side, when I convert the response into a POJO:

java
Booking booking = mapper.readValue(jsonString, Booking.class);
// or
Booking booking = response.as(Booking.class);

A good way to verify both are working is a round trip: serialize, deserialize, and assert that the objects are equal, which needs equals() and hashCode() implemented, and Lombok’s @Data gives me that.”

4. Does Jackson need a no-arg constructor?

“By default, yes. Jackson creates the object using the no-arg constructor, then populates fields through setters, or directly through fields if they’re public or annotated with @JsonProperty. If a class has only a parameterized constructor, I get an InvalidDefinitionException, saying no suitable constructor was found.

There are a few ways around it. For immutable classes, I use @JsonCreator on the constructor with @JsonProperty on each parameter:

java
public class Address {
    private final String city;
    private final String pincode;

    @JsonCreator
    public Address(@JsonProperty("city") String city,
                   @JsonProperty("pincode") String pincode) {
        this.city = city;
        this.pincode = pincode;
    }
}

With Lombok, I add @NoArgsConstructor and @AllArgsConstructor together with @Data. And on Java 16+ with Jackson 2.12 or later, I can use a record, which Jackson supports directly without extra annotations:

java
public record Address(String city, String pincode) {}

Records are a good fit for response models since they’re immutable and have no boilerplate.”

# Q : 1. Header appears multiple times, like Set-Cookie?

“response.getHeader("Set-Cookie") returns only one value, so it’s not reliable when a header is repeated. I use getHeaders().getValues(...) to get all of them:

java
List<String> setCookies = response.getHeaders().getValues("Set-Cookie");
Assert.assertTrue(setCookies.stream().anyMatch(c -> c.startsWith("session_id=")));

I use the same approach for headers like Via or Warning. In the DSL, a matcher such as .header("Set-Cookie", containsString("session_id")) can be unreliable with multiple values, so I switch to extraction.”

2. How do you assert a header is absent?

“I assert it’s null in the DSL, or check for the header name on the response:

java
.then().header("X-Powered-By", nullValue());

Assert.assertFalse(response.getHeaders().hasHeaderWithName("X-Powered-By"));

I use this for security hygiene. For example, Server or X-Powered-By shouldn’t leak version details like Apache/2.4.1 or Express, since that helps attackers. The same check works for confirming that a sensitive header isn’t returned on certain endpoints.”

3. Content-Type exact match fails?

“This happens because the server often returns application/json; charset=utf-8, so an exact match against application/json fails. I avoid exact string matching here:

java
.header("Content-Type", containsString("application/json"))
// or
.contentType(ContentType.JSON)

ContentType.JSON tolerates the charset suffix. The same applies to text/html; charset=UTF-8. I only use exact matching when the contract specifically requires a charset.”

4. How do you check SameSite?

“Depending on the REST Assured version, the Cookie object may not expose SameSite, so I assert on the raw Set-Cookie header:

java
String raw = response.getHeaders().getValues("Set-Cookie").stream()
        .filter(c -> c.startsWith("session_id="))
        .findFirst().orElseThrow();

Assert.assertTrue(raw.contains("SameSite=Strict"));
Assert.assertTrue(raw.contains("HttpOnly"));
Assert.assertTrue(raw.contains("Secure"));

I filter by cookie name first because a response can set several cookies, and I don’t want to assert against the wrong one.”

5. header() vs headers()?

“header(name, value) validates a single header. headers(...) takes alternating name/value pairs, so I can validate several in one call:

java
.header("Content-Type", containsString("json"))

.headers("Connection", "keep-alive",
         "Cache-Control", "no-cache",
         "X-Content-Type-Options", "nosniff");

On the request side, there’s also headers(Map) and headers(Headers), which I use to send a set of common headers from a shared spec. For readability, I use headers() when I’m validating a group of related headers, like all security headers together.”

6. Security headers I validate

“I check the standard set on key endpoints:

java
.then()
    .header("Strict-Transport-Security", containsString("max-age"))
    .header("X-Content-Type-Options", "nosniff")
    .header("X-Frame-Options", anyOf(equalTo("DENY"), equalTo("SAMEORIGIN")))
    .header("Cache-Control", containsString("no-store"))   // for sensitive responses
    .header("X-Powered-By", nullValue());

For cookies, I verify Secure, HttpOnly and SameSite. Strict-Transport-Security forces HTTPS, nosniff stops MIME sniffing, X-Frame-Options or CSP frame-ancestors protects against clickjacking, and Cache-Control: no-store stops sensitive data being cached. These are quick, cheap checks that catch config regressions.”

7. How is this done in Playwright API testing?

“With Playwright’s APIRequestContext, the response is an APIResponse, and response.headers() returns an object with lowercase keys, so I assert on headers['content-type']:

ts
const response = await request.get('/booking/1');
expect(response.status()).toBe(200);

const headers = response.headers();
expect(headers['content-type']).toContain('application/json');
expect(headers['x-powered-by']).toBeUndefined();   // absent header

// Repeated headers like Set-Cookie
const setCookies = response.headersArray()
    			.filter(h => h.name.toLowerCase() === 'set-cookie');
expect(setCookies.length).toBeGreaterThan(0);

headers() merges repeated headers into one value, so I use headersArray() when a header appears more than once.

For cookies, APIRequestContext stores them automatically and sends them on later calls, so login-then-call flows work without extra code. To inspect them, I use await request.storageState(), which returns the cookies. If I’m working with a browser context, it’s context.cookies():

ts
const state = await request.storageState();
const session = state.cookies.find(c => c.name === 'session_id');
expect(session?.httpOnly).toBe(true);
expect(session?.secure).toBe(true);
expect(session?.sameSite).toBe('Strict');

Playwright exposes sameSite directly on the cookie object, which is a small advantage over REST Assured, where I parse the raw header.”

One correction to my earlier answer: for pure API tests, the cookie read is request.storageState(). context.cookies() applies when you’re using a browser context.

# Q : What is dependency injection in Rest Assured? How does it enhance API testing?
==> In Rest Assured (a popular Java library for API testing), Dependency Injection (DI) is a design pattern where a test class receives its required objects or configuration states from an external framework rather than creating them manually inside the code.
Instead of using the new keyword or global static variables to initialize your endpoints, configurations, request specifications, or database connectors, an external DI container (like Cucumber-PicoContainer, Spring Boot, or Guice) automatically "injects" them exactly when and where they are needed.

How Dependency Injection Works in Rest Assured

To understand its value, consider a standard Behavior-Driven Development (BDD) Cucumber scenario where one step creates a resource and a subsequent step validates or modifies it.

❌ Without Dependency Injection (The Anti-Pattern)

Without DI, QA engineers often resort to static variables or tight coupling to pass data (like a generated userId) between step definition classes. This breaks down instantly during concurrent test runs.
java
public class StepDefinitionA {
    // Sharing state via static variables causes data corruption during parallel runs
    public static String userId; 

    @When("I create a new user")
    public void createNewUser() {
        userId = RestAssured.given()
            .body("{ \"name\": \"John\" }")
            .post("/users").jsonPath().getString("id");
    }
}
Use code with caution.

With Dependency Injection (The Clean Approach)

Using a DI container like PicoContainer, you create a simple, isolated POJO (Plain Old Java Object) called a TestContext. The DI container automatically instantiates this object and passes the exact same instance into the constructors of any step definition class involved in that specific scenario execution thread.
java
// 1. Define a shared, thread-safe memory container
public class TestContext {
    public RequestSpecification requestSpec;
    public Response response;
    public String userId;
}

// 2. Inject it cleanly via the Constructor
public class UserStepDefinitions {
    private final TestContext context;

    // The DI container automatically injects this object at runtime
    public UserStepDefinitions(TestContext context) {
        this.context = context; 
    }

    @When("I create a new user")
    public void createNewUser() {
        context.response = RestAssured.given()
            .body("{ \"name\": \"John\" }")
            .post("/users");
        
        context.userId = context.response.jsonPath().getString("id");
    }
}
Use code with caution.

How DI Enhances API Testing

Integrating Dependency Injection into a Rest Assured automation framework provides several major architectural upgrades:
• Enables Thread-Safe Parallel Execution: In modern API automation, speed is everything. If you share data using static variables, running tests in parallel will cause threads to overwrite each other’s data, leading to flaky tests and false failures. DI gives every single test thread its own isolated sandbox context.
• Seamless State Sharing: API tests frequently involve multi-step user journeys (e.g., Generate Auth Token → Create Order → Get Order Details → Refund Order). DI allows you to safely pass generated tokens, payload IDs, and raw responses smoothly from step to step across different files.
• Eliminates Code Duplication (DRY Principle): Instead of configuring base URLs, base paths, and authorization headers in @Before hooks inside every single test class, you can instantiate a central RequestSpecification once inside your DI configuration module and inject it globally wherever requests are fired.
• Better Maintainability and Loose Coupling: If your authentication mechanism changes from basic auth to an OAuth2 Bearer token, you only need to update the logic inside your injected security component rather than modifying hundreds of lines of code scattered across dozens of test scripts.

# Q :  How do you read test data from Excel or JSON using Java?
==> To read test data in Java, developers use Apache POI for Excel files and libraries like Jackson or Gson for JSON files.
Integrating these libraries allows you to feed dynamic test data directly into your automation frameworks (such as TestNG, JUnit, or Cucumber) without hardcoding values inside your scripts.

1. Reading Test Data from Excel (Using Apache POI)

To read .xlsx files, you need to add the org.apache.poi:poi-ooxml dependency to your pom.xml or build.gradle file.

The Java Implementation

This utility method opens an Excel workbook, navigates to a specific sheet, and reads data row by row, cell by cell:
java
import org.apache.poi.ss.usermodel.*;
import java.io.File;
import java.io.FileInputStream;
import java.io.IOException;

public class ExcelReader {
    public static Object[][] getExcelData(String filePath, String sheetName) {
        Object[][] data = null;
        try (FileInputStream fis = new FileInputStream(new File(filePath));
             Workbook workbook = WorkbookFactory.create(fis)) {
            
            Sheet sheet = workbook.getSheet(sheetName);
            int rowCount = sheet.getLastRowNum();
            int colCount = sheet.getRow(0).getLastCellNum();
            
            // Initialize array (excluding header row)
            data = new Object[rowCount][colCount];
            
            DataFormatter formatter = new DataFormatter(); // Handles cell types smoothly as strings
            
            for (int i = 1; i <= rowCount; i++) {
                Row row = sheet.getRow(i);
                for (int j = 0; j < colCount; j++) {
                    Cell cell = row.getCell(j);
                    data[i - 1][j] = formatter.formatCellValue(cell);
                }
            }
        } catch (IOException e) {
            e.printStackTrace();
        }
        return data;
    }
}

# Q : What are the different types of API authentication?
==> API authentication verifies the identity of the client making a request to ensure they have the proper permissions to access a resource. The most common methods are API Keys, Basic Authentication, Bearer Tokens (JWT), and OAuth 2.0.

1. API Keys (Simplest & Most Common)

An API Key is a unique, long string of characters generated by the server and assigned to a specific user or application.
• How it works: The client passes this static key with every single request. It can be sent in the query parameters (?api_key=xyz), but securely sending it inside a custom HTTP Header is preferred.
• Header Example: X-API-Key: abc123xyz789
• Best for: Public data APIs, read-only metrics, or low-security services (e.g., weather APIs, map widgets).

2. Basic Authentication (Legacy Method)

Basic Auth is a built-in HTTP protocol that sends standard credentials directly across the wire.
• How it works: The client combines the username and password with a colon (username:password) and encodes the resulting string using Base64 encryption.
• Header Example: Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ= (where the string is the Base64 value for username:password).
• Best for: Internal legacy systems or private microservices. It is highly insecure unless used strictly over HTTPS, as Base64 strings can be easily decoded by anyone who intercepts the request.

3. Bearer Tokens & JWT (Session-Based)

A Bearer Token is an access key generated by the server after a user successfully logs in with their credentials. The term "Bearer" literally means "give access to the bearer (holder) of this token."
• How it works: The client logs in once using credentials. The server responds with a token (often a JWT - JSON Web Token). The client stores this token and passes it in the Authorization header for all subsequent API requests.
• Header Example: Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
• Best for: Modern web applications, mobile apps, and single-page apps (SPAs) where a user session needs to be maintained securely without continuously re-sending passwords.

4. OAuth 2.0 (Delegated Authorization Protocol)

OAuth 2.0 is not a single token format, but an entire open-standard framework that allows third-party applications to obtain limited access to a service on behalf of a user.
• How it works: Think of the "Sign in with Google" or "Connect to GitHub" buttons. The application redirects you to Google/GitHub to log in. Once approved, the third-party app receives an access token to fetch your profile data without ever seeing your actual password.
• Best for: Enterprise ecosystems, third-party integrations, and complex token management workflows where security, token expiration, and precise user permissions (scopes) are required.

📊 Quick Comparison Overview

Authentication Type	Security Level	Complexity	Main Use Case
API Keys	Low - Medium	Very Low	Third-party developers accessing public data
Basic Auth	Low	Low	Quick internal testing or simple private APIs
Bearer / JWT	High	Medium	Modern user-centric web and mobile apps
OAuth 2.0	Very High	High	Third-party integrations & enterprise security

# Q : How do you validate response status code, headers, JSON schema, and response time?
==> To validate response details in Rest Assured, you combine its native fluent validation engine (validatableResponse) with hamcrest matchers and schema validation libraries.
Here is a complete, production-ready example demonstrating how to validate the status code, headers, JSON schema, and response time in a single assertion chain.

Step 1: Add the Schema Validator Dependency

To validate JSON schemas, make sure you have the json-schema-validator module added to your pom.xml:
xml
<dependency>
    <groupId>io.rest-assured</groupId>
    <artifactId>json-schema-validator</artifactId>
    <version>5.5.0</version> <!-- Use the version matching your rest-assured core -->
    <scope>test</scope>
</dependency>
Use code with caution.

Step 2: The Unified Rest Assured Assertion Chain

Place your target schema file (e.g., user-schema.json) inside your project directory at src/test/resources/user-schema.json. Then, execute your test using the following structure:
java
import io.restassured.RestAssured;
import io.restassured.http.ContentType;
import org.testng.annotations.Test;

import static io.restassured.module.jsv.JsonSchemaValidator.matchesJsonSchemaInClasspath;
import static org.hamcrest.Matchers.*;

public class ApiResponseValidationTest {

    @Test
    public void validateFullApiResponse() {
        RestAssured.baseURI = "https://example.com";

        RestAssured.given()
            .header("Accept", "application/json")
        .when()
            .get("/v1/users/123")
        .then()
            // 1. Validate Response Status Code
            .statusCode(200)
            
            // 2. Validate Response Headers
            .contentType(ContentType.JSON) // Shortcut method for Content-Type
            .header("Cache-Control", containsString("no-cache"))
            .header("Server", notNullValue())
            
            // 3. Validate Response Time (e.g., less than 2000 milliseconds)
            .time(lessThan(2000L)) 
            
            // 4. Validate JSON Schema
            .body(matchesJsonSchemaInClasspath("user-schema.json"))
            
            // Bonus: Inline field values validation
            .body("id", equalTo(123))
            .body("status", equalTo("active"));
    }
}
Use code with caution.

🔍 Deep Dive into Components

1. Status Code Validation

• .statusCode(200) checks for an exact match.
• You can also pass hamcrest matchers if you want to verify a range (e.g., .statusCode(anyOf(equalTo(200), equalTo(201)))).

2. Headers Validation

• .header("Key", "Exact Value") checks for explicit string matches.
• Use hamcrest matchers like containsString(), startsWith(), or notNullValue() to safely validate headers that dynamically append timestamps or tracking IDs.

3. Response Time Validation

• Rest Assured calculates response time in milliseconds by default.
• You must append an L to your integer value (e.g., 2000L) because the method expects a Java Long type comparison.
• Alternative configuration: If you prefer checking in seconds, use: .time(lessThan(2L), java.util.concurrent.TimeUnit.SECONDS).

4. JSON Schema Validation

• matchesJsonSchemaInClasspath() automatically looks inside your src/test/resources folder.
• If your schema fails validation, Rest Assured outputs a highly descriptive error stack tracing exactly which keys or data types mismatched (e.g., expected type: string, found: integer).

# Q : How do you handle 429 rate limits in API automation tests?
==> Handling HTTP 429 Too Many Requests in API automation requires balancing test speed with server courtesy. If your test suite fires hundreds of requests concurrently (especially during parallel runs), APIs will trigger rate limiters to protect themselves.
You can handle 429 rate limits dynamically using Automatic Retries with Exponential Backoff, Jitter, and by leveraging Server Header Hints.

1. Inspect the 429 Response Headers (The Smart Way)

Well-designed APIs don't just block you; they tell you exactly when you are allowed to try again using standard response headers. Your code should intercept a 429 and parse these headers before waiting:
• Retry-After: Specifies the delay in seconds (e.g., Retry-After: 5) or a specific HTTP-date timestamp indicating when to retry.
• X-RateLimit-Reset: A Unix epoch timestamp indicating when the current rate limit window resets.

2. Implementing the Solution across Frameworks


🛑 The Strategy: Exponential Backoff + Jitter

If multiple parallel tests hit a 429 at the same time, waiting for an exact static window (e.g., 2 seconds) means they will all retry simultaneously, crashing the server again.
• Exponential Backoff: Multiplies the wait time on each subsequent failure (e.g., 1s ➔ 2s ➔ 4s ➔ 8s).
• Jitter: Adds a small amount of randomized time (e.g., ±200ms) to break the synchronization of concurrent test threads.

A. Implementing in Playwright (TypeScript)

Playwright makes this incredibly clean. You can leverage custom interceptors or custom API fixtures to wrap your request utilities with a retry mechanism automatically.
typescript
import { APIRequestContext, APIResponse } from '@playwright/test';

export async function customGetRequest(
  apiContext: APIRequestContext,
  endpoint: string,
  maxRetries = 3
): Promise<APIResponse> {
  let attempt = 0;
  let delay = 1000; // Base delay of 1 second

  while (attempt < maxRetries) {
    const response = await apiContext.get(endpoint);

    if (response.status() !== 429) {
      return response; // Return immediately if successful or failing with a non-429 error
    }

    attempt++;
    if (attempt >= maxRetries) return response; // Give up if max retries exceeded

    // Check if the server told us how long to wait
    const retryAfterHeader = response.headers()['retry-after'];
    let waitTime = retryAfterHeader ? parseInt(retryAfterHeader, 10) * 1000 : delay;

    // Add randomized Jitter to prevent concurrent workers from smashing the API at the exact same millisecond
    const jitter = Math.random() * 300;
    waitTime += jitter;

    console.warn(`⚠️ Hit 429 Rate Limit. Retrying in ${Math.round(waitTime)}ms (Attempt ${attempt}/${maxRetries})`);
    await new Promise((resolve) => setTimeout(resolve, waitTime));

    // Exponentially grow the delay for the next loop if 'retry-after' wasn't provided
    delay *= 2;
  }
  throw new Error(`Failed to execute request due to persistent 429 Rate Limits after ${maxRetries} attempts.`);
}
Use code with caution.

B. Implementing in Rest Assured (Java)

In Rest Assured, you can implement this cleanly by using a custom Filter. Filters intercept the request/response lifecycle globally across your entire test suite.
java
import io.restassured.filter.Filter;
import io.restassured.filter.FilterContext;
import io.restassured.response.Response;
import io.restassured.specification.FilterableRequestSpecification;
import io.restassured.specification.FilterableResponseSpecification;

public class RateLimitRetryFilter implements Filter {
    private static final int MAX_RETRIES = 3;

    @Override
    public Response filter(FilterableRequestSpecification requestSpec, FilterableResponseSpecification responseSpec, FilterContext ctx) {
        Response response = ctx.next(requestSpec, responseSpec);
        int attempts = 0;
        long delay = 1000; // 1 second base

        while (response.getStatusCode() == 429 && attempts < MAX_RETRIES) {
            attempts++;
            
            // Extract the 'Retry-After' header if present
            String retryAfter = response.getHeader("Retry-After");
            long waitTime = (retryAfter != null) ? Long.parseLong(retryAfter) * 1000 : delay;
            
            // Add Jitter
            waitTime += (Math.random() * 200);

            System.out.printf("⚠️ 429 Detected. Retrying in %dms (Attempt %d/%d)%n", waitTime, attempts, MAX_RETRIES);
            
            try {
                Thread.sleep(waitTime);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }

            response = ctx.next(requestSpec, responseSpec); // Re-execute the request
            delay *= 2; // Increase exponential delay boundary
        }
        return response;
    }
}

// How to attach it globally to your Rest Assured instances:
// RestAssured.filters(new RateLimitRetryFilter());
Use code with caution.

3. Architecture & Environment Optimization

If writing retry code feels like putting a band-aid over a larger problem, consider updating your test execution architecture:
• Throttle Parallel Workers: If you are running tests with 20 parallel threads, you may simply be overpowering the infrastructure. Lower your parallel runner counts (e.g., down to 3–5 concurrent threads).
• Whitelisted IPs / Test API Gateways: Request that your DevOps or Engineering team whitelist your automation runner IPs (like GitHub Actions, GitLab CI, or Jenkins nodes) from rate-limiting middleware (such as Cloudflare, AWS WAF, or Nginx limits) inside the Staging/QA environments.
• Use Scopes & Unique Accounts: Instead of running all 100 tests under a single admin@company.com user profile, utilize data-driven patterns to assign unique, dynamically generated user accounts to different test threads to spread out the rate-limiting quotas.
