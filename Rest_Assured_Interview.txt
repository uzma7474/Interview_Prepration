# Q : What are the important validation you will put on a API.

==> When I test an API, I don't validate only the status code. I validate the response at multiple levels—HTTP response, headers, response body, schema, business rules, and data consistency.

1. Status Code Validation
	First, I verify that the API returns the expected HTTP status code.
200 → Successful GET
201 → Resource created
204 → Successful request with no response body
400 → Bad request
401 → Unauthorized
403 → Forbidden
404 → Resource not found
500 → Internal server error

given()
    .when()
    .get("/booking/1")
    .then()
    .statusCode(200);

2. Response Body Validation
	I verify that the response contains the expected data.
.then()
    .body("firstname", equalTo("John"))
    .body("lastname", equalTo("Doe"));

I also validate:

Required fields
Field values
Data types
Null/empty values
Array size
Nested objects

3. JSON Schema Validation

I validate the response structure against the expected JSON schema.

.then()
    .assertThat()
    .body(matchesJsonSchemaInClasspath("booking-schema.json"));

This helps detect issues such as a field changing from:

"bookingid": 123

to:

"bookingid": "123"

4. Headers Validation

I verify important response headers such as:

Content-Type
Authorization
Cache-Control
Location

Example :
.then()
    .header("Content-Type", containsString("application/json"));

5. Authentication and Authorization

I verify:

Valid credentials/token
Missing token
Expired token
Invalid token
User permissions
Access to protected endpoints

For example:

“A user without the required role should not be able to access an admin endpoint.”

6. Request Validation / Negative Testing

I deliberately send invalid requests and verify that the API handles them correctly.

Examples:\
Missing mandatory field
Invalid data type
Invalid ID
Invalid email
Empty request body
Malformed JSON
Invalid query parameter
Duplicate data

Ex: given()
    .body(invalidRequest)
.when()
    .post("/booking")
.then()
    .statusCode(400);

7. Business Logic Validation

This is very important because a 200 status code doesn't necessarily mean the business logic is correct.

For example, for an order API:

“If the quantity is 2 and the unit price is ₹500, I would verify that the total price is ₹1,000.”

Similarly:

Discount calculation
Tax calculation
Order status
Booking dates
Inventory availability
Payment status

8. CRUD / Data Consistency Validation

For CRUD APIs, I verify the complete lifecycle:

POST → Create
GET  → Verify created data
PUT  → Update
GET  → Verify update
DELETE → Delete
GET → Verify resource is no longer available

This verifies that the API actually persists and modifies data correctly.

9. Response Time / Performance

I also validate that the API responds within the expected SLA.

.then()
    .time(lessThan(2000L));

I would mention that the actual threshold should come from the application's performance requirements rather than being arbitrarily chosen.

10. Database Validation

If database access is available, I verify that API operations correctly affect the database.

For example:

“After creating a booking through POST, I can query the database and verify that the booking record was actually created with the expected values.”

11. Idempotency

For APIs where idempotency matters, I verify repeated requests behave correctly.

For example:

“If the same payment request is submitted twice with the same idempotency key, it should not create two payments.”

12. Security Validation

Depending on the API, I also consider:

Unauthorized access
Broken access control
Sensitive data exposure
Injection attacks
Token handling
Input validation

# Status code 
HTTP status codes are three-digit numbers returned by a server to indicate the outcome of an HTTP request. Each code is paired with a standard reason phrase that explains its specific meaning.
The codes are divided into five major categories based on their first digit:

Code Range	Category	General Meaning
1xx	Informational	Request received, continuing process.
2xx	Success	Action successfully received, understood, and accepted.
3xx	Redirection	Further action needs to be taken to complete the request.
4xx	Client Error	The request contains bad syntax or cannot be fulfilled.
5xx	Server Error	The server failed to fulfill an apparently valid request.


Complete List of Common Standard HTTP Status Codes


1xx Informational

• 100 Continue: The server has received the request headers and the client should proceed to send the request body.

• 101 Switching Protocols: The requester has asked the server to switch protocols (e.g., upgrading to WebSockets).

• 103 Early Hints: Used to return some response headers before the final HTTP message.

2xx Success

• 200 OK: The standard response for successful HTTP requests.

• 201 Created: The request has been fulfilled, resulting in the creation of a new resource.

• 202 Accepted: The request has been accepted for processing, but processing is not complete.

• 204 No Content: The server successfully processed the request but is not returning any content in the response body.

• 206 Partial Content: The server is delivering only part of the resource due to a range header sent by the client.

3xx Redirection

• 301 Moved Permanently: The requested resource has been assigned a new permanent URI.

• 302 Found: The requested resource resides temporarily under a different URI.

• 304 Not Modified: Indicates that the resource has not been modified since the version cached by the client.

• 307 Temporary Redirect: The request should be repeated with another URI, but future requests should still use the original URI.

• 308 Permanent Redirect: The request and all future requests should be repeated using another URI.

4xx Client Error

• 400 Bad Request: The server cannot process the request due to a client error (e.g., malformed request syntax).

• 401 Unauthorized: The request requires user authentication. (Strictly speaking, this means "unauthenticated").

• 403 Forbidden: The server understood the request but refuses to authorize it.

• 404 Not Found: The requested resource could not be found on the server.

• 405 Method Not Allowed: The request method (GET, POST, etc.) is not supported for the requested resource.

• 408 Request Timeout: The server timed out waiting for the request from the client.

• 409 Conflict: The request could not be completed due to a conflict with the current state of the target resource.

• 422 Unprocessable Entity: The request was well-formed but was unable to be followed due to semantic errors.

• 429 Too Many Requests: The user has sent too many requests in a given amount of time (rate-limiting).

The Codes Your Monitoring Should Actually Alert On
Out of the 60+ codes above, the ones that earn alert thresholds in most production setups are a much shorter list:

200—as a baseline ratio. A sudden drop means something else is going wrong.
301, 302, 307, 308—redirect counts. Spikes can mean misconfigured routing or a deploy that broke canonical URLs.
400—malformed requests. Usually a consumer-side change.
401, 403—auth and permission failures. Often a token, IAM, or WAF change.
404—missing resources. Background noise as one-offs; a release problem in bursts.
408—client timeouts. Worth alerting at sustained rates; signals slow downstream calls.
429—rate limiting. Either you’re being throttled or your throttle is too aggressive.
500, 502, 503, 504—application, upstream, capacity, and gateway timeout failures. These page on-call.
520-526—Cloudflare edge failures. If you’re behind Cloudflare, these are critical signals because they isolate the failure to the edge-to-origin path.

# Q : What is API and WebServices ?
==> As a 3.5 years experienced API Automation Tester using Rest Assured, I would answer this in an interview like this:

API stands for Application Programming Interface. It is a set of rules that allows two different software applications to communicate with each other. For example, when I use a banking application and request my account balance, the application communicates with the backend through an API and receives the required data.

A Web Service is a type of API that is specifically designed to enable communication between applications over a network, typically using HTTP/HTTPS. Web services commonly use technologies such as REST or SOAP.

In my automation framework, I mainly work with REST APIs and use Rest Assured with Java to send HTTP requests such as GET, POST, PUT, PATCH, and DELETE, and validate the status code, response body, headers, schema, and response time.

Simple Difference
API	Web Service
General mechanism for communication between software components	API that communicates over a network
Can be used locally or over a network	Primarily network-based
Can include REST, SOAP, libraries, SDK interfaces, etc.	Commonly REST or SOAP based
Broader concept	Subset/type of API

     API
      ↓
Backend Server

   Database

# Q : What is the difference between 201 and 204 Status Code?
==> Difference between 201 and 204 Status Codes

As a 3.5 years experienced API Automation Tester using Rest Assured, I would explain it like this:

201 Created and 204 No Content both indicate that the request was successful, but they are used in different scenarios.

Status Code	Meaning	Response Body	Typical Usage
201 Created	A new resource was successfully created	Usually contains the created resource or its details	POST request
204 No Content	Request was successful, but there is no content to return	No response body	DELETE, PUT, or PATCH
Example — 201 Created

Suppose I create a new booking:

POST /booking

Request:

{
  "firstname": "John",
  "lastname": "Doe"
}

Response:

HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 101,
  "firstname": "John",
  "lastname": "Doe"
}

Here, 201 indicates that the server successfully created the booking. The response may provide the newly created resource or its ID.

In Rest Assured, I can validate:

given()
    .body(requestBody)
.when()
    .post("/booking")
.then()
    .statusCode(201)
    .body("id", notNullValue());
Example — 204 No Content

Suppose I delete the booking:

DELETE /booking/101

Response:

HTTP/1.1 204 No Content

There is no response body because the server successfully processed the request and has nothing to return.

In Rest Assured:

given()
.when()
    .delete("/booking/101")
.then()
    .statusCode(204)
    .body(emptyString());
Interview Answer

201 means the request was successful and a new resource was created, so the response may contain details of that newly created resource. 204 means the request was successful, but the server intentionally does not return any response content. In my Rest Assured framework, I validate 201 for resource-creation APIs like POST and 204 for operations such as successful DELETE or update APIs where no response body is expected.

Key point:
201 = Created + response can contain data
204 = Success + no response body

# Q : What is the difference between 401 and 403 Status Code?
==> Difference between 401 and 403 Status Codes

As a 3.5 years experienced API Automation Tester using Rest Assured, I would explain it like this:

401 Unauthorized means the client has not provided valid authentication credentials, or the credentials are missing/invalid.

403 Forbidden means the user is authenticated, but does not have sufficient permission to access the requested resource.

Status Code	Meaning	Authentication	Authorization
401 Unauthorized	Authentication is missing or invalid	❌ Failed	Not reached/irrelevant
403 Forbidden	User is authenticated but not allowed	✅ Successful	❌ Failed
Example of 401

Suppose an API requires a JWT token:

GET /api/admin/users
Authorization: Bearer <token>

If the token is missing, expired, or invalid, the API may return:

401 Unauthorized

In Rest Assured:

given()
    .when()
    .get("/api/admin/users")
    .then()
    .statusCode(401);
Example of 403

Suppose I have a valid token, but my user has a normal-user role and I'm trying to access an admin API:

GET /api/admin/users
Authorization: Bearer <valid-token>

Authentication succeeds, but the user doesn't have admin permission.

The API returns:

403 Forbidden

Rest Assured validation:

given()
    .header("Authorization", "Bearer " + validToken)
.when()
    .get("/api/admin/users")
.then()
    .statusCode(403);

Think of entering an office:

401 → "Who are you?" → You haven't provided valid identification.
403 → "I know who you are, but you can't enter this room." → You are authenticated but don't have permission.
Interview Answer

The main difference between 401 and 403 is authentication versus authorization. 401 indicates an authentication problem, such as a missing, invalid, or expired token. 403 indicates that authentication was successful, but the authenticated user doesn't have sufficient permission to access the resource. In my Rest Assured framework, I create negative test cases for both scenarios by validating the appropriate status code and error response.

# Q : What are the components of an API Request?
==> As a 3.5 years experienced API Automation Tester using Rest Assured, I would answer:

An API request generally consists of HTTP Method, URL/Endpoint, Headers, Query Parameters, Path Parameters, Request Body, and Authentication details. Depending on the API, some components may be optional.

1. HTTP Method

It defines what operation we want to perform.

GET → Retrieve data
POST → Create data
PUT → Completely update data
PATCH → Partially update data
DELETE → Delete data

2. URL / Endpoint

It specifies where the request needs to be sent.

https://restful-booker.herokuapp.com/booking

It generally consists of:

Base URL + Endpoint

For example:

Base URL  : https://restful-booker.herokuapp.com
Endpoint  : /booking
3. Headers

Headers provide additional information about the request.

Common headers are:

Content-Type: application/json
Accept: application/json
Authorization: Bearer <token>

For example:

Content-Type → tells the server the format of request body.
Accept → tells the server what response format the client expects.
Authorization → provides authentication credentials/token.
4. Query Parameters

Query parameters are used to filter or customize the request.

Example:

GET /users?status=active&page=2

Here:

status=active
page=2

are query parameters.

In Rest Assured:

given()
    .queryParam("status", "active")
    .queryParam("page", 2)
.when()
    .get("/users");
5. Path Parameters

Path parameters identify a specific resource.

Example:

GET /users/101

Here 101 is the path parameter.

In Rest Assured:

given()
    .pathParam("id", 101)
.when()
    .get("/users/{id}");
6. Request Body

The request body contains the actual data that we want to send to the server, mainly with POST, PUT, and PATCH requests.

Example:

{
  "firstname": "John",
  "lastname": "Doe",
  "totalprice": 100
}

In Rest Assured:

given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .post("/booking");
7. Authentication / Authorization

If the API is secured, we need to provide authentication details.

For example:

given()
    .auth()
    .oauth2(token)
.when()
    .get("/users");
Complete Request Example
POST https://api.example.com/users?source=web
Authorization: Bearer abc123
Content-Type: application/json
Accept: application/json

{
    "name": "John",
    "email": "john@test.com"
}

Here:

Component		Example
1. HTTP Method		POST
2. Base URL		https://api.example.com
3. Endpoint		/users
4. Query Parameter	 source=web
5. Headers		Authorization, Content-Type, Accept
6. Request Body		JSON user details
7. Authentication		Bearer token
8. Interview Answer

The major components of an API request are HTTP method, URL or endpoint, headers, query parameters, path parameters, request body, and authentication details. In my Rest Assured framework, I use these components based on the API requirement. For example, while testing a POST API, I typically pass the endpoint, headers, authentication token, and JSON request body, and then validate the response status code, headers, response body, and response time.

Easy way to remember:
Method + URL + Headers + Parameters + Body + Authentication.

# Q : What is the difference between Query Parameters and Path Parameters?
==> As a 3.5 years experienced API Automation Tester using Rest Assured, I would explain it like this:

Path parameters are used to identify a specific resource, whereas query parameters are generally used to filter, sort, search, or customize the data returned by an API.

Path Parameter					Query Parameter
Used to identify a specific resource		Used to filter/customize resources
Part of the URL path				Comes after ? in the URL
Usually mandatory when defined by the endpoint	Usually optional
Example: /users/101				Example: /users?status=active
Used commonly for retrieving/updating a 	Used commonly for filtering/searching/pagination
specific resource	

1. Path Parameter
Suppose we want to get a specific booking:
GET /booking/123
Here, 123 is the path parameter.

In Rest Assured:

given()
    .pathParam("bookingId", 123)
.when()
    .get("/booking/{bookingId}")
.then()
    .statusCode(200);

The URL becomes:

/booking/123

The path parameter tells the API which specific booking we want.

2. Query Parameter

Suppose we want to retrieve users based on their status:

GET /users?status=active

Here:

status=active

is a query parameter.

In Rest Assured:

given()
    .queryParam("status", "active")
.when()
    .get("/users")
.then()
    .statusCode(200);

We can also have multiple query parameters:

GET /users?status=active&page=2&limit=10

This could mean:

status=active → filter active users
page=2 → retrieve page 2
limit=10 → return 10 records
Easy Example

Think about an API for products:

/products/101

Path parameter: 101 → "Give me product number 101."

Whereas:

/products?category=mobile&sort=price

Query parameters: category=mobile, sort=price → "Give me mobile products and sort them by price."

Interview Answer

Path parameters identify a specific resource and are part of the URL path. Query parameters are used to filter, search, sort, or paginate the response and are appended to the URL after ?. For example, /booking/123 uses 123 as a path parameter to identify a specific booking, while /booking?status=active uses status as a query parameter to filter the bookings. In Rest Assured, I use pathParam() for path parameters and queryParam() for query parameters.

# Q : Meaning of 405 status code in Postman , what does it means and how to resolve it?
==> As a 3.5-year experienced Rest Assured/API automation engineer, I would explain 405 Method Not Allowed like this:

What does 405 mean?

HTTP 405 – Method Not Allowed means:

The API endpoint exists, but the HTTP method you are using is not allowed for that endpoint.

For example, suppose the API supports:

GET /users/123

but in Postman I send:

POST /users/123

The server may return:

405 Method Not Allowed

So the problem is usually not that the URL doesn't exist. The problem is that the HTTP method doesn't match what the endpoint supports.

Common example in Postman

Suppose the API documentation says:

GET    /booking/{id}       → Get booking
PUT    /booking/{id}       → Update booking
DELETE /booking/{id}       → Delete booking

If I send:

POST /booking/123

I may get:

405 Method Not Allowed
How would I resolve it?

I would check the following:

1. Verify the HTTP method

In Postman, make sure I am using the method expected by the API:

GET
POST
PUT
PATCH
DELETE

2. Verify the endpoint

Check that the URL and path are correct.

For example:

Correct:
PUT /booking/123

Incorrect:
PUT /booking

if the API specifically requires an ID.

3. Check API documentation

I would verify which methods are supported for that particular endpoint.

Sometimes the response also contains an Allow header:

Allow: GET, PUT, DELETE

This tells me which methods are permitted.

4. Check environment/base URL

In an automation framework, I would also verify that I'm hitting the correct environment:

QA
UAT
Production

because different environments can have different API configurations.

5. Check routing/API gateway configuration

If the method is definitely correct but I still receive 405, I would check:

API Gateway
Reverse proxy
Server routing
Web server configuration
Authentication/authorization middleware
HTTP method restrictions
Rest Assured example

If the API expects PUT but I accidentally use POST:

given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .post("/booking/123")
.then()
    .statusCode(405);

I would correct it to:

given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .put("/booking/123")
.then()
    .statusCode(200);
Difference from 404

This is a common interview follow-up:

Status	Meaning
404	Resource/endpoint was not found
405	Endpoint exists, but the HTTP method is not allowed
Interview answer

“405 Method Not Allowed means the requested API endpoint exists, but the HTTP method I'm using is not supported for that endpoint. For example, if an endpoint supports GET but I send POST, I can receive 405. To resolve it, I first verify the HTTP method against the API documentation, then check the endpoint path, request URL, environment, and the Allow header if available. If the method is correct and the issue still occurs, I would investigate API Gateway or server-side routing configuration.”

Easy way to remember:
404 = Wrong/unknown endpoint.
405 = Endpoint is there, but wrong HTTP method.

# Q : how to use objectMapper 

As a 3.5-year experienced Rest Assured + Java automation engineer, I use Jackson's ObjectMapper mainly to convert Java objects to JSON and JSON responses to Java objects.

1. Add Jackson dependency

If you're using Rest Assured, Jackson is commonly used for JSON serialization/deserialization.

<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.2</version>
</dependency>
2. Java Object → JSON

Suppose I have a POJO:

public class User {

    private String username;
    private String password;

    public User() {
    }

    public User(String username, String password) {
        this.username = username;
        this.password = password;
    }

    // getters and setters
}

I can convert it to JSON using ObjectMapper:

ObjectMapper mapper = new ObjectMapper();

User user = new User("standard_user", "secret_sauce");

String jsonRequest = mapper.writeValueAsString(user);

System.out.println(jsonRequest);

Output:

{
  "username": "standard_user",
  "password": "secret_sauce"
}

This is called serialization.

Java Object
     ↓
ObjectMapper
     ↓
JSON
3. JSON → Java Object

Suppose the API returns:

{
  "username": "standard_user",
  "password": "secret_sauce"
}

I can convert it back to a Java object:

ObjectMapper mapper = new ObjectMapper();

User user = mapper.readValue(jsonResponse, User.class);

System.out.println(user.getUsername());

This is called deserialization.

JSON
 ↓
ObjectMapper
 ↓
Java Object
4. Using ObjectMapper with Rest Assured

For example, in a POST request:

@Test
public void createUser() throws Exception {

    User user = new User(
        "standard_user",
        "secret_sauce"
    );

    ObjectMapper mapper = new ObjectMapper();

    String requestBody = mapper.writeValueAsString(user);

    given()
        .contentType(ContentType.JSON)
        .body(requestBody)
    .when()
        .post("/users")
    .then()
        .statusCode(201);
}

However, Rest Assured can also serialize POJOs automatically if Jackson is available:

given()
    .contentType(ContentType.JSON)
    .body(user)
.when()
    .post("/users");

So I don't always need to explicitly call writeValueAsString().

5. Deserialize API response

Suppose the API response is:

{
    "id": 101,
    "username": "john"
}

POJO:

public class UserResponse {

    private int id;
    private String username;

    // getters and setters
}

Then:

Why do I use ObjectMapper?

response.jsonPath().getString("user.email");

I can deserialize the entire response into a Java model:

UserResponse user = mapper.readValue(
    response.asString(),
    UserResponse.class
);

Then I work with normal Java objects.

Interview answer

“I use Jackson's ObjectMapper for JSON serialization and deserialization. writeValueAsString() converts a Java POJO into a JSON string, which I can send as an API request body. readValue() converts a JSON response into a Java POJO, which makes response validation easier, especially for complex nested JSON. In Rest Assured, Jackson can also be integrated automatically so Rest Assured can serialize and deserialize POJOs.”

Easy way to remember:

writeValueAsString() → Java Object → JSON
readValue()          → JSON → Java Object

# Q :  How would you store API response data dynamically?
===> In my automation framework, I store API response data dynamically using Rest Assured with JsonPath, Java collections, or POJO classes, depending on how I need to use the response data in subsequent test steps.

For example, if I create a user through a POST API and receive a dynamically generated user ID, I store that ID and use it in subsequent GET, PUT, or DELETE requests rather than hardcoding it.

1. Store API response data using Rest Assured

Suppose a POST request creates a student and returns this response:

{
  "id": 101,
  "name": "Uzma",
  "email": "uzma@example.com"
}

The ID might change each time the test runs, so I extract it dynamically.

import io.restassured.response.Response;
import static io.restassured.RestAssured.given;

public class StudentApiTest {

    public static void main(String[] args) {

        Response response =
            given()
                .header("Content-Type", "application/json")
                .body("{\"name\":\"Uzma\","
                    + "\"email\":\"uzma@example.com\"}")
            .when()
                .post("http://localhost:3000/students")
            .then()
                .statusCode(201)
                .extract()
                .response();

        // Extract dynamically generated response data
        int studentId = response.jsonPath().getInt("id");
        String studentName =
                response.jsonPath().getString("name");
        String email =
                response.jsonPath().getString("email");

        System.out.println("Student ID: " + studentId);
        System.out.println("Student Name: " + studentName);
        System.out.println("Email: " + email);

        // Reuse studentId in a subsequent GET request
        given()
            .pathParam("id", studentId)
        .when()
            .get("http://localhost:3000/students/{id}")
        .then()
            .statusCode(200);
    }
}

Why this approach?

JsonPath extracts individual fields from the JSON response.

The generated ID is stored in a Java variable.

The same ID is reused in the next API request.

This eliminates hardcoded IDs and makes the test repeatable.

The example assumes the API returns HTTP 201 Created and the response contains an integer id.

2. Store response data in a Map

When I need to reuse multiple response values across test steps, I can store them in a Map<String, Object>.

Map<String, Object> testData = new HashMap<>();

testData.put("email",  response.jsonPath().getString("email"));

String name = (String) testData.get("studentName");

This is useful when the response contains several fields that subsequent requests or assertions need.

3. Store response data using a POJO

For larger responses or strongly typed data, I prefer a POJO (Plain Old Java Object).

public class Student {

    private int id;
    private String name;
    private String email;

    public int getId() {
        return id;

        return name;

    }

Deserialize the response into the POJO:

int id = student.getId();

This approach is easier to maintain when working with complex JSON responses and multiple API endpoints.

4. Where would I store this data in a framework?

Requirement : Approach
1. Extract a single response field : JsonPath
2. Reuse multiple fields in test steps : Map<String, Object>

# Q :  Meaning of 405 status code in Postman , what does it means and how to resolve it?
==> As an Automation and Development Engineer with 3.6 years of experience in Selenium Java and REST Assured, I would explain that 405 Method Not Allowed means the server recognizes the API endpoint, but the HTTP method used in the request is not supported for that particular resource.

1. What does 405 mean in Postman?
For example, suppose I send this request in Postman:
GET https://simple-books-api.glitch.me/orders

But the API endpoint supports only POST for the operation I'm trying to perform. The server may return:
405 Method Not Allowed

This means the HTTP method is not allowed for that resource. The response may include an Allow header indicating which methods are supported.
2. Common reasons for a 405 error
- Incorrect HTTP method: Using GET instead of POST, or POST instead of DELETE.
- Incorrect API endpoint: The URL may point to a resource that does not support the selected method.
- API documentation mismatch: The method used in Postman does not match the API contract.
- Server or proxy configuration: The web server, gateway, or proxy may block certain HTTP methods.
- Trailing slash or routing differences: Some server configurations handle routes with and without a trailing slash differently.

3. How to resolve a 405 error in Postman
1. Verify the API documentation and confirm the supported HTTP method.
2. Check the endpoint URL and resource path.
3. Inspect the response headers, especially Allow, if present.
4. Verify that the request body and headers match the API requirements.
5. If the method is correct, ask the backend team to check routing, gateway, or server configuration.

Important: Missing or invalid authentication usually results in 401 or 403, rather than 405, although server implementations can vary.

4. Example using REST Assured
Incorrect request:
given()
    .baseUri("https://simple-books-api.glitch.me")
.when()
    .put("/status")
.then()
    .statusCode(405);


If the API supports only GET for /status, change the request to:
given()
    .baseUri("https://simple-books-api.glitch.me")
.when()
    .get("/status")
.then()
    .statusCode(200);

The expected status code depends on the API's actual contract.
5. Difference between 404 and 405
Status code		|	Meaning
404 Not Found		|	The requested resource or route was not found.
405 Method Not Allowed	|	The resource exists or is recognized, but the HTTP method is not permitted for it.

Interview-ready answer
"In my API testing experience, a 405 status code indicates that the HTTP method used in the request is not supported by the requested endpoint. When I encounter this error in Postman, I first verify the API documentation, endpoint URL, and HTTP method. I also inspect the response headers for the Allow header. If my request matches the API contract, I coordinate with the backend team to investigate server or gateway configuration issues."

# Q : What are the different types of API authentication?
===> In API testing, authentication is used to verify the identity of a user or client before allowing access to an API. The main types of API authentication I work with or consider during testing are Basic Authentication, Bearer Token Authentication, API Key Authentication, OAuth 2.0, JWT-based authentication, and client certificate authentication.
1. Types of API authentication
Authentication type : 	How it works :	Example
1. Basic Authentication	: Sends a username and password encoded using Base64 in the Authorization header. :	Authorization: Basic <base64-value>
2. Bearer Token Authentication : Sends an access token in the Authorization header. :	Authorization: Bearer <token>
3. API Key Authentication : 	Uses a key to identify or authorize an API client, commonly through a header. :	x-api-key: abc123
4. OAuth 2.0 : 	Uses access tokens issued through an authorization framework to grant scoped access. :	Access token obtained from an authorization server
5. JWT Authentication :  Uses a signed JSON Web Token that the API validates. Often implemented with bearer tokens. :	Authorization: Bearer <JWT>
6. Client Certificate / mTLS :	Uses client certificates to authenticate the client during a TLS handshake. :	Certificate-based client identity
7. HMAC Authentication	: Uses a cryptographic signature generated from a secret and request data. :	Signature in an authorization header

Important distinction: Bearer authentication describes how a token is presented. JWT describes a token format. OAuth 2.0 is an authorization framework that can issue access tokens, including JWTs or opaque tokens.

2. REST Assured examples
A. Basic Authentication
given()
    .auth()
    .basic("username", "password")
.when()
    .get("/api/users")
.then()
    .statusCode(200);


B. Bearer Token Authentication
given()
    .header("Authorization", "Bearer " + accessToken)
.when()
    .get("/api/users")
.then()
    .statusCode(200);


C. API Key Authentication
given()
    .header("x-api-key", apiKey)
.when()
    .get("/api/users")
.then()
    .statusCode(200);


D. OAuth 2.0 access token
given()
    .auth()
    .oauth2(accessToken)
.when()
    .get("/api/users")
.then()
    .statusCode(200);

In a real framework, I would obtain credentials and tokens from secure configuration or an authentication endpoint instead of hardcoding them.

3. How do I test API authentication?
As an Automation Engineer, I cover the following scenarios:
- Valid credentials or token should allow authorized access.
- Missing credentials should return the expected 401 Unauthorized response when authentication is required.
- Invalid or expired tokens should be rejected.
- Insufficient permissions should return 403 Forbidden when the client is authenticated but not authorized.
- API keys should be validated, and revoked keys should not work.
- Tokens should be handled securely and should not appear in logs or reports.
- Protected endpoints should enforce authorization consistently.

4. Interview conclusion
“In my API automation framework using REST Assured, I commonly handle Basic Authentication, Bearer Tokens, API Keys, and OAuth 2.0. I create reusable authentication methods so that tokens and credentials can be managed centrally. I also validate negative scenarios such as missing, invalid, and expired tokens, along with authorization failures, to ensure that APIs are secure.

# Q : What is JWT token?
===> JWT stands for JSON Web Token. It is a compact, URL-safe token format used to securely transmit claims between two parties. In API testing, JWT is commonly used to authenticate users and carry information about their identity and permissions.
For example, when a user logs in successfully, the server may generate a JWT and return it to the client. The client sends that token in subsequent API requests to access protected resources.
1. Structure of a JWT
A JWT typically consists of three parts separated by dots (.).
Header
Token type and signing algorithm


Payload
Claims such as user ID, role, and expiration


Signature
Used to verify token integrity and authenticity


A JWT looks like this:
xxxxx.yyyyy.zzzzz


- Header: Specifies the signing algorithm, such as HS256.
- Payload: Contains claims such as sub (subject), role, and exp (expiration time).
- Signature: Allows the receiver to verify that the token has not been altered and was signed by a trusted party.

Important: A signed JWT is not automatically encrypted. Its header and payload can usually be decoded, so passwords and other sensitive information should not be stored in them.
2. How does JWT authentication work?
1. The user sends login credentials to the authentication API.
2. The server validates the credentials and generates a signed JWT.
3. The client receives and stores the token securely.
4. The client sends the token with subsequent requests using the Authorization header.
5. The server validates the signature, expiration, and required claims before granting access.
Example request header:
Authorization: Bearer <JWT_TOKEN>


3. How do I test JWT authentication using REST Assured?
import io.restassured.RestAssured;
import io.restassured.response.Response;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.*;

public class JwtAuthenticationTest {

    public static void main(String[] args) {

        RestAssured.baseURI = "https://api.example.com";

        String token = "your_jwt_token";

        given()
            .header("Authorization", "Bearer " + token)
        .when()
            .get("/api/profile")
        .then()
            .statusCode(200);
    }
}
In a real framework, I would obtain the token from the login or token endpoint rather than hardcoding it.
JWT test scenarios
- Valid JWT → expected successful response.
- Missing JWT → typically 401 Unauthorized.
- Invalid or tampered JWT → rejected.
- Expired JWT → rejected.
- Valid JWT with insufficient permissions → typically 403 Forbidden.
- Verify that sensitive token data is not exposed in logs.

4. JWT vs. session-based authentication
JWT-based authentication :	Session-based authentication
1. Client sends a token with requests. : 	Client typically sends a session ID in a cookie.
2. Server can validate a signed token without looking up a session, depending on the design. : 	Server commonly maintains session state.
3. Token expiration and revocation require careful handling. :	Sessions can often be invalidated centrally.

Interview conclusion: “JWT is a token format commonly used for API authentication. It consists of a header, payload, and signature. In my REST Assured framework, I would retrieve the JWT from the authentication API, pass it as a Bearer token, and validate successful access as well as negative scenarios such as invalid, expired, and missing tokens.”
